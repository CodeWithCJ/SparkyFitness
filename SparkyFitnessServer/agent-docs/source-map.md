# Source Map: details

Longer notes for the "Source Map" section of [`SparkyFitnessServer/AGENTS.md`](../AGENTS.md). Each one has a one-line link there.

## Route generation endpoints (routeRoutes.ts)

- `routes/v2/routeRoutes.ts` generation endpoints - `GET /api/v2/routes/generate/capabilities` and `POST /api/v2/routes/generate` (preview only, never saves; owner-only; 10 requests per user per 10 min via `utils/userRateLimiter.ts`). Orchestration is `services/routeGenerationService.ts` (loop resizing, shared `prepareRoute` thinning); the engine sits behind `RoutingProvider` in `services/routing/`. `routingConfig.ts` `resolveRoutingProvider(userId)` picks the engine per request: the user's active `valhalla` external provider first (own, then admin-public, then family-shared via `externalProviderRepository.getActiveProviderWithKeyByType`), else none. The base URL is re-checked with the food-provider network policy and DNS-guarded for non-admin owners, the key comes from the encrypted `app_key` and is sent as `api_key`, and nothing is cached so a new provider applies at once. There are no environment variables for routing. Every engine request carries a `SparkyFitness/<version>` `User-Agent`. The type is seeded by migration `20261021120200_add_valhalla_routing_provider_type.sql` and registered in `BASE_URL_FETCHING_PROVIDER_TYPES` in `externalProviderService.ts`; `valhallaProvider.ts` talks to the engine, pure `valhallaManeuvers.ts` decodes polylines and maps maneuvers to cues, pure `loopPlanner.ts` plans loops. `GET /generate/capabilities` reports `{ available, maxAlternatives, style, stops, source }` from `getRouteGenerateCapabilities` (Valhalla: 3 alternatives and all four style preferences; `stops` is false). `POST /generate` answers `{ route, options }`: a loop with `alternatives > 1` runs one `generateLoop` per heading in parallel (`OPEN_OFFSETS`/`PINNED_OFFSETS`), drops a candidate that `routesAreDistinct` (shared, bounded overlap check) says repeats an earlier one, tries further headings one at a time to make up the number, and labels options with the shared `labelRouteOptions`; `style` goes through `restrictRouteStyle` to what `provider.capabilities` supports and `valhallaCosting.ts` maps it to `costing_options` (trail share comes from a best-effort `trace_attributes` call). Saving a generated route posts it to `POST /api/v2/routes` with `source: 'generated'` (the only source a client may choose besides `drawn`; migration `20261021120100_allow_generated_route_source.sql` widens the check). Add an engine by implementing `RoutingProvider` and a case in `routingConfig.ts`; never log the provider error object (it can carry the key).

## Run program routes (runProgramRoutes.ts)

- `routes/v2/runProgramRoutes.ts` - the person's run program and place in it (`/api/v2/run-program`: `GET`, `PUT` to start, switch on or off, move, or set the Diary schedule (`run_days`, `start_date`, `end_date`), `POST /complete` which also records the person's local `day` as `last_done_date` and, given `entry_id`, appends `{index, entry_id, at}` to `completion_log` (newest 200 kept; cleared on a program switch) so the app can show a diary run as part of the program, `POST /effort` which saves a 1 to 10 rating for a workout already done (`rateRunProgramWorkout`: under the row lock, replaces an earlier rating of the same index, keeps the last 40 in `effort_log`, refused for a workout not yet done or another program; a program switch clears it); the tool's `get_run_program` lists recent ratings and, through shared `suggestFromEffort`, notes two hard or two easy in a row); `POST /realign` rebuilds the rest of the plan to end on the goal day through shared `realignProgram`/`applyRealign` (`../shared/src/utils/runProgramRealign.ts`): without `confirmed: true` it only returns the preview (and the options when the goal is unrealistic) and saves nothing; confirmed, it recomputes under the `adjustRunProgram` row lock (the callback also receives the whole stored `program`), refuses a stale preview `token` with 409 and an unrealistic goal without `force` with 400; the person's local `today` comes from the body or their timezone. After a realignment the stored workouts no longer line up with the built-in definition, so adjusts measure against `builtInBaseline` (built-in workouts only while the lengths match). Owner-only (`requireSelfActor`, `run_programs` owner policy). The person's own plans live in `custom_run_programs` (`GET/POST /custom`, `PUT/DELETE /custom/:id`, 30 per person, up to 364 workouts of timed steps, program id `custom:<uuid>`): starting one through `PUT` copies it into `run_programs` (with `name`/`activity`), editing one also updates the active copy and keeps the place, deleting keeps the active copy. `models/runProgramRepository.ts` seeds the stored `workouts` from the built-in program in `../shared/src/utils/runPrograms.ts` (which includes the Zone 2 base, `zone2Base` and `zone2Base4`, whose steps carry the `zone2` effort; the tool lists both by id and the request schema accepts the effort on a custom plan too), completes the due workout in one statement so a repeat cannot skip one, and `adjustRunProgram` applies a change under a row lock with a log entry. The change rules (only upcoming workouts, running eased up to 30% or raised at most 10%) are `../shared/src/utils/runProgramAdjust.ts`, shared by the AI tool `ai/tools/runProgramTools.ts` (`sparky_manage_run_program`; every change needs `confirmed=true`; `set_run_program_schedule` changes the Diary days (names or 0 to 6), first day and goal day through the same upsert; `realign_run_program` (fields `force`, `distance`, `confirmed`) previews the same plan and applies it only with `confirmed=true`, and says nothing was changed for an unrealistic goal; `get_run_program` adds a line when the plan has drifted from the goal day; only `get_run_program` is read-only for MCP keys, and the realign POST is not on the read-only allowlist in `utils/apiKeyScope.ts`) and the contract is `../shared/src/schemas/api/RunProgram.api.zod.ts`

## Lab report scan limits (labReportRoutes.ts)

`POST /api/v2/lab-reports/scan` takes a user's document, so it is bounded on every side. A PDF over `MAX_PDF_PAGES` (30) is refused with `document_too_large` after opening it (which reports the page count) and before any page is read, because text extraction runs on the server's one thread and a PDF declaring thousands of pages exhausted memory; the document is opened with a cap on decoded image size and always released. Text is read page by page from pdf.js's stream (`streamTextContent`) with a running budget of `MAX_RAW_PDF_TEXT_CHARS` (120,000, twice what one prompt takes, counted before whitespace is collapsed) and the stream is cancelled the moment it is spent, never through `extractText`, which builds the whole document's text first; a PDF stream can expand about a thousandfold, so a 14 MB file holding 4.8 million characters took 4.7 s to read in full and is now refused in about 0.1 s. After whitespace is collapsed, text past `MAX_PDF_TEXT_CHARS` (60,000, what one prompt takes) is refused too. Both answer `document_too_large` rather than cutting the text off, because results from the cut-off part would be missing from the review with nothing to say so. A single huge string inside one text item is still read whole, which bounds memory by that string, not by the document. A photo is limited to JPEG, PNG or WebP (`unsupported_media`; HEIC and HEIF are refused because they go through a converter that decodes the whole image and sharp cannot read their headers to bound it first, and the phone app sends JPEG), at most 8M base64 characters, and at most `MAX_IMAGE_PIXELS` (50 million) declared in the header, read without decoding (`image_too_large`), because a small file can declare dimensions that decode to hundreds of megabytes. A file whose header cannot be read is refused as `unsupported_media` rather than passed on. Scans are limited per person (`scanRateLimiter`, 10 per 10 minutes, 429 with `Retry-After`), and the demo account is refused outright (`DEMO_BLOCKED_PATH_PATTERNS` in `middleware/demoGuardMiddleware.ts`) because the document goes to the operator's AI provider. A number the model writes as text is read by `parseNumberText` in `services/labReportScanService.ts`: a single comma is a decimal separator unless it is a thousands separator, meaning three digits follow it and the whole part is one to three digits without a leading zero ("5,4" is 5.4 and "0,007" is 0.007, but "1,130" is 1130), and with both a comma and a dot the last one is the decimal separator. Tests: `tests/labReportScanService.test.ts`, `tests/labReportRoutes.test.ts`, `tests/demoLabReportGuard.test.ts`, and `tests/labReportPdfLimit.test.ts` (real unpdf, no mock).

## Restore (backupService.ts performRestore)

`performRestore` restores while reads keep being served. Under a session-level advisory lock in the `postgres` database (one restore at a time, a second answers 409), it loads the backup into a uniquely named database (`<db>_restore_<hex>`) and the uploads under `uploads/_staging/`, upgrades that copy with `applyMigrations`/`applyRlsPolicies`, then closes the live database to connections, ends its sessions (checked up front: the owner needs `pg_signal_backend` or membership in every connected role, and a non-superuser owner cannot end a superuser's session; autovacuum workers are left to the rename) and renames both databases in one transaction, keeping the old one as `<db>_pre_restore_<stamp>` and the old uploads in `uploads/_staging/pre-restore-<stamp>`. A failure before that commit leaves the live data untouched. Other instances keep running throughout: they fence writes as below, skip scheduled ticks (`services/scheduledJobs.ts`), and lose their sessions at the swap like any client.

While the lock exists, `middleware/restoreWriteFence.ts` (before every route, after CORS) answers non-GET requests with 503 and `Retry-After`, and `getClient`/`getSystemClient` refuse a connection to any sync or write request already running (`runAsWriteRequest`, `isInsideWorkScope`); a write request or scheduled job (`admitted` in `services/scheduledJobs.ts`) still running after the swap gets none either (`restoredSinceAdmitted`: the live database's oid changed), and the check after an acquire runs on the connection just acquired. psql loads with `ON_ERROR_STOP`, after dropping the statements this install cannot run: ownership, grants for roles it lacks or cannot act for, and the few superuser-only statements an older install's dump can hold (`skipStatementsThisInstallCannotRun`). Both read `pg_locks` through `services/restoreLock.ts`, at most once a second, and treat a failed check as a restore in progress unless the database is unreachable (`isConnectionError`), which is a restart the connect retry waits out; 55000 (closed to connections) still counts as a restore. A database an interrupted restore left closed to connections is reopened at startup and when a connection is refused that way, if no restore holds the lock (`reopenAfterInterruptedRestore`). The upload mounts never serve `uploads/_staging`. A restore drops any `<db>_restore_<12 hex>` database an interrupted one left (`dropStaleStagingDatabases`) before loading.
