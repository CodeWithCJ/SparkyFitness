# Architecture resources

## Hevy session persistence

Hevy session persistence lives in `integrations/hevy/hevyWorkoutRepository.ts`: source-lock the import, then lock its existing session and calorie participants before library preparation, matching the session → allocation → library order used by history deletion. Reuse that transaction's client throughout preparation, adopt legacy sessions through child source IDs, and update a complete workout in one transaction. Best-effort metadata/preset writes use savepoints when borrowing the client. Logged sessions carry nullable `source_id`; update included Hevy sessions in place. After a complete live fetch and successful processing, reconcile missing session source IDs only within that fetched date window; raw replays never infer deletion. Clear calorie links before removing missing or empty sessions. Compare session names/descriptions to the previous provider snapshot to preserve local edits, and defer per-entry calorie reapplication until the whole session is reconciled. `hevyWorkoutIdentity.ts` reserves uniquely distinguishable provider occurrences before ordinal matches and refuses ambiguous edits/removals/replays without changing stored data. Raw details retain known template identity separately under `identity`; deleted-library snapshots keep their metadata and NULL library link. Untimed duration stays allocated once across reorders, and manual-field protection includes actually edited sets and their derived distance. `exerciseCalorieLinkService.ts` treats Hevy as the workout side of a calorie link through shared `isCalorieLinkWorkoutSource`, while the health recording remains the synced side. Health range cleanup retains re-sent source IDs for in-place updates, but clears links and removes missing recordings using the existing day-range behavior for both Hevy and app-logged workouts.

When legacy entries are adopted from several sessions, reconcile only those superseded parent IDs after moving the entries and reapplying their calorie link. Remove an empty, unidentified Hevy shell only if it has no remaining entries, activity details, feedback, custom notes, location, description or nonstandard format. The participant locks hold the parent rows throughout this check.

`utils/manualFields.ts` resolves sparse set edits against the stored sets loaded under the entry lock. Reserve all stored ID matches first, then fall back to an unclaimed set number for omitted or stale client IDs; each stored set supplies omitted fields at most once. Missing fields retain their values, explicit nulls clear nullable fields (full web-editor saves serialize cleared values as null), and rows absent from the submitted list are removed. Use the same resolved sets for persistence, change detection, derived distance and calorie estimation so an unchanged save does not freeze later provider updates. `prepareCalorieEstimator` reads the exercise/user inputs before the transaction and returns a calculation that needs no further database connection when the locked sets become available.
