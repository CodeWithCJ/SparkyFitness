# AGENTS.md

_Last updated: 2026-10-30_

SparkyFitness Mobile is a React Native 0.86 + Expo SDK 57 app for syncing Apple Health / Health Connect data with the SparkyFitness backend, tracking nutrition, hydration, fasting, measurements, exercise, saved foods, meal templates, custom exercises, workout presets, iOS / Android widgets, the active workout HUD, and the Sparky AI chat.

This is the package guide for `SparkyFitnessMobile/`. Work from this directory for mobile implementation and validation. If a task crosses into the backend, frontend, or `shared/`, read that package guide too before editing outside mobile.

## Scope And Style

- TypeScript is strict. Keep changes type-safe and compiling cleanly.
- Prefer small, direct changes that fit the existing screen, hook, and service boundaries.
- For ambiguous bugs, prove which layer is failing before patching. One narrow diagnostic check beats speculative edits across multiple layers.
- Do not replace a working implementation with a rewrite unless the requester explicitly approves that direction.
- When asked to plan work, confirm scope with clarifying questions before exploring code or drafting the plan.
- Run scripts from `SparkyFitnessMobile/`, except root package operations such as `pnpm install` for patched dependencies.
- Treat `android/` and `ios/` as generated output when possible. Edit `app.config.ts`, `plugins/`, `targets/`, JS/TS sources, or patch files first, then regenerate with prebuild when needed.

## Stack And Imports

- Primary stack: React 19.2, React Native 0.86, Expo SDK 57, TypeScript 6, React Navigation 7, TanStack Query 5, Uniwind / TailwindCSS v4, Reanimated 4, Skia, Victory Native, Expo Background Task / Task Manager / Notifications, Zustand, assistant-ui + AI SDK (chat).
- `@/*` maps to this package and `@workspace/shared` maps to `../shared/src/index.ts`.
- Prefer `@workspace/shared` schemas, constants, date/timezone helpers, and types over local duplicates.
- The app talks to the backend under `/api`; health uploads go to `POST /api/health-data`.
- Global `fetch` is Expo's WinterCG `expo/fetch`, so React Native's `{uri, name, type}` FormData file parts throw "Unsupported FormDataPart implementation". Append an `expo-file-system` `File` (it implements Blob) for multipart uploads; see `pregnancyPhotosApi.ts`.
- Server-stored distance/weight units are metric. UI conversion belongs in mobile helpers such as `unitConversions.ts`.

## Localization contract

English (`en`) is the canonical source locale and the deterministic fallback. Feature developers must add/update the English catalog, use semantic static keys, provide explicit English fallback/defaultValue text, use count-based i18next pluralization, use app-locale date/number/unit formatters, and avoid user-facing hardcoded text. Custom, user, and server content stays literal.

Feature developers do not need to know or translate Polish or any future language, and do not need to wait for Weblate. Translators/Weblate own Polish and future translations and linguistic QA. Missing translation content is non-blocking and falls back to English; existing translated content remains structurally validated.

The shipped locale registry is `src/localization/localeRegistry.json`, read through the typed accessors in `src/localization/localeRegistry.ts`. Adding a catalog to Weblate does not ship it. Shipping requires explicit registry enablement plus native/platform support verification. RN catalogs and native resources are separate surfaces (Expo metadata, Android widget resources, and iOS widget/Live Activity `.lproj` resources), each its own Weblate component and each synced by `.github/workflows/sync-translations.yml`. Only the `en` side of any surface is edited by hand; the i18n audit blocks on registered locales and reports unregistered ones without failing. The workflow pulls the widget resources for registered locales only, because Android and iOS compile whatever resource directories are present and there is no build-time registry check for them.

## App Shell And Navigation

- `App.tsx` is the root composition point. `App()` wraps `QueryClientProvider`, `KeyboardProvider`, `GestureHandlerRootView`, and `BottomSheetModalProvider`; `AppContent()` owns `NavigationContainer`, `SafeAreaProvider`, navigators, `AddSheet`, auth modals, the embedded/floating active-workout bars, the tab-bar `WhatsNewBanner`, and toasts.
- App-shell logic lives in dedicated hooks that `AppContent` composes: `useAppBootstrap` (`src/hooks/useAppBootstrap.ts`) owns language initialization, initial-route selection, the initial linking-enabled state, and splash hiding; `useAppStartup` (`src/hooks/useAppStartup.ts`) owns the one-time startup services (theme, notifications, notification actions, background sync, HealthKit observers); `useAutoSyncOnOpen` (`src/hooks/useAutoSyncOnOpen.ts`) for cold-start/foreground-return sync and the observer-yield window; `useAddSheetActions` (`src/hooks/useAddSheetActions.ts`) for AddSheet handlers and last-active-tab tracking. Error-boundary-wrapped `Safe*` screen components live in `src/navigation/safeScreens.tsx`.
- The What's New screen (`WhatsNewScreen`) uses coded mockups, not images, and its banner is gated on `WHATS_NEW_CONTENT_VERSION`. Use the `whats-new` skill to update it; the `What's New Drift` workflow keeps an issue open listing features since the last bump.
- Startup initializes theme, haptics, sounds, notification prefs, logs, timezone bootstrap, background sync, pending cache refreshes, fasting/hydration card visibility, and platform health observers.
- Initial route comes from `getActiveServerConfig()` inside `useAppBootstrap`: no active config lands on `Onboarding`; otherwise users enter `Tabs`. A language-initialization failure is logged and never changes the route.
- Deep links are enabled only after startup confirms `Tabs`, so widget links do not bypass first-run onboarding.
- `CompareReport` is a stack route (`SafeCompareReport`, title `screens.compareReport`) opened from the Reports hub.
- Navigation source of truth is `App.tsx` plus `src/types/navigation.ts`; update both and the linking config when routes change.
- Root stack uses `@react-navigation/native-stack`. Tabs use `@react-navigation/bottom-tabs`.
- Tabs are `Dashboard`, `Diary`, `Add`, `Library`, and `Settings`. `Add` is a center action in `CustomTabBar`, not a content screen.
- Native iOS Liquid Glass tabs use `@bottom-tabs/react-navigation` in `src/components/TabsLayout.tsx`; each content tab is wrapped in its own `createNativeStackNavigator` so the tab path still gets native headers. The `Add` tab uses `role: 'search'`, which the iOS 26 SDK draws as the detached round button. The iOS 27 SDK no longer does, so `patches/react-native-bottom-tabs@1.4.0.patch` (a pnpm patch) leaves the role off on iOS 27+ and sets the tab controller's `prominentTabIdentifier` (the iOS 27 API for a separated trailing tab) to that tab instead. Drop the patch once the library does this itself.
- `TabsLayout` switches at runtime via `useNativeIOSTabsActive()` (`services/nativeTabBarPreference.ts`): native tabs require iOS 26+ Liquid Glass support AND the user's `liquidGlassTabBarEnabled` preference (opt-in). Everything else renders `CustomTabBar` (`TAB_BAR_HEIGHT = 56`); `ActiveWorkoutBar` reads the native tab-bar height instead when native tabs are active.
- When adding a root-stack screen, add the route to `RootStackParamList` and register a matching `<Stack.Screen>` in `App.tsx` with `createStackScreenOptions(...)` or equivalent explicit iOS native-stack header options.
- Native header option/button builders live in `utils/nativeHeaderItems.ts` (`createIOSNativeHeaderOptions`, `createIOSSmallNativeHeaderOptions`, text/icon button items); header action colors come from `useHeaderActionColors`, which is Liquid-Glass-aware on iOS.
- Root-stack screens with a screen-owned React header are automatically checked by `__tests__/navigation/nativeHeaderContract.test.ts`; do not add screen-specific native-header allowlists.
- Root-stack screens with a screen-owned React header and a real back button must set `headerBackTitle` or `headerBackButtonDisplayMode: 'minimal'` in `App.tsx` so iOS back labels stay explicit or intentionally hidden; close/cancel modal headers do not need either option.
- Declare screen headers with `useScreenHeader(config)` (`src/hooks/useScreenHeader.tsx`). One declarative descriptor (`title`/`nativeTitle`, `left`/`right` items of kind `back`/`dismiss`/`text`/`icon`/`primary`/`menu`, `busy`/`disabled`, `animateKey` for view↔edit cross-fades) renders both paths: on the native path it mirrors items into `unstable_header{Left,Right}Items` via a layout effect and returns `null`; on the custom path it returns the bar element for the screen to render. A `menu` item is a declarative dropdown (plain actions and/or titled single-select sections, optional accent-dot `showsBadge`): the native path builds a system UIMenu header button, the custom path renders the trigger plus an `AnchoredMenu` under it — one item list drives both, as in `FoodsLibraryScreen`'s ownership filter. Hook screens must not keep hand-rolled header code (no `unstable_header*Items` blocks or custom bars alongside the hook) — the contract test enforces this.
- Path selection is `useNativeIOSHeadersActive()` (`services/nativeTabBarPreference.ts`): always false on Android; on iOS it is true below iOS 26 (classic native headers) and follows the Liquid Glass toggle on iOS 26+, so turning the toggle off swaps in the same screen-owned fallback headers Android renders.
- One-accent rule: exactly one primary header action per screen (`kind: 'primary'` or `role: 'primary'`), enforced with a `__DEV__` throw; primary header save buttons fall back to the localized `t('common.save')` / `t('common.saving')` labels when no `label`/`busyLabel` is supplied. Footer-save forms mark their header Save `placement: 'native-only'` so the custom bar does not duplicate the sticky-footer button. `onPress` handlers dispatch through the hook's internal ref map — do not add per-screen handler-ref effects for native header buttons.
- A **right-slot** `kind: 'primary'` press is wrapped in the shared synchronous duplicate-press guard (`utils/duplicatePress.ts`, same one `FooterSaveBar` uses): presses inside `DUPLICATE_PRESS_WINDOW_MS` collapse to one. `disabled`/`busy` are React state and have not committed when taps queued behind a blocked JS thread replay, so every queued press otherwise ran the handler again (#2191). The guard is deliberately time-based, not a latch on `busy`, because handlers that never report a pending state would leave the button dead. **Left-slot** primaries are exempt — that slot is navigation, and `CycleOnboardingScreen` uses the sugar for a wizard Back where repeated presses are intended. A screen that needs a rapidly repeatable right-slot action must not use `kind: 'primary'`.
- If a root-stack screen is intentionally presented above `Tabs` instead of inside native-tabs mode, document it in `NATIVE_TABS_ROUTE_EXCLUSIONS` in `__tests__/navigation/nativeHeaderContract.test.ts` with a short reason.
- Screens intentionally off the hook (e.g. `FoodSearchScreen`'s bespoke anchored-menu bar) must mirror custom actions with `unstable_header{Left,Right}Items` themselves, hide the screen-owned React header behind `useNativeIOSHeadersActive()` with a guard such as `{!usesNativeHeader && <Header />}`, and gate the `useLayoutEffect` that sets native header items on the same flag; otherwise iOS renders both headers.
- When adding a tab, update `TabParamList`, `NativeTab.Screen`, and `FallbackTab.Screen`; for content tabs also add a tab-local native stack screen using `createIOSNativeHeaderOptions(...)`.
- `__tests__/navigation/nativeHeaderContract.test.ts` enforces this native-header wiring. If it fails, fix the route/type/navigator alignment instead of weakening the test.

How each item looks below the tiles is `ADD_MENU_ITEM_ROW_STYLES`, its tile colour `ADD_MENU_ITEM_TINTS` (`constants/addMenuItems.ts`); `AddMenuIconTile` draws the tile for the sheet and its settings. The handler fixes the day once (the Diary's active date, else the diary store's), and every hop is a `replace` guarded by `isFocused()` and a one-shot latch, so a save that resolves after the user left never moves the stack. Each step shows "Check-in: Step N of 3"; steps 1 and 2 have Skip and "Save & continue", and steps 2 and 3 have a Back in the same bar that replaces the step with the one before (disabled while a save or a photo is pending). Skip and Back ask first when the step has edits: on `MeasurementsAdd` when the form differs from what the day holds (a value typed and cleared again is not an edit), on the mood forms once any field has been touched. Every step saves on its own, so going back drops nothing that was saved, and `MeasurementsAdd` remembers its own writes (`stepSavedRef`) so a retry after a partial failure, Skip or Back still reports the step as saved. "Save & continue" moves on without writing on `MeasurementsAdd` when nothing differs from the day's values and on the one-entry mood form while it is untouched (so an untouched form never saves its default mood); the multi-check-in composer keeps it disabled until the check-in has content, leaving an empty step to Skip. Steps 2 and 3 lock the date (no `CalendarSheet`, so the global diary date is untouched). The steps keep to logging the day: inside the flow `ProgressPhotos` leaves out Compare and Time-lapse (its capped history note no longer points at them) and the Log weight prompts (`PhotoDayWeight` without `onLogWeight` shows only a stored weight), since step 2 logs the weight and those prompts open a `MeasurementsAdd` with a date picker. Step 3 has a Close X and a header Finish, both disabled while a picked photo is processed, uploaded or deleted. Photos save as they are added, so on step 3 the X, Finish, system Back and the iOS swipe down all finish the flow (the last two through a `beforeRemove` listener calling `onNavigatorClose`; while a picked photo is still on its way it waits until the photo has landed or failed): it goes back, shows "Check-in complete" when a step saved something and, after a new mood check-in, makes the one-time reminder offer that `MoodLog` otherwise makes on leaving. Leaving at steps 1-2 (X, system Back, a swipe) keeps what was saved, without the toast or the offer; the step-bar Back never leaves the flow (on step 3 it returns to step 2 carrying whether a photo was saved). A `checkinId` from elsewhere turns the flow off; the flow only edits the check-in its own step 1 created, which it carries as `guidedCheckIn.moodCheckin` (id and the day it was saved on) so going back to step 1 opens it for editing instead of adding another (no Delete there, an unchanged edit moves on without writing, and a check-in deleted meanwhile is replaced by a new one, decided only once the day's list has finished loading or refreshing, since a list cached before step 1 created the check-in lacks it; a failed load shows Retry rather than a Back that would close the flow). On an older one-entry server step 1 saves over the day's mood, as the standalone form does. Each hop also records the check-in in progress (day, step to open, flags) in `stores/guidedCheckInStore.ts`, a device-local persisted store cleared when step 3 finishes and on an account or server switch (`useAuth`'s identity-change reset); Check-In in the Add menu (`startGuidedCheckIn`) asks "Continue your check-in?" when one was left on the same day, with Continue (opens the recorded step) and Start over (clears it; a new mood check-in is added rather than the earlier one edited). Its Mood row opens `MoodLog`, and the Dashboard has a toggleable `mood` card (today's mood, 7-day trend) that opens it (mood faces, tags, a Journal box, and a mood-over-time chart). `useMoodCheckinsSupport` probes `GET /api/mood/date/<today>` with `X-Mood-Model-Version: 2` the first time the `mood` card, `MoodLog` or `MoodDay` mounts, and the answer is cached for the session: an array back means the server takes several check-ins a day and any other answer keeps the one-entry-per-day screen via `POST /api/mood`. A failed probe with nothing known shows a Retry on `MoodLog` and `MoodDay` (`components/mood/MoodSupportCheckFailed`) rather than either form, because the one-entry POST on a v2 server edits the day's latest check-in instead of adding one. On a v2 server the `mood` card shows one mood per day (the average of your own moods, else the Garmin or imported one), its body always opens `MoodDay` (the day's check-ins in time order with the day's averages; tap to edit in `MoodLog`, swipe or long-press to delete, Add check-in for a new one), which replaces itself with `MoodLog` for the day on an older server, and its "+ Log" (shown when no mood is logged) opens `MoodLog` for a new check-in. `MoodLog` takes an optional `checkinId` to edit; a new check-in for today goes on the profile zone's today even when the dashboard passed the device's day (`utils/moodDay.ts` `moodDayInZone`, which `MoodDay` also uses so its list shows that day; its redirect to the one-entry form keeps the requested day); each face writes the shared `moodFaceValue` (Sad 10 to Excited 90, as on the web); every field is optional but at least one is required, the mood can be left unset (tapping the selected face clears it), the time row opens `TimeSheet` and stays on the current time until set, and edit mode has Delete check-in. The mood report and history chart use one value per day. It also has optional 1-5 Energy and Focus taps (`components/mood/RatingSelector`) that are sent only when changed on the screen (absent means keep, `null` means clear); `useMoodRatingsSupport` applies only to the one-entry-per-day form; it hides them when the server's mood rows lack `energy_value` and shows them when there are no rows to tell, and a save whose response lacks the key shows a one-time "update your server" toast. Its Progress Photos row opens `ProgressPhotos` on the diary's active date. Its Mindfulness row opens `MindfulnessLog` (`MindfulnessLogScreen`), a root-stack modal laid out like `MoodLog` and `MeasurementsAdd` (screen header, scrolling form, sticky `FooterSaveBar`, so the navigator owns Android's Back); `MindfulnessDetail` opens the same screen from the Log Mindful Session row on its Practice & Log tab and, with a `session` param, from Edit on its History tab, so it has no log form of its own. Session type names and icons come from `utils/mindfulnessSessionTypes.ts`, shared by the log screen, the detail screen and `MindfulnessCard`; the list is the shared `mindfulnessSessionTypeSchema`, and a stored type it does not have shows as Other and is kept on save. Paced Breathing and the Meditation Timer keep Finish & Save on screen while the save runs, so they go through `useSaveOncePerRun`: a run is saved once (presses are dropped until the practice is reset, taps replayed before that reset renders included), a failed save can be retried, and a save from a run closed while pending does not reset the next one. `MindfulnessLog` goes back after a save only while it is still focused, because it can be opened from a screen other than the tab host. Keep `AddSheet`'s present/dismiss refs intact to avoid Android re-present loops. Android's hardware Back in `AddSheet` does what the sheet's own Back link does: from the Exercise menu it returns to the main menu, from the main menu it closes the sheet.
- `useNavigationActionGuard` locks navigation-triggering actions while a native-stack transition is running (idle-callback unlock on re-focus, 5s safety release) so double-taps cannot queue duplicate screens; Library create actions use it.
- `ActiveWorkoutBar` is mounted outside normal screen trees, uses the root navigation ref, and hides itself on modal/editor routes such as food search/forms/scan/photo, exercise search, workout/activity add, measurements, mindfulness log, and barcode edit.
- Most screens are wrapped with `withErrorBoundary(...)`; `SettingsScreen` also uses section-level recovery so settings remain reachable.

## React Query And Local State

- Meal mutations invalidate meals, recent meals, search, and details; food entry creation can affect recent meals.
- Exercise/workout preset list/search/detail invalidation belongs in their mutation hooks.
- `useUpsertCheckIn` updates measurement queries and calls `refreshHealthSyncCache(queryClient)`.
- Custom measurement categories are managed in `CustomCategoriesScreen` / `CustomCategoryEditScreen` (Settings > Custom Measurements) through `useCreateCustomCategory` / `useUpdateCustomCategory` / `useDeleteCustomCategory`, which invalidate the category list and every cached custom-entry day because entry rows embed their category.

- App-local toggles live in `stores/appPreferencesStore.ts` (Zustand `persist`, single AsyncStorage key `@SparkyFitness/app-preferences`): haptics, sounds, notifications, hydration/fasting card visibility, Ask Sparky and progress photos card visibility, the Liquid Glass tab bar opt-in, the guided check-in opt-in (`guidedCheckInEnabled`, edited in `DiarySettingsScreen`, adds the AddSheet's Check-In row), the active-workout metric column, the default rest period (`defaultRestSec`, edited in `WorkoutSettingsScreen`), mood check-in reminders (`checkinRemindersEnabled`, `checkinReminderTimes`, edited in `NotificationSettingsScreen` and offered once after the first check-in), hydration reminders (`waterReminderEnabled`, `waterReminderIntervalHours`, `waterReminderWindowStart` / `waterReminderWindowEnd`, edited in `NotificationSettingsScreen`), the Health Trends layout (`healthTrendOrder` + `hiddenHealthTrends`, edited in `HealthTrendsSettingsScreen`), the Reports layout (`reportOrder`, `hiddenReports`, `reportDefaultRange`, `hiddenReportSections`, `reportNutrientOrder`, `shownReportNutrients`, edited in `ReportsSettingsScreen`), the Compare report's recent questions (`compareRecentQuestions`, newest first, max 5, written by `CompareReportScreen` and read through `knownCompareQuestions`, which drops any a later build no longer knows), and the Apple Watch layout (`watchPageOrder` + `hiddenWatchPages`, the Goals page's `watchNutrientOrder` + `shownWatchNutrients`, and `watchSetInputStyle`, all edited in `WatchSettingsScreen`). ## Health Sync

- `src/services/healthConnectService.ts` is Android orchestration; `src/services/healthConnectService.ios.ts` is iOS orchestration. They are substantial platform implementations, not thin wrappers.
- Both orchestrators batch metric reads with `runTasksInBatches`, a concurrency of 3, and per-metric timeouts. Preserve timeout and partial-error handling.
- Bootstrap timezone state before sync. `ensureTimezoneBootstrapped(...)` runs at startup and `healthDataApi.ts` enforces it before upload.
- Preserve `record_timezone` and `record_utc_offset_minutes` when available.
- Manual sync, sync-on-open, foreground-return sync, background sync, and iOS observer-triggered sync share coordination logic. Preserve claim/in-flight guards and cooldown recording.
- Health uploads are chunked. Simple measurements use large chunks; sleep sessions use smaller session chunks; exercise/workout records are grouped by source to match server delete-then-insert behavior.
- Sync result objects include `syncErrors`; callers should surface partial failures and avoid advancing `lastSyncedTime` when any metric read failed.
- `backgroundSyncService.ts` uses overlap windows for sessions and day-aligned rolling windows for cumulative metrics and nutrition. Do not collapse those into one naive window.
- On iOS, cumulative metrics should use HealthKit statistics queries, not raw sample summation. Active energy (Active Calories, and the active part of Total Calories) can instead use the Move ring: with the account setting `use_move_ring_active_calories` on (an iPhone-only switch on `CalorieSettingsScreen`; `healthkit/provider.ts` and the Sync screen preview read it through `fetchMoveRingActiveCaloriesSetting` on every read; a failed fetch fails the calorie read so the sync retries, never a remembered answer that could belong to another account), each day uses the ring's calories (`HKActivitySummary`, `activeEnergyByDay`) so it matches the Fitness app, and a day with no ring keeps the statistics sum, because a denied or unanswered activity summary permission reads as no rings rather than an error. The activity summary read is requested with both calorie metrics whether the setting is on or not, so the switch needs no permission step and a new phone already has it.
- On Android, cumulative metrics (`Steps`, `Distance`, `ActiveCaloriesBurned`, `TotalCaloriesBurned`, `FloorsClimbed`) use Health Connect `aggregateGroupByPeriod` once per range. Native source-priority dedup should match Health Connect UI; do not reintroduce JS `Math.max` or source allowlist dedup.
- Android read helpers return `{ records, error }` via `readHealthRecordsDetailed` and `aggregateCumulativeMetricByDayDetailed`; legacy wrappers unwrap only records.
- Android sleep sessions are uploaded with one per night: `postProcessRaw` passes them through `keepMostDetailedSleepSessions` (`services/healthconnect/index.ts`) before the HRV/RHR enrichment, so when two apps wrote the same night (same wake day, overlapping for at least half of the shorter session) only the more detailed session goes up, by the shared `keepMostDetailedSleep` rule (`shared/src/utils/sleepSameNight.ts`: among sessions at least 80% as long as the longest, more stage kinds, then more stages, then the longer session). Every session is sent as `Health Connect`, so the server would otherwise merge both apps' nights into one entry (#2839). A nap that does not overlap the night still goes up. iOS does not do this yet.
- Android exercise sessions are enriched with `aggregateRecord` for active, total, and basal calories plus distance and steps over the session window. Active/total calories start scoped to `dataOrigin`, while basal energy remains unfiltered; `total - basal` is compared as an active-energy candidate. Incomplete or implausible active/total pairs retry without the origin filter so Health Connect can apply source priority. Distance and steps always stay origin-scoped; never infer workout steps from an unfiltered clock-window query.
- iOS exercise-session steps must come from statistics attached directly to the `HKWorkout`. Do not infer workout steps by querying all step samples in the workout's clock window.
- iOS HealthKit locked-device failures surface as database-inaccessible warnings. Do not treat these as successful empty reads.
- `app.config.ts` grants `android.permission.health.READ_HEALTH_DATA_HISTORY` so Android can read data older than 30 days.
- Health Connect permission migrations belong in `services/shared/healthPermissionMigration.ts`, not UI-only state. iOS does not use that version: `refreshEnabledMetricPermissions` asks HealthKit through `hasUnrequestedHealthPermissions` and requests only when an enabled type was never asked about, so bump the version for Android permission changes only.
- Core check-in measurements use `measurementsApi.ts` and `MeasurementsAddScreen`; preserve `upsertCheckIn` omitted-vs-null semantics. `MeasurementsAddScreen` holds measurements only: mindfulness is logged from the Add menu's Mindfulness row and the Dashboard's `MindfulnessCard`, not from this screen.
- "Import Full History" (`ImportHistoryScreen`, reached from `SyncScreen`) is a one-time resumable backfill: `backfillService.ts` walks 30-day day-aligned windows newest-first from start-of-today down to a probe-derived floor (`readEarliestRecord` on both providers), one upload per window, with a per-server checkpoint in `backfillCheckpoint.ts`. It never advances `lastSyncedTime` and never runs writeback; while it runs, `isBackfillRunning()` (autoSyncCoordinator) makes background sync skip.
- The backfill's metric set is FROZEN in its checkpoint at first run; resume uses the frozen set verbatim and toggle changes require Start Over. Quota exhaustion, locked device, and app-inactive are expected mid-run stops — the checkpoint keeps them resumable.

## Health Writeback

- Writeback sends Sparky diary nutrition and hydration back to Apple Health on iOS and Health Connect on Android.
- Platform split: `services/writeback.ios.ts` re-exports `healthkit/writeback.ts`; `services/writeback.ts` re-exports `healthconnect/writeback.ts`.
- `runWriteback()` runs after inbound sync in its own try/catch. Writeback failures must not block inbound sync results.
- Writeback is opt-in per metric and gated on write permissions. Android production permissions include `WRITE_NUTRITION` and `WRITE_HYDRATION`; other write permissions are dev-only.
- Imported health entries are skipped to avoid echo loops. iOS sets the app bundle id as the own-source guard; Android relies on source metadata.
- Per-day content-signature hashing skips unchanged days. Each run deletes prior tracked UUIDs then saves fresh records; failed deletes are retried next run.
- `HealthDataWriteback` on `SyncScreen` owns the remove flow. `BottomSheetPicker` offers all-time purge or date range through `DateRangeSheet`; both call `removeWrittenData(range)` and clear tracking.
- Inbound iOS nutrition sync reads food correlations with a rolling nutrition lookback and upserts by `(source, source_id)` server-side.

## Native Patches

- `react-native-health-connect` is declared as `^4.1.3`; the installed build is patched from the repo root via `patchedDependencies` in `pnpm-workspace.yaml`.
- Patch file: `../patches/react-native-health-connect@4.1.3.patch`, one hunk. `PermissionUtils.mapPermissionResult` maps `ExerciseRoute` and `BackgroundAccessPermission` back to JS but not `ReadHealthDataHistory`, even though `parsePermissions` accepts it on the request path. Since `requestPermission` also resolves through `mapPermissionResult`, a granted history permission can never be observed, so `ensureHistoryReadPermission` always returns false and Import Full History believes it is capped at 30 days. Reported upstream as matinzd/react-native-health-connect#276; drop the patch if that lands.
- The older 3.5.3 patch also forced `getTimeRangeFilterLocal` in `getAggregateGroupByPeriodRequest` (DST / local-day grouping) and made `ExerciseRouteResultType` string-valued. Both are gone: 4.1.3 uses the local filter at all 21 sites, and upstream is fixing the route enum in #274 by typing the read path as a string literal union instead — a better fix than ours, so `routeNeedsConsent` keeps accepting both forms and depends on neither declaration.
- `@bacons/apple-targets@4.0.7` is patched via `../patches/@bacons__apple-targets@4.0.7.patch`, fixing two upstream bugs. First, its xcode pass matched "its" extension target by type with a fall-back to any same-type target, which adopted and corrupted the expo-widgets `ExpoWidgetsTarget` on a clean prebuild; the patch scopes the match to an exact product-name hit. Second, the existing-target update path crashed every non-clean prebuild (EvanBacon/expo-apple-targets#201): removing the old build configuration list's referrers cleared `target.props.buildConfigurationList`, which the next line then dereferenced; the patch holds the list in a local and iterates a copy of its configurations so none are skipped mid-removal.
- `@bacons/apple-targets` is held on the 4.x line on purpose: it has a 5.x major, and moving to it invalidates the patch file. `expo install --fix` does not touch either patched package (neither is an Expo SDK package), so SDK upgrades leave both patches applying cleanly.
- `expo-health-connect` was removed. It only ever supplied an Expo config plugin, and upstream archived it: everything it did ships inside `react-native-health-connect` as of v4, which now writes both the `ACTION_SHOW_PERMISSIONS_RATIONALE` intent filter (Android 13 and below) and the `ViewPermissionUsageActivity` alias (Android 14+). Installing both causes Android build failures from duplicate classes.
- After changing a patch or upgrading a patched package, run `pnpm install` from the repo root and then `npx expo prebuild --clean` from mobile before native validation.

The phone module routes it as `onRunLive` (same four-place rename rule), `useWatchRunBridge` feeds `stores/watchRunLiveStore.ts` (in memory; ignores a message older than the one held, clears on `ended`, on `onRunFinished`, and after `WATCH_RUN_LIVE_MAX_AGE_MS` of silence through a 5 s sweep) and `useWatchRunLive()` moves the clock and step countdown on locally between messages while running. `ActiveWorkoutBar` shows it through `useWatchRunBarContent` (after a strength workout or a phone recording, which take the bar first; `useActiveWorkoutBarPadding` reserves room via `useHasWatchRunLive`) and a tap opens `WatchRunLiveScreen` (root-stack `WatchRunLive`, hidden-bar route): stats plus Pause/Resume, Lap, Finish and Discard that are sent to the watch (see the next bullet).
- Phone starts the watch (walk and run): when a watch is paired (`useWatchConnectivity`) and the activity is a walk or run, `RecordActivityScreen` asks Outdoor/Indoor first (`indoor`) and then shows **Record with** (`recordWith`: `phone` (default) or `watch`, labelled Phone GPS / Watch GPS outdoors and Phone / Watch indoors, each with its own hint); a ride is phone-only. Indoor + Phone is the step-counted phone session above, Indoor + Watch the watch's treadmill run. The Auto-pause and Voice cues switches (`components/recording/RecordingSwitchRow.tsx`) show for both devices and save the same preferences; auto-pause is hidden (and sent off) only for a phone indoor session, which gets no location fixes to judge by (the watch judges indoors by its step counter), and the voice picker is phone-only. With a watch choice Start calls `startRunOnWatch` (`services/watchRunControl.ts`, which sends the two switches as `autoPause`/`voiceCues` in `runStart`) instead of `startRecording`, then opens `WatchRunLive`. Messages (same four-place rename rule): `runStart` {requestId, kind, place, requestedAt (ms), optional plan from `buildWatchStartPlan`} is sent by the module's `startRun` with `transferUserInfo` (queued) plus `sendMessage` when reachable, then `launchWatchApp(activity:indoor:)` opens the watch app so the `HKWorkoutConfiguration` location type matches; `runControl` {runId, action pause|resume|lap|finish|discard, controlId} via `sendRunControl`, same transports. On the watch `WatchSessionManager.route` hands them to `WatchRunStore.startRequested` (dedupes by requestId, ignores a request older than 120 s or while `!canStart`) and `applyRemote` (dedupes by controlId, needs `runId == healthKit.runId`). The watch's `runLive` carries the `requestId` (nil for a run begun on the wrist), which settles the phone's pending request in `watchRunLiveStore` (`pending`, shown as "Starting on your watch…" for up to `WATCH_RUN_PENDING_MAX_AGE_MS`; the stale-run sweep leaves it alone). The run still files through `runFinished`, so a phone that goes away mid-run loses nothing; the wrist-only start (Cardio row) is unchanged. The watch Swift has not been compiled outside Xcode.
- Treadmill distance: a watch run recorded indoors has no route, so its distance is the watch's motion estimate. `watchRunSummary` sets `RunSummaryParams.editableDistance` (indoor and filed), and `RunSummaryScreen` then shows a "Treadmill distance" card: the person types what the machine showed (in their distance unit), `setExerciseEntryDistance` posts it to `POST /api/exercise-entries/:id/distance` (km), and the screen swaps the figure, the pace and the lap distances (scaled by the same factor, as the server does). When the run has a measured form with `steps`, the stride is worked out again from the corrected distance and written with `setExerciseEntryStrideLength` (`PUT /api/exercise-entries/:id` with only `stride_length_cm`, which the server merges without touching the rest; `null` clears a stride the new distance cannot support). No server change was needed for that; the `/distance` route still does not touch stride. Indoor distance learning: the watch's indoor figure is Apple's motion estimate, which the app cannot retrain, so it learns a correction factor instead, one per walk and run (`utils/indoorDistanceScale.ts` `learnScale`: the first correction is taken as is, later ones averaged geometrically over at most three, clamped to 0.5–2, an entry within 1% of what was shown teaches nothing). `services/watchIndoorScale.ts` stores it and `useWatchCheckInBridge` sends it as `indoorDistanceScale` (`{walk, run}`). The watch (`WatchRunStore.distanceScale`, set at start and on recovery from `IndoorDistanceScale.factor`) multiplies its live indoor distance and the finished run by it, and sends the factor as `distanceScale` in `runFinished` (the phone module's `normalizedRunEvent` passes it and `estimatedDistanceMeters` through; it forwards only listed keys). An indoor finish first asks "Treadmill distance?" on the wrist (`Phase.confirmingDistance`, `TreadmillDistanceView` with the strength keypad, or Keep watch distance); the run is held, its snapshot kept, until the answer, and an entered figure goes out as `distanceMeters` with the shown one as `estimatedDistanceMeters`. The phone learns from that pair in `watchRunQueue` once the run is filed, and from a correction on the Treadmill distance card (`RunSummaryParams.watchIndoor`, the factor applied and the distance shown before any correction). It is only reachable from the filed-run toast; there is no later edit screen.

- Nutrient metadata and defaults live in `constants/nutrients.ts`; aggregation and visibility toggling live in `utils/nutrientUtils.ts`.
- Measurements and water routes are in `measurementsApi.ts`; date-sensitive flows should preserve calendar-day strings and shared timezone helpers.

## Chat (Ask Sparky)

- `Chat` is a root-stack route (`src/screens/ChatScreen.tsx`), reached from `AddSheet`'s "Ask Sparky" row and an optional dashboard card gated by the `askSparkyVisible` preference.
- The thread is an assistant-ui runtime: `@assistant-ui/react-native` primitives plus `useChatRuntime` / `AssistantChatTransport` from `@assistant-ui/react-ai-sdk`, streaming from `POST /api/chat/stream` (AI SDK UI message stream protocol).
- The transport must use `expo/fetch` — it exposes a real `ReadableStream` body. RN's global fetch buffers responses and silently breaks incremental streaming.
- Auth and proxy headers are resolved per request through an async `headers` callback; `service_config_id` (the user's active AI provider) is merged into the request body and required by the server.
- `chatApi.ts` is history persistence only: `GET /api/chat/sparky-chat-history` and `POST /api/chat/clear-all-history`. `useChatHistory` seeds the runtime with prior messages and uses `staleTime`/`gcTime` of 0 because the runtime ignores `messages` changes after mount — every chat open must re-seed cold. `mapHistoryToInitialMessages` normalizes stored text and image parts into AI SDK `UIMessage` parts so historical user photos render in the thread without synthetic `[Image message]` placeholders.
- Photo attachments in `ChatScreen.tsx` use `pickChatImageFromCamera` / `pickChatImagesFromLibrary` (`utils/pickImage.ts`, downscaled to `CHAT_MAX_IMAGE_DIMENSION = 1024` and encoded as `0.8` JPEG base64 data URLs, up to `MAX_CHAT_ATTACHMENTS = 5` per turn) and add `CreateAttachment` entries via `aui.composer().addAttachment(...)`. The composer's `+` opens `ActionSheet` in icon-grid mode (camera/library); native pickers launch only after sheet dismissal finishes. The sheet dismisses the keyboard and consumes Android Back; leaving chat cancels a queued picker launch. Pending composer attachments and user message attachments open in a shared `ImageLightbox` (`useImageLightbox`).
- Chat UI lives in `components/chat/`: `MarkdownMessage` (`react-native-enriched-markdown` + `remend` to repair unclosed streamed markdown), `ToolCallCard` (derives running/complete/error from `result`/`isError`), `TypingIndicator`. Tool-name display mapping lives in `constants/chat.ts`.
- `ChatSettings` (`src/screens/ChatSettingsScreen.tsx`) is a root-stack settings route reached from Settings → Voice settings. `voice_input_enabled` and `active_voice_ai_service_id` are server-backed preferences shared with web, not local Zustand settings. Disabling voice hides the microphone without erasing the model. Null selects System; compatible Chat models are suggestions and AI always requires explicit selection. `useVoicePreferencesRefresh` refreshes choices on screen focus and foreground return.
- Voice dictation defaults to platform recognition in `ChatScreen.tsx`. `active_voice_ai_service_id` selects optional server transcription via `components/chat/AiVoiceDictationButton.tsx` and `services/api/voiceTranscriptionApi.ts`. `useVoiceInputLifecycle` cancels work on blur/background/unmount; temporary recordings are deleted, and the composer stays locked until processing finishes. `VoiceWaveform` uses a shared microphone level (no per-sample chat re-renders) and respects Reduce Motion. Sending always remains manual.
- There is no chat Zustand store; thread state lives in the assistant-ui runtime and history seeding in React Query.

Read it before visual or redesign work, and update its color tables in the same change whenever a token in `global.css` is added, renamed, or retuned.

- Many visual components read CSS variables with `useCSSVariable`, especially Skia charts and themed controls.
- Animate Skia paths from Reanimated `useSharedValue` / `useDerivedValue`, not Skia's deprecated animation API.
- `Icon.tsx` maps semantic names to SF Symbols on iOS and Ionicons on Android; verify identifiers before adding icons.
- Use shared primitives where they fit: `FormInput`, `Button`, `SettingsRow`, `SettingsRowGroup`, `SegmentedControl`, `StepperInput`, `BottomSheetPicker`, `CalendarSheet`, `DateRangeSheet`, `AnchoredMenu`, `FooterActionBar`, `FullScreenModalBody`, and `FormScreenChrome`.
- An action pinned below a list goes in `FooterActionBar`, never a hand-rolled `View` with flat bottom padding. A list's own `contentContainerStyle` inset does not reach a sibling pinned under it, so a flat padding leaves the action beneath Android's navigation bar; the component applies `Math.max(insets.bottom, 16)` in one place so the next screen cannot rediscover that. `FormScreenChrome`'s `FooterSaveBar` stays separate — it is the save-specific variant, with a top divider and the duplicate-press guard. A bar that only makes sense with a keyboard is the opposite case: it is never visible without one. Park it behind the keyboard with `KeyboardStickyView` `offset={{ closed: <its own height>, opened: 0 }}` (the sticky view translates by keyboard height plus that offset over keyboard progress, so at rest it sits just below the screen edge, off Android's navigation buttons and the docked rest bar, and rises from behind the keyboard's top edge), and never animate a layout property (height, padding, margins) from keyboard progress, which re-lays the screen out on every keyboard frame. The set surfaces' Done / Next / Log bar is `StickySetInputAccessoryBar` (`components/SetRowChrome.tsx`): screens render it unconditionally with `visible` (a set cell is focused) and an optional `restSlot` (the live screen's `ActiveWorkoutCompactRestRow` while a rest runs, left out below `MIN_WINDOW_HEIGHT_FOR_COMPACT_REST_ROW` (740 dp) of window height, where it would cover the set being edited); `useSetEditAccessoryBar` returns the same bar for the edit forms, and their `KeyboardAwareScrollView` `bottomOffset` adds `SET_ACCESSORY_BAR_HEIGHT` (plus `COMPACT_REST_ROW_HEIGHT` on the live screen while the bar carries the rest row).
- Never import `SafeAreaView` from `react-native`: it only applies insets on iOS and is a plain `View` on Android, where the app runs edge-to-edge, so a full-screen `Modal` built on it draws its header under the status bar and its actions under the navigation bar. Full-screen modal content goes in `FullScreenModalBody` (status-bar inset plus 16 on top, `Math.max(insets.bottom, 16)` below); anything else reads `useSafeAreaInsets()` from `react-native-safe-area-context`.
- `DateRangeSheet` takes optional `title` and `confirmLabel`; they default to the writeback removal wording, so a consumer that is not removing anything (the time-lapse) must pass its own. It also takes `markedDates`, like `CalendarSheet`: both dot their days through the shared `useMarkedDayComponent` (`components/calendarMarkedDays.tsx`), which inverts the dot on a selected day and on either end of a range, and supplies no `Day` override at all when there is nothing to mark so every other caller keeps the library's own cell.
- `BottomSheetPicker`, `CalendarSheet`, and sheets shown over native modals use `FullWindowOverlay` on iOS to avoid nested-provider inset bugs.
- `BottomSheetModal` does not handle Android's hardware Back, so the press falls through to navigation with the sheet still up: it pops the screen under the sheet, switches another tab to the Dashboard, or exits the app from the Dashboard. Only `ActionSheet` and `AddSheet` take it today, through `useSheetHardwareBack(isOpen, onBack)` from `components/ui/sheetChrome.tsx`, with `isOpen` set when the sheet opens and cleared in `onDismiss`; the other sheets (`BottomSheetPicker`, `CalendarSheet`, `DateRangeSheet`, `TimeSheet`, `CopyMealSheet`, the fasting sheets and the rest) still let Back fall through. Set `isOpen` from both `onAnimate` and `onChange`: when the open finishes before `onAnimate` reaches JS (Android's "Remove animations", or a busy JS thread), the library drops `onAnimate`, and `onChange` is the only signal that arrives.
- Keep button text and compact cards within their stable dimensions across mobile sizes. Avoid layout shifts from dynamic labels, loading states, or icon swaps.

## Widgets And Native Config

- iOS launches through the UIScene life cycle, which the iOS 27 SDK (Xcode 27) requires — a build that still creates its window in `AppDelegate` is killed at launch in `_UIApplicationEvaluateRuntimeIssueForNoSceneLifecycleAdoption`. The SDK 57 prebuild template predates this, so `plugins/withSceneLifecycle.ts` applies the SDK 58 template's changes: `AppDelegate` conforms to `ExpoReactNativeFactoryProvider` and stops starting React Native, a `SceneDelegate.swift` subclassing expo's `ExpoAppSceneDelegate` (needs `expo` >= 57.0.25) is added to the app target, and `Info.plist` gets `UIApplicationSceneManifest`. The plugin throws if `AppDelegate.swift` no longer matches the template; delete it when moving to SDK 58, whose template already does all three.
- iOS widgets live under `targets/widget/`, share data through the app group from `app.identifiers.js`, and reload through `ExtensionStorage` in `useWidgetSync`.
- Current iOS widgets are calorie, macro and water widgets; Android has the same three. When changing display, update Swift views, shared helpers, TS snapshot shape, and reload kind handling together.
- Widget string keys are derived from the Swift sources, not tracked by hand: `__tests__/config/helpers/widgetSwiftKeys.ts` discovers every `.swift` file under `targets/widget/` (recursively) and extracts the literal keys passed to `localizedWidgetString`, `configurationDisplayName` and `.description`. A new key must therefore be added to `targets/widget/en.lproj/Localizable.strings`, and — for `localizedWidgetString` keys — to the `fallbackWidgetString` map, or the contract tests fail. Target-language files stay optional and fall back to EN.
- Android widgets live under `targets/android-widget/`. `plugins/withCalorieWidget.ts` copies Kotlin/templates/resources, registers receivers, wires the native module package, and documents the pattern for adding another widget.
- Android widgets can be resized (#2050): every provider XML has `resizeMode="horizontal|vertical"` and no `maxResize*`; `minWidth`/`minHeight`/`targetCell*` are unchanged, so a new widget still lands at 2x1 (calorie) or 2x2 (macro, water), and `minResize*` is 110x40 dp for calorie and water (a one-row water widget is allowed) and 110x110 for macro. Each widget draws one layout per step in `WidgetSizes.kt` (`SizeMode.Responsive` picked through `LocalSize.current`, never `Exact`; from Android 12L the launcher picks among the layouts already sent and a resize needs no redraw, though the receiver still gets the resize broadcast, while Glance 1.1.1 redraws on Android 12 and below): the classic composition where it fits, and every other step keeps its content, adding to it or moving the shortcuts as described below. A step's height is about its content's height at font scale 1.3, worked out in `WidgetSizes.kt` (a line is about 1.33 x its sp, Glance keeps the font padding); a one-row widget on a phone's landscape home screen (about 51 dp) is shorter than any layout and cuts it; the reference cells are Pixel portrait 2 columns 130 dp / 1 row 102 dp and HyperOS 2 columns 149 dp, 3 columns 241 dp, 1 row 75 dp, 2 rows 167 dp, 3 rows 260 dp. For the calorie and macro widgets wide means at least 230 dp (3 columns on HyperOS, 4 on a Pixel). Calorie: below 96 dp tall (a HyperOS 2x1) search and scan sit beside the bar instead of being cut off; wide adds the Diary (`sparkyfitnessmobile://diary`) and fasting (`sparkyfitnessmobile://fasting`, the `FastingDetail` linking entry in `App.tsx`) shortcuts; wide and at least 160 dp tall, Goal / Food / Burned fill the flexible space, so a short widget cuts the figures rather than the shortcuts. Goal is food + remaining, worked out in Kotlin (the Dashboard's figure; the snapshot's `goal`, which the iOS medium widget shows as Goal, leaves out the exercise calories the dynamic and percentage modes add back), and the figures are hidden for a snapshot without `food`/`burned` (one stored by an older app) or without a goal. Macro: the 2x2 keeps the classic layout (a HyperOS 2x2 at 167 dp still cuts its shortcut row, accepted); wide, each row shows grams against the goal through `widget_amount_of_goal` inside `widget_grams` (so the translated unit stays) and the four shortcuts move to a column of 34 dp buttons on the right, which fits a two-row widget (the rows sit 5 dp apart so Fat still shows at font scale 1.3 on a HyperOS 3x2); wide and at least 255 dp tall, the shortcuts go back under the rows, the kcal eaten (`widget_kcal_eaten`, the snapshot's `calories`, which is `calorieBalance.eaten`) show under the kcal left, and the bars and spacing grow. In every macro row the label takes the width the value leaves, so a long label is cut and the grams stay whole. Water: the classic layout needs 140 dp of height (`WATER_CLASSIC_HEIGHT`; a HyperOS 2x2 is 167 dp); narrow and shorter, as a one-row widget or a Pixel's landscape 2x2 is, the amount sits over the bar and smaller buttons, with a status under the amount from 98 dp tall (a Pixel's one-row widget is 102 dp) and in its place on a shorter row (a HyperOS 2x1, 75 dp); at least 300 dp wide (`WATER_WIDE`, 4 columns on HyperOS), the amount and bar sit on the left and − / + on the right, with the title and status line from 140 dp tall, the status in place of the bar below that. Narrower widgets keep the stacked layouts, because beside the buttons an amount such as "1,250 / 2,800 ml" is cut at 3 HyperOS columns (241 dp) and at a Pixel's 4 (276 dp). Glance drops a container's children past the tenth (the macro and water columns already have nine), so new elements join an existing row or column. Kotlin is not compiled by CI: compile the widget sources locally against Glance 1.1.1 before pushing.
- `src/services/CalorieWidgetBridge.ts` is the JS bridge for Android widget snapshot writes, Glance reloads and the clear on an account change.
- The scheduled "Rest complete" alert fires exactly only with the `SCHEDULE_EXACT_ALARM` special access ("Alarms & reminders", user-granted, denied by default on Android 13+) — without it expo-notifications falls back to inexact alarms the OS batches ~15s late. The `targets/android-exact-alarm/` Kotlin module (registered by `plugins/withExactAlarmModule.ts`) exposes `canScheduleExactAlarms`/`openExactAlarmSettings` through `src/services/ExactAlarmBridge.ts`; `maybePromptForExactAlarmPermission` in `notifications.ts` owns the one-time grant prompt at workout start.
- Widget snapshot shapes: the calorie snapshot (`food`, `burned`, `goal`, `remaining`, `progress`, all from `calorieBalance`) is built once by `buildCalorieWidgetSnapshot` (`src/services/calorieWidgetSnapshot.ts`) for iOS and Android; the other iOS snapshots are built in `useWidgetSync.ts`, and the Android macro and water contracts live in `src/services/androidWidgetSyncService.ts`. Keep them aligned with the Swift views and Kotlin `parseSnapshot`/`WaterWidgetStore`.
- The workout Live Activity (Lock Screen + Dynamic Island elapsed/rest timers) uses `expo-widgets`, whose generated `ExpoWidgetsTarget` extension coexists with the `@bacons/apple-targets` `targets/widget/` target. `src/services/WorkoutLiveActivityLayout.tsx` is the `'widget'`-directive layout (self-contained; only `@expo/ui/swift-ui` imports; epoch-ms props, never `Date`s) and must only be imported from `src/services/workoutLiveActivity.ios.ts` — `createLiveActivity` runs at module scope and would drag iOS native modules into the Android bundle. The `.ios.ts` service subscribes to `activeWorkoutStore` (ops held until persist hydration + instance reconcile) and serializes all start/update/end calls; the OS ticks the timers from absolute timestamps, no polling — the app pushes an update only on a real state change. The Lock Screen banner shows a small header (app icon, workout name, elapsed), the exercise as headline with "Set 1 of 3" (or "Next: Set 2 of 3 (65 lbs × 12 reps)" while resting), then either the set's target in the user's unit with a check button, or the rest row of "-15s", a large countdown, "+15s" and "Skip". Those two subtitle lines are formatted in the service from the `setProgress`, `nextSet`, and `nextSetWithTarget` templates and passed as `subtitleText`; the widget body only displays that string. The target comes from `describeActiveSetAssumed`, so an empty set shows the same grayed-in values the live row does. The rest "-15s"/"+15s"/"Skip" and active-phase "Complete" buttons (iOS 17+; inert below 17) fire a `LiveActivityIntent` that runs in the app process and lands in the service via `addUserInteractionListener`, which dispatches to store actions; the button `target` strings are duplicated by hand between layout and service because the `'widget'` body cannot import them. A press after a force-quit is lost (the event fires before JS boots). The rest progress bar is an OS-ticked `ProgressView timerInterval`; the `bannerSmall` slot targets the watchOS Smart Stack/CarPlay and stays button-free. Live Activities get NO `widgets[]` entry in `app.config.ts` (that array is only for home/Lock Screen widgets).
- The run Live Activity (`RunLiveActivity`, a second type beside the workout one) shows a phone GPS recording or a watch run (`watchRunLiveStore`) on the Lock Screen and Dynamic Island. Same rules as the workout one: `src/services/RunLiveActivityLayout.tsx` is the self-contained `'widget'` layout, imported only from `runLiveActivity.ios.ts` (`runLiveActivity.ts` is the Android no-op). The phone recording wins over a watch run; a watch run that has been quiet for `WATCH_RUN_LIVE_MAX_AGE_MS` ends the activity. The clock is OS-ticked from `now - activeSeconds*1000`; the app pushes at most every 5 s (`MIN_REPAINT_MS`) with a trailing repaint, never polling. Buttons (`run-toggle`, `run-lap`) call the recording service or `sendRunControl`; the activity opens `sparkyfitnessmobile://record-activity` (linking entry in `App.tsx`). Labels are translated by the caller via `configureRunLiveActivity({ t, distanceUnit })` from `WatchWorkoutGate` in `App.tsx`; the layout never calls `t`.
- Android uses `src/services/workoutLiveActivity.android.ts` to mirror the active workout as an ongoing notification. `plugins/withWorkoutNotification.ts` copies the Kotlin module from `targets/android-workout-notification/` at prebuild. On Android 16+, the system ProgressStyle shows exercise segments and requests a Live Update status chip with the next set position (for example, `3/16`); older Android versions use a standard ongoing notification with overall set progress. Native notifications are reconciled after workout-store hydration; rest-complete alerts remain separate.
- `app.config.ts` controls bundle identifiers, Apple team IDs, iOS app group, Android permissions, navigation bar contrast, widget plugins, and production-only network security config.
- iOS entitlements in `app.config.ts` are the app group plus `com.apple.developer.usernotifications.time-sensitive`. The latter is what lets the `timeSensitive` rest-complete alert break through Focus modes and the Scheduled Summary; it is an App ID capability, so credentials have to be re-synced (profile regenerated) on the first build that carries it.
- `APP_VARIANT` selects dev vs production behavior; dev builds request extra Android Health Connect write permissions for local testing/seeding.
- After editing `targets/`, native config plugins, app groups, permissions, or native bridge shape, run `npx expo prebuild --clean`.

## Apple Watch

- The watchOS companion app lives entirely under `targets/watch/` (a `@bacons/apple-targets` `type: 'watch'` extension, `expo-target.config.js`), iOS-only (Wear OS has its own app, see the Wear OS section below). Layers: `Presentation/` (SwiftUI views, `ContentView`'s `TabView` — one tab per `WatchPage` the phone's layout shows, in its order), `Application/` (`CheckInStore`, `WorkoutSessionStore` — `@MainActor ObservableObject` singletons, injected in `SparkyFitnessWatchApp.swift`), `Infrastructure/` (`WatchSessionManager` wrapping `WCSession`; `WorkoutHealthKitController` wrapping `HKWorkoutSession`/`HKLiveWorkoutBuilder`), `Adapters/` (`OutboundPayloads` builds outgoing `[String: Any]` dictionaries, `ContextPayloadMapper` parses incoming ones — the only two files that know wire key names), `Domain/` (plain `Codable` models).
- Look and touch targets on the watch: follow Apple's watchOS guidelines. Text uses system text styles (`.headline`, `.body`, `.footnote`; nothing smaller than footnote, no fixed 9–12 pt sizes) so it follows the wearer's text size; large numerals use `WatchStyle.s(_:)` sizes in the rounded design. One main action per screen, names wrap to two lines instead of truncating, and a screen shows only what its job needs. On the workout screens there is one control shape, `SquircleButton` in `WorkoutView.swift` (flat dark squircle from `WatchStyle`, 44 pt tall in a row at the 44 mm reference size, dimmed when disabled, the whole box tappable; `prominent` is the white main action). The set screen is the exercise's name (`ExerciseTitle`, up to two lines, or one line over "Superset · partner" in the superset's colour; tapping it opens the exercise list, so there is no separate list button), `SetProgressRow` ("Set 2 of 3" or "Warm-up 1 of 3" in orange, and one dot per set of the exercise: filled once logged, ringed for the current one; tapping a dot moves to that set through `WorkoutSessionStore.goToStep(setId:)`), the value cards (`ValueBox`, same fill, bold rounded numerals, a white border while selected) and the bottom row: previous set, a wide `DoneButton` (Done in white, Undo in orange once logged) and next set, the arrows crossing into the neighbouring exercise as the dots do not. Elapsed time, heart rate and calories are on the set screen by default, as one line in the clock's row (`SetScreenMetricsLine`); with Settings → Apple Watch → "Metrics on the set screen" off they move to `WorkoutMetricsPage`, the first page after the set screen, or the second when Up Next is on (always before Set options), one large reading per line as in Apple's Workout app, and that page exists only then. With the metrics line off, the heart rate is also inside the rest ring (with it on, the line already shows it). With the "Up Next page" setting on (off by default), the first swipe up is `UpNextPage`: the next exercise's name, one dot per set, its first target, and the exercise after it; a tap opens the exercise list. Under it, Swap (and Swap Exercise on the exercise options page) opens `SwapExerciseSheet`, the exercises still to come; picking one sends the `doExerciseNow` workout edit, which the phone applies with `activeWorkoutStore.doExerciseNow` (the picked exercise moves in front of the current one and becomes active), and the watch jumps to it at once. Both are shown only while the phone's context says `exerciseDoNow`, since an older phone ignores the edit. The rest screen is a countdown ring (time left and heart rate inside it) over back 15 s, skip and forward 15 s, then one "up next" line that opens the exercise list. The exercise list sheet is a `NavigationStack` titled with the workout name over flat squircle rows: name on up to two lines and sets logged over sets planned on the right, green once the exercise is done. Every size on these screens goes through `WatchStyle.s(_:)`, which scales it by the watch's screen height (0.82x to 1.1x of a 44 mm), so a 40 mm watch is not squeezed off its screen. These three settings reach the watch as `setScreenMetrics`, `upNextPage` and `largerText` in the context (absent means today's behaviour: metrics on, no Up Next, original Goals and Water). Goals and Water keep their original layout (`ClassicGoalSummaryView`, `ClassicWaterIntakeView`) unless "Larger text on the watch" is on (`largerText` in the context; `ContentView` picks the view and sets the `watchLargeText` environment value). - Following a saved route on the watch (outdoor walk or run only; the watch's ride is the phone-GPS recording, which has no route support): `startRunOnWatch({ ..., route })` (`services/watchRunControl.ts`) takes a route from the library (`Route` from `@workspace/shared`, at most 2000 points) and sends `toWatchRoutePayload(route)` (`utils/watchRoute.ts`) as the `route` of the `runStart` request, dropped for an indoor start. It fits because the points are one flat integer array in millionths of a degree (`[lat, lon, …]`, ~5 bytes a number, ~20 KB at 2000 points) with no altitude; a route over the cap is re-thinned with `simplifyRoute` and its cues re-pointed. A route with no cues gets derived ones (`deriveRouteCues`: a heading change of 30 degrees or more measured over ~25 m either side, merged within 30 m, sized slight/normal/sharp/U-turn) so the watch always has directions; the library's own `text` wins over the watch's wording. On the watch `ContextPayloadMapper.route(from:)` reads it into `WatchRunStartRequest.route`, `WatchRunStore.start` keeps it as `route` (saved by `WatchRouteStorage` so a relaunch resumes following, cleared when the run ends), and each GPS fix (`WatchRunHealthKitController.onLocation`) goes to `WatchRouteTracker` (`Domain/WatchRoute.swift`, pure Swift: nearest point on the polyline searched near the last position first so a loop is followed on the right lap, progress, metres left, next cue; off-route is more than 40 m from the line for 6 s, cleared at once on return, fixes worse than 50 m ignored; a buzz 50 m before each turn, `Haptics.routeCue`/`offRoute`/`onRoute`, and spoken lines when voice cues are on). `WatchRunView` shows `RouteCueStrip` under the clock and, with a route, a second and third vertical page: `WatchRouteMapPage` (Apple Maps via MapKit's `Map`, close around the wearer and turned heading up, the covered part grey, the rest cyan, the next turn as a marker) and `WatchRouteOverviewPage` (the whole route, north up). The tiles are MapKit's own: the watch asks Apple Maps for tiles for the area on screen and nothing else; there is no tile server URL in the app, and the route and position are never sent anywhere (they are overlays drawn on the watch, so with no signal the tiles stay blank and the route still shows). `WatchRouteCamera` (`Domain/`, pure, tested in `watch-tests/` with the tracker) picks the camera: centred on the wearer, heading from the route 40 m ahead (north up when off the route, arrived or with no fix), pulled back from 450 m to at most 1000 m so the next turn stays in the top half, and `isWorthMoving` drops a new camera unless it moved 8 m, turned 10 degrees or zoomed 50 m, so a 1 Hz fix does not restart a MapKit animation each second. `WatchRunView` gives each page a selection tag and the maps are built only while their page is selected and the screen is not dimmed (a vertical-page `TabView` keeps its neighbours alive); points of interest and the compass badge are off. No extra GPS: the position is the run's own. The tracker's tests are XCTest in `watch-tests/` (a SwiftPM package symlinking `WatchRoute.swift`; run `swift test` there on a Mac) because the watch target has no test target and everything under `targets/watch/` is compiled into the app. The TypeScript half is tested in `__tests__/utils/watchRoute.test.ts` and `__tests__/services/watchRunControl.test.ts`.
- Routes kept on the watch (iOS only): `RouteDetailScreen` (shown only while `useWatchConnectivity().isPaired`) has **Start on watch** (Run or Walk, `startRunOnWatch` with the route) and **Send to watch** / **Remove from watch**. `services/watchRouteSync.ts` sends `routeSync` (`buildRouteSync`: the `toWatchRoutePayload` route plus `updatedAt` in epoch ms as its revision) and `routeRemove` through `WatchConnectivity.sendRoute` / `removeRoute`, both queued `transferUserInfo`; `removeRoute` in `routeService.ts` also drops the watch copy, best effort. The watch holds at most `WatchRouteLibrary.capacity` (10) routes in `watch-route-library.json` (`WatchRouteLibraryStorage`), refuses a new route when full instead of evicting one, ignores a copy not newer than the stored revision, and holds a removal for the route being followed until the run ends. After every change and on session activation it answers with `routeLibrary` (stored ids and revisions, rejected ids with `full`/`storage`, capacity), which `useWatchRouteBridge` feeds to `stores/watchRouteStore.ts` (persisted device-local record, never synced to the server); `watchRouteStatus` (`utils/watchRouteSync.ts`) turns the record into `none`/`pending`/`onWatch`/`outdated`/`full`, and an edited route is never re-sent on its own. The wrist lists them under **Routes** in the Cardio sheet (`CardioChoicesView`), outdoor only. The Record screen offers a route picker only for an outdoor watch run. Renaming `routeSync`, `routeRemove` or `routeLibrary` means updating `ContextPayloadMapper`/`OutboundPayloads` and `WatchSessionManager.route`.

- Workout effort (1-10, `exercise_entries.workout_effort`): when a strength workout or a wrist-only run ends on the watch, the summary offers `WorkoutEffortPicker` ("How hard was that?"): the set screen's `ValueBox` card starting at 5, with Apple Health's band (Easy 1-3, Moderate 4-6, Hard 7-8, All Out 9-10) as the line under the number. As on the set screen the card must be tapped before the crown adjusts it (`.focusable(selected)`; until then the crown scrolls the page), and tapping it again hands the crown back. The rating goes three places. (1) Apple Health, as `workoutEffortScore` related to the saved `HKWorkout` through `WorkoutEffort` (`Infrastructure/WorkoutEffort.swift`, watchOS 11+; older watches skip the Health write and the type is only requested for write access on 11+); `WorkoutHealthKitController` and `WatchRunHealthKitController` keep the `HKWorkout` that `finishWorkout` returned for it. (2) The phone, as a queued message (same four-place rename rule): `runEffort` `{clientId, rating}` for a run and `workoutEffort` `{sessionId, rating}` for a strength workout (`OutboundPayloads`, `WatchSessionManager.sendRunEffort` / `rateWorkoutEffort`; module events `onRunEffort` / `onWorkoutEffort`). (3) The server, by the phone calling `setExerciseEntryEffort` (`POST /api/exercise-entries/:id/effort`, which also rates the other entries of a strength session). A run is handled in `services/watchRunQueue.ts`: it keeps `{rating, entryId, program}` per run under `@SparkyFitness/watchRunEffort` (the entry once the run is filed, the program once it is ticked off), so a rating that arrives before the run is filed waits, and it also rates the program workout (`rateProgramWorkout`, in place of the Diary's `RunEffortPrompt`, which stays as the fallback). A strength rating is handled in `useWatchWorkoutBridge` (`settleEfforts`): it waits in memory until the phone has ended the session and then uses any entry id the session's telemetry or attribution knows; an app that is not running when it arrives loses it (nothing stores it natively, unlike `runFinished`). Apple's own rating is read on sync by `services/healthkit/workoutEffort.ts`: `filter: { workout }` cannot see it (it matches samples saved with the workout, and a rating is related afterwards), so `handleWorkout` reads the `WorkoutEffortScore` samples for the whole window in one query and `matchWorkoutEffort` pairs them to workouts by start and end (5 s tolerance, newest wins), setting `telemetry.workout_effort`; Apple's automatic estimate is never read. The type is in `WORKOUT_TELEMETRY_READ_IDENTIFIERS` (iOS asks for an enabled type it never asked about without the Android permission version; the library skips an identifier the OS does not know, so iOS 17 and older just never see it). Shown by `summarizeWorkoutEffort` on `WorkoutDetailScreen`, and as `workout_effort` / `workoutEffort` on `ActivityDetailScreen` and `CardioSessionScreen`. Phone-only cardio has no `HKWorkout`, so it has no Apple rating and keeps the run summary's program rating row. The watch Swift has not been compiled outside Xcode.

## Localization And Reactive Helpers

- React UI gets `t` from `useTranslation()`; user-facing utility helpers accept an injected `TFunction` and never hide singleton `i18n.t()` fallbacks.
- Pass `t` through every presentation helper and include it in `useMemo` / `useCallback` dependencies when the derived result contains localized text; this keeps mounted UI correct after a runtime language switch.
- Translation keys are semantic and statically analyzable. Every static `defaultValue` is the English source fallback and must exactly match the EN catalog entry.
- A key used with `count` is a plural family: EN requires `_one` and `_other`; PL requires `_one`, `_few`, `_many`, and `_other`. Use grammatically correct forms rather than duplicating suffixes blindly.
- Apple Watch Swift text (`targets/watch`, `targets/watch-widget`) must use `String(localized: "watch.<key>", defaultValue: ...)` with the key in that target's `en.lproj/Localizable.strings` (each target is its own bundle; `%@`/`%lld` for interpolations, and a static `defaultValue` must match the English entry). `pnpm run i18n:audit:watch` (tested by `__tests__/scripts/watchI18nAudit.test.ts`) fails on bare `Text("...")`/`Button("...")`/`Label("...")`-style literals, missing catalog keys, and mismatched defaults; add `// i18n-ignore` for literals that must stay.
- Run `pnpm run i18n:audit` after localization work. `pnpm run validate` includes typecheck, lint with zero warnings, and this audit.
- Keep canonical storage/API values and user-generated content literal; localize only application-owned presentation labels.

## Priority Rule

- For work inside `SparkyFitnessMobile/`, this file is the package guide.
- If a task also changes another package, combine this with that package guide instead of stretching this file to cover the whole monorepo.
- Timed sets without a planned length (#99): the start payload marks every set of a duration exercise `timed: true`. With a `targetDurationSec` the watch counts down (`HoldCountdown`); with none it shows a stopwatch (`HoldStopwatch`, `WorkoutSessionStore.startStopwatch`) that starts on tap, freezes when the set is ticked and logs the elapsed seconds.
- Timer sync for timed sets: both sides share one start time (epoch ms). The phone's newest running `setTimerStartedAt` is sent in every `setTargets` update as `setTimers` (one entry at most, for a set not yet logged, because the wrist holds one timer); the watch (`WorkoutSessionStore.applyPhoneTimers`) starts its countdown or stopwatch from that time, never replacing one it started itself, and stops a copied one if the phone drops it without logging the set. A timer started on the wrist is sent as `setTimerStarted` (`onSetTimerStarted` → `applyWatchSetTimerStart`, ignored for another session, a logged set or a start over 3h old) and starts the phone's stopwatch from the same time; a countdown that already ran out does not buzz. A set logged on the wrist clears the phone's stopwatch after its reported duration is written. Last session's time for a timed set rides along as `previousDurationSec` (in the plan and in every `setTargets` update) and the idle watch stopwatch shows it in gray as "Last m:ss"; it is never a target. A timer started on the wrist is kept until it is logged even when the phone times a different set; logging another set leaves a synchronized timer for a different set running; the running timer is stored in the workout snapshot so a relaunch resumes it; a `setTargets` update that arrives before its plan keeps its `setTimers`; and `setTimerStarted` carries `armedAt` so the phone ignores a queued start from an earlier arm of the same session.

- Timed-set sync both ways: the wrist's Stop button sends `setTimerStopped` (`seconds` and that run's `startedAt`); the phone drops its stopwatch and writes the seconds only when `startedAt` is the timer it has (`applyWatchSetTimerStop`), so a stop queued across a later run is ignored. Start and stop ignores are logged to the app log. Only a duration typed on the phone makes the watch count down; the gray "last time" value never does, so a timed set starts at 0 like the phone.
- Watch RPE (#87): Settings → Apple Watch → "Ask for effort (RPE) after each set" (`watchRpeEnabled`, default off) rides the watch context as `rpeEnabled`. When on, logging a set on the watch holds it behind an effort screen laid out like Hevy's: the exercise and set (`Set 1/3: 65.0lbs × 12`) over one large value box that the Digital Crown changes through 1 to 6 in whole numbers, then 6.5, 7, 7.5, 8, 8.5, 9, 9.5 and 10, an "RPE" label, a line saying how many more reps were left in the tank for that value, and Skip and Save buttons. Those labels and descriptions use `watch.rpe.*` keys in `targets/watch/en.lproj/Localizable.strings`, with the English text as the `defaultValue`. The crown stays quiet when the phone's haptics switch is off. Save sends `rpe` with `setCompleted`; Skip sends the set without one. The screen is an overlay on the workout page and not a sheet, because a sheet's system close button covered the exercise name on a 40 mm watch; the set waits there until Save or Skip. The held completion (set, logged values, the tick time, a timed set's seconds at that tick, and the Save or Skip choice) is written into the workout snapshot in `completeCurrentSet(holdForEffort:)` and cleared only after an activated Watch Connectivity session accepts the send. A choice made before activation is kept and sent when the session activates, including after a relaunch. The phone writes `rpe` through `updateSetField` only when it is within 1–10. The overlay state lives in `ActiveWorkoutView`, not `CurrentSetView`, because logging a set starts the rest and swaps the set view out.
- Exercise History layout: `ExerciseHistoryList` shows one card per session — the workout's name (or the date for a single entry) with the date and start time beneath, and a chevron that opens the workout when `ExerciseDetailScreen` passes `onOpenSession` — over a table of SET, a value column headed for the exercise's modality, RPE and a record marker. Working sets are numbered among themselves; warm-up, drop and failure sets show W, D and F (`setTypeLetter`). A set's RPE is a pill in the effort tones, a record is a filled trophy and a tie of the best set an outlined one.
- Effort (RPE) in the app: the exercise History tab opens with `ExerciseEffortCard` (built by `buildExerciseEffortSummary` in `utils/exerciseEffort.ts` from the loaded history sessions): the last session's average RPE, bars for up to the last ten, and for plain weight × reps exercises the best estimated 1RM with and without counting reps left (`effortAdjustedOneRepMaxKg` in `@workspace/shared`: reps + (10 − RPE) for an RPE of 6 to 10, otherwise plain Epley). Warm-ups never count. Personal records and best sets still use reps alone. In adaptive coaching (`decideAdaptiveAdjustment`) a logged average RPE of 7 or lower, or 3+ reps in reserve, with no difficulty answer adds one step (`low_effort`), the mirror of the existing hold at RPE 9.5+.
