# Dashboard, Diary, Measurements, And Nutrients: details

Longer notes for the "Dashboard, Diary, Measurements, And Nutrients" section of [`SparkyFitnessMobile/AGENTS.md`](../AGENTS.md). Each one has a one-line link there.

## Quick Settings tiles (Android)

- Quick Settings tiles (Android, the counterpart of the iOS Control Center controls in `targets/widget/Controls.swift`): Log water, Scan barcode, Search food and Calories left, declared by `plugins/withQuickSettingsTiles.ts` and written in `targets/android-widget/kotlin/com/sparkyapps/sparkyfitness/widget/QuickSettingsTiles.kt.tmpl`. They sit with the widgets because they share their strings (`widget_strings.xml`, plus `tile_log_water` and `tile_calories_left`), icons, `WidgetLocale` language handling and the calorie snapshot (`CalorieWidget.loadSnapshot`), and each is redrawn when the panel opens. Log water runs `enqueueLogWater` from the background-water code, so it logs without opening the app, lock screen included, and is unavailable while no login is stored. It is a button, never left on (pinned by `__tests__/config/withQuickSettingsTiles.test.ts`). A Toast would be drawn under the open panel and hidden by the lock screen, and some panels (HyperOS) do not show a tile's subtitle, so `enqueueLogWater(context, fromTile = true)` puts the result in the notification list instead: the `quick-logging` channel, IMPORTANCE_DEFAULT with no sound, vibration or heads-up, since it only confirms a tap. HyperOS still shows it as a banner while the app's floating notifications are on. A lock screen that hides sensitive content shows a logged drink's public version, "Water logged", without the container name; a failure, which never names it, stays public and readable. A logged drink clears after 30 seconds, a failure stays until a drink is logged (from the tile or the shortcut) or the tile fails again, and tapping either opens the app. With the app's notifications off it falls back to the Toast, which Android drops unless the app is on screen, so the tile then gives no feedback. The others open `sparkyfitnessmobile://scan`, `://search` and `://diary` (the `Diary` path in `App.tsx`'s linking config), asking to unlock first; `plugins/withQuickActionLaunchGuard.ts` drops such a link, like a shortcut's action, from a `MainActivity` Android restores after killing the app, so the screen does not open again by itself. Calories left puts "N kcal left" in its label, like the iOS control, rounded by the calorie widget's own `formatInt`, and only while a login is stored, since the panel opens on the lock screen. The snapshots carry no account, so the `useAuth` identity-change handler erases every widget's snapshot (`clearAndroidWidgetSnapshots`, the native `clearSnapshots`) in the same turn as the query cache; snapshot writes and the clear share one serial executor and one lock, so they run whole in the order JS sent them; the clear tries each widget's stored copy and every instance's state, carrying on past a failure, and rejects with the first cause (logged by the handler, never blocking the sign-in) if any part kept or still shows the old snapshot; a background refresh started for the previous account does not push (`widgetGeneration`), and `useWidgetSync` keys its Android dedupe on that generation so the same figures are pushed again after a re-sign-in. The Glance widgets read the stored copy at composition, so a live session does not bring a cleared snapshot back. iOS does not clear its app-group snapshots yet. The user adds the tiles from the panel's edit view; the app does not prompt for it.

## Siri and Shortcuts actions

- Siri and Shortcuts actions that log without opening the app (no setting; always available while a server is signed in): `useBackgroundWaterSync` (mounted in `DashboardScreen` with the active container) calls `syncBackgroundWater`, which hands `modules/background-water` a JSON copy of the server address, auth/proxy headers, weight unit and, when there is one, the dashboard container. `clearBackgroundWater` erases it when the active server is removed, and a signed-out app holds no copy. Syncs and clears run one at a time. iOS stores it in the Keychain; `targets/widget/ShortcutIntents.swift` holds the App Intents (compiled into the widget extension and copied into the app target by `plugins/withBackgroundWater.ts`; the app-only `plugins/ios/ShortcutProvider.swift` has the `AppShortcutsProvider`) (`openAppWhenRun = false`) — Log water (drinks), Log weight (converted to kg), Start fast (hours) and End fast (reads `/api/fasting/current`) — — so the iOS 18 Lock Screen / Control Center buttons in `targets/widget/Controls.swift` (Log water, Start fast, End fast) run the same code; Scan food and Log food controls run `ScanFoodControlIntent` / `LogFoodControlIntent` (`openAppWhenRun`, no parameters, compiled into the app target too), which leave `scan` or `search` under `pendingControlRoute` in the shared app group; `useControlRouteHandoff` reads it when the app opens or returns to the front and navigates. A control cannot be relied on to open a custom URL scheme (Apple's guidance is universal links only), which is why they do not use `OpenURLIntent`. The app and the widget extension read the copy through a shared Keychain group (`SparkyKeychainGroup` in both Info.plists, `keychain-access-groups` in both entitlements); a build without it falls back to the app-only item. The calorie widget also has Lock Screen families (circular ring, rectangular card, inline text) reading the same `calorieSnapshot`, and the macro widget has Lock Screen families too (circular share ring with calories, rectangular protein/carbs/fat rows, inline grams), separated by opacity because the Lock Screen draws one tint. Android stores it AES-GCM-encrypted with an Android Keystore key (`targets/android-background-water`), publishes the dynamic "Log water" launcher shortcut (no-UI `LogWaterActivity` enqueues a WorkManager job; it has an empty `taskAffinity`, so a tap never brings the app's own task to the front), and toasts the result. Android drops a Toast from an app in the background while the app's notifications are off (on Android 13+ until `POST_NOTIFICATIONS` is granted, which the app asks for only from its notification features), and the result arrives after the no-UI activity has finished, so it only shows while they are on. HyperOS also drops it while the app's floating notifications are off (seen on a Xiaomi phone), so there the shortcut logs the drink without any message; the app can neither read nor change that setting. The shortcut's labels come from the app through `refreshShortcut` and are kept in plain shared preferences (English until the app first sets them); the result messages, and the tile's `Quick logging` notification channel, are English-only. A new action must read the server path from `src/services/api` so the two stay in step.

## Android water widget

- Android water widget (upstream #1815; `WaterWidget.kt.tmpl`, `WaterWidgetReceiver.kt.tmpl`, `WaterWidgetStore.kt`, `WaterWidgetActions.kt` in `targets/android-widget`): a 2x2 by default that can be resized (see the resizing bullet under Widgets And Native Config), with today's water against the goal, a bar, and `−` / `+` buttons that remove or add one drink of the dashboard container without opening the app. `useWidgetSync(summary, water)` pushes a `waterSnapshot` (`consumedMl`, `goalMl`, `manualMl`, `drinkMl`, `unit`, `canLog`) from the Dashboard; a background refresh sends only the totals and `manualMl`, and the native side keeps the rest (`mergeFromAppLocked`). `manualMl` is the daily summary's `waterIntakeBreakdown.manual_ml` (`DailySummary.waterManual`, null on a server without the breakdown) and is never carried over from an earlier push. The Dashboard leaves `drinkMl` out until a container has loaded (`servingVolume` is undefined until then), so the widget keeps its buttons meanwhile. The native side ignores a push for any day but the device's (the background refresh builds the account timezone's day); when the day changes it keeps the taps not yet sent, which go out stamped with the day they are sent, and forgets the request still out, whose answer is then dropped. The buttons show only once the Dashboard has sent the container (`canLog`, false until then, as on iOS) and it has a drink size (one linked to a food has none); `−` is greyed out at zero and when none of the day's water was logged by hand (`manualMl`), since the server removes only drinks logged that way; a greyed-out `−` sends a change of 0, so a tap on it does nothing instead of opening the app, and it is announced as "No drink logged here to remove". A tap (`WaterChangeAction`, a Glance `ActionCallback`) adds to the snapshot's pending drinks and shows at once, or redraws the widget when the snapshot no longer allows it (yesterday's figures before the midnight refresh); `WaterWidgetWorker` (unique WorkManager work, `APPEND_OR_REPLACE`, expedited on Android 12+) sends them in one `POST /api/measurements/water-intake` through the background-water `postWaterChange`, so they share the shortcut's stored login, and the server's total replaces the guess. A worker starts by forgetting taps an earlier one took and never answered (stopped, or its process died): they are not sent again, since the request may have landed, and the next push brings the real total. A failed request (sign in, pick a container, login expired, server unreachable, could not log) drops the waiting taps and shows a status line until the next tap or app push; a `−` the server could not honour keeps the total and shows "No drink logged here to remove", judged from the total before and after, as on iOS. A drink logged by the shortcut or tile reaches the widget through an explicit `ACTION_WATER_TOTALS` broadcast to its receiver, carrying the widget's account epoch read before the request. Every change to the water snapshot, the app's pushes and the clear on an account change run under `WidgetSnapshotLock`; the clear also moves the account epoch on and cancels the queued work, so a late answer or shortcut total for the previous account is dropped. Below Android 12, where Glance cannot round a view, the buttons' shape is the `bg_widget_water_button` drawable (light and night) and their press ripple `bg_widget_water_button_ripple`.
