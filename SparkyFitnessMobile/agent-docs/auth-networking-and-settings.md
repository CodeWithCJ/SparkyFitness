# Auth, Networking, And Settings: details

Longer notes for the "Auth, Networking, And Settings" section of [`SparkyFitnessMobile/AGENTS.md`](../AGENTS.md). Each one has a one-line link there.

## Features (optional features)

- Settings → Features (#3487) is `FeatureSettingsScreen` (root-stack `FeatureSettings`, a Settings row shown while connected). It lists the shared registry's keys (`OPTIONAL_FEATURES` in `@workspace/shared`) by group, one set of rows per key (`FeatureRows` must cover each). Every entry point in the app asks `useMobileFeatures().isEnabled(key)` (`hooks/useMobileFeatures.ts`, the shared `isFeatureEnabled` for `mobile`), never the stored value: the + sheet through `ADD_MENU_ITEM_FEATURES` (`constants/addMenuItems.ts`) and `useAddMenuItemAvailable`, the Dashboard through `DASHBOARD_CARD_FEATURES` (`constants/dashboardCards.ts`), both with the shared `isShownByFeature`, and `CycleCard` itself. Dashboard Settings and Quick Actions leave out an item of a feature that is off, as the Dashboard and the sheet do, and show one "Some features are turned off · Manage" line (`components/FeaturesOffNotice.tsx`; Manage opens `FeatureSettings`, only while connected, as the Settings row to it is). A tile holding such an item shows empty and the tile picker does not offer it. The stored arrangement is never rewritten because of a feature: a drag in the shortened list is merged back into the full order with `mergeSubsetOrder` (`utils/reorderUtils.ts`, which `mergeGroupOrder` also uses), so a hidden item keeps its index, switch, style and tile, and turning the feature back on restores the layout.
- Features stored in `feature_choices` (medications and lab results: for each, the Library row, the Dashboard card through `DASHBOARD_CARD_FEATURES` and the What's New button) have one switch per platform: `useFeatureChoicesQuery` (`hooks/useFeatureChoices.ts`, over `services/api/featureChoicesApi.ts`, key `featureChoicesQueryKey`) reads both, and `useSetMobileFeatureChoice` changes the app's only. Their rows are `ChoiceFeatureRows`, usable only once the choices have loaded (`state`: `ready`, `loading`, `loadFailed` with Retry, or `serverTooOld` when the server answers the read with 404, which the query turns into `null`, with an "update your server" line; the Features screen then reads the choices again on each visit, `useRefetchOnFocus`, so updating the server takes effect without a restart). While the choices load, after a failed read and on an older server, every feature is at its default, so nothing that was showing disappears. Saves run one at a time (mutation `scope`), cancel a read on its way, drop an answer whose cached choices were cleared meanwhile (`startedOn` in `hooks/queryOwner.ts`, shared with the cycle settings writes) and show a toast when they fail. Each change is bound when the switch is tapped to the server on screen (`serverOnScreen` in `hooks/serverOnScreen.ts`, the `useServerConfigs` cache, passed to `apiFetch` as `serverConfig`), because a server switch stores the new active server before it clears the cache: a save queued behind another one would otherwise go to the new account. The lab results and medications screens have no deep link, so there is no route guard.
- Medications (`medications`, on by default) covers supplements, GLP-1 tracking, injections, adherence and the medication log. While it is off in the app, the Library row leaves and its count query (`useMedications`, enabled only while on) and its pull-to-refresh refetch stop, the Dashboard card leaves through `DASHBOARD_CARD_FEATURES`, the What's New "Set up medications" button leaves, Settings → Notifications shows one `FeaturesOffNotice` in place of its Medications group (Manage only while connected), and `MeasurementTimelineCard` leaves out the `medication` layer (the shared `GLUCOSE_CONTEXT_KIND_FEATURES`; the chosen layers are kept). The GLP-1 check-in categories (the shared `GLP1_CHECKIN_CATEGORY_NAMES`, through `FEATURE_CUSTOM_CATEGORIES`) are in `hiddenCustomCategories` only while it is explicitly off. Never gated: supplement nutrients in the day's totals (`dailySummaryService`, `hasSupplementNutrition`), the JS pending Taken/Skip queue, the iOS native ledger, the notification categories and channel, and watch `medicationTaken` taps. The watch pages do not follow the switch yet (#3487 step 5b): the watch's Medications page still shows and logs doses.
- Medication reminders follow the switch with three states (`MedicationsFeatureState` in `utils/medicationsFeatureState.ts`: `on`, `off`, `unknown`), read by `useMedicationsFeatureState` from the choices query alone, not `useMobileFeatures`, which gives the default while the choices load. It is `unknown` until the choices have been read (loading, a failed read, an offline launch) and `on` for a server older than Features (the read gives null). `MedicationReminderReconciler` schedules only while `on` and the reminder preferences allow, and cancels and dismisses every medication reminder while `off`. While `unknown` with an active server and the reminder settings wanting reminders (Medication Reminders and app notifications on), it leaves the active server's reminders exactly as they are, neither cancelled nor rescheduled, cancels only those made for another server (`cancelMedicationRemindersOfOtherServers`, by the `serverId` each reminder carries; one without it counts as the active server's; it reads only the stored active id (`getActiveServerConfigId`, no keychain), does nothing when that read fails, forgets the snooze records of the snoozed copies it cancels, and runs through the reconcile queue, after a pass under way and after any reconcile waiting with it, which it never drops; the reconciler runs it again when the active server changes), so an account switched away from offline stops reminding, and replays the Taken / Skip presses still waiting (`retryPendingMedicationActions`, one at a time, ownership-checked, a no-op on an empty queue), since the reconcile that would flush them is not run. With either reminder setting off the state does not matter: every medication reminder is cancelled and dismissed as before Features, also when the setting is switched off while `unknown` (both settings are effect deps); with no active server at all (none set up, or its config deleted) it cancels them as before. It reads the choices again when the app returns to the foreground, so a switch made elsewhere applies. `reconcileMedicationReminders` takes a required `{ active }` scope, so no caller can forget the feature, an optional `serverId` and an optional `accountGeneration` (`accountGeneration()` from `offline/accountGeneration.ts`): a pass read for one server does nothing (beyond logging waiting presses) if another server is active when it runs, and a pass read before an account change is dropped as it is queued, so it never takes the place of the new account's waiting reconcile, or skipped if the account changes before it runs. The background task binds its passes to the account and the server of when it starts (its reads follow whichever account is signed in as each one is sent, and an account change on the same server keeps the server id), and the reconciler passes the account its render read, so its effect, which runs after the render, is dropped if an account change started in between. The queue holds work rather than one pass: an account change (`useAuth`'s identity change: another account on the same server, another server, or the server deleted) calls `cancelMedicationRemindersForAccountChange`, which cancels and dismisses every medication reminder, clears the snooze records and drops a reconcile still waiting for the previous account; a reconcile queued after it runs after it. Once the change is done (`useAuth` calls `notifyAccountChanged` from `offline/events.ts` after the cookie sweep), the reconciler renders again (`subscribeAccountChanged`): `queryClient.clear()` does not tell the observers already mounted, and the reconciler lives outside the screens, so without it the new account's reminders would wait for the app to come back to the foreground. Like the caches, it cannot tell a sign-in back into the same account from another one, so that cancels too: the next reconcile schedules the reminders again, but a snoozed copy and the reminders already shown are gone. Snooze records that a clear or removal could not write away are logged and kept in an in-memory retry set (a removal whose read failed keeps its keys too): while the app runs, the reconcile's snooze sync leaves them out, so they do not keep a dose silent, and the next write that works removes them; a slot snoozed again since keeps its new record. A restart forgets the set, and a clear that could neither read nor write leaves the records as they were. A pass that cancels every reminder (`active: false`, or a reminder setting off) also clears the stored snoozed-reminder records (`clearSnoozedMedicationReminders`, `snoozed_medication_reminders`, under the lock their writers use), so turned back on the same day a snoozed dose's slot is scheduled again with its remaining repeats; denied OS permission leaves the records, and `cancelMedicationRemindersOfOtherServers` removes only those of the copies it cancels (`removeSnoozedMedicationReminders`). The background run (`reconcileMedicationRemindersInBackground` in `services/backgroundSyncService.ts`, from the OS task, the HealthKit observer and a manual sync) cancels everything when a reminder setting is off; otherwise it reads the choices itself through `fetchFeatureChoices` (`services/api/featureChoicesApi.ts`, which turns a 404 into null for the query and the task alike, read as on). When the read fails or the answer is empty it follows the `unknown` rule (leaves the active server's reminders, replays waiting presses, cancels other servers' reminders) and logs a warning. A reconcile is the last caller's, and an open app shares the JS runtime with a background run, so the run notes when its read started and, right before it reconciles (the cancel while `off`, the schedule while `on`), checks the app's cache under `featureChoicesQueryKey` (`medicationsStateChangedSince`): choices received after its read started that give a different Medications state make it skip the reconcile and leave it to the app (logged at DEBUG); older cached choices are ignored, a newer read that agrees lets it go ahead, and a headless run has an empty cache, so its own read stands. Nothing writes the `medicationReminder*` preferences because of the switch, so turning Medications back on brings the reminders back as they were.
- Cycle keeps its own account-wide switch, `cycle_settings.enabled`, so it also shows or hides cycle on the website. `useCycleSwitch` is the one cycle switch, shown only on Features (Settings → Cycle & Pregnancy shows its state and links there): it sends only `enabled` (`useSetCycleEnabled`, never `mark_onboarded`), opens `CycleOnboarding` the first time so the setup runs, and works only once the settings have loaded (`state`: `ready` once the query has data, `null` included, else `loadFailed` with Retry, else `loading`). There is no acting-for-someone mode in the app, so the web's `actingOnBehalf` state has no counterpart.
- Settings → Cycle & Pregnancy (`CycleSettingsScreen`) shows its details, Export and Reset only once cycle is on and set up, so none of their per-field writes can create a cycle row (an insert without `enabled` turns cycle on); with no row it says Turned off instead of loading forever, and Reset says it is done only once the server confirms it.
- `CycleHubScreen` runs the setup (`replace('CycleOnboarding')`) only while cycle was never set up or its setup was reset, and the + sheet's cycle row (`handleOpenCycle` in `useAddSheetActions`) opens `CycleOnboarding` instead of the log until `onboarded_at` is set, as `CycleCard`'s Set Up does. Once it was set up, a hub turned off shows "turned off" with **Turn on** and **Open Features**, so the setup never asks again and overwrites the settings; a failed load shows Retry, never the setup.
- Until the cycle settings are known, discreet mode is unknown too (`useDiscreetMode` fails closed), so the Features row names nothing (a spinner, or Retry), and the + sheet's cycle label and the Dashboard Settings row read the fail-closed hook. Both settings writes (`useCycleSettings().updateSettings` and `useSetCycleEnabled`) run one at a time (mutation `scope`), cancel a settings read already on its way (it answers with the values from before the write), refresh the overview, insights and fertility queries, and drop an answer whose cached settings were cleared meanwhile (`useAuth` clears the cache on an account or server change). Each is sent to the server on screen when it was made (`serverOnScreen`, passed to `putSettings` as `serverConfig`), so one queued during a server switch never reaches the new account; with no server known it saves nothing: `updateSettings` and the switch show the save failed toast, and `updateSettingsAsync` rejects instead, so its caller reports it (onboarding shows its own error). The cycle setup (`CycleOnboardingScreen`) binds the server once when Accept is tapped and sends every write with it: the settings (`updateSettingsAsync`'s optional `serverConfig`), the seeded period days (`bulkPutLogs`) and the pregnancy (`createPregnancyAsync` / `updatePregnancyAsync` take an optional `serverConfig`), so a switch while it saves never splits the setup across two accounts. A queued write takes its snapshot when it is queued, so a failed edit puts back only the fields it changed, never an `enabled` the switch saved meanwhile.
- Entry points of a feature outside its own screens (a Dashboard card, a + sheet row, the `MeasurementTimelineCard` `medication` layer) follow `useMobileFeatures().isEnabled`, so they show at the feature's default while the choices load or fail. Records a person already has, shown outside the feature's own screens, hide only while that feature is turned off on purpose (`useMobileFeatures().isExplicitlyOff`, the shared `isFeatureExplicitlyOff`: for cycle a row with `enabled = false`, for a `feature_choices` feature an explicit `false`, never a missing row, a missing choice or a load). The categories in `hiddenCustomCategories` (the shared `hiddenFeatureCustomCategories`: the reproductive ones for cycle, the GLP-1 check-in ones for medications; memoized because forms build lists from it) are left out of what `MeasurementsAddScreen` shows (its form keeps every Daily category, so a value typed before cycle's settings loaded comes back with cycle, but only the shown categories are checked for unsaved edits, validated and saved, so a hidden draft never blocks Save), `MeasurementTimelineCard` (a category picked before falls back to glucose) and the Diary's measurement tiles, with the shared `withoutHiddenCategories` where they use the list, never in the shared `customCategories` query, which Settings → Custom Measurements also reads. `useSymptomEntriesDetailed` and `useOngoingEpisodes` leave out cycle hub symptoms (`source = 'cycle'`, the shared `withoutCycleHubSymptoms`) through `select`. `useSymptomEntries` is not filtered: the hub reads it to save its picks, and a filtered list would log them again.
