# Auth, Networking, And Settings: details

Longer notes for the "Auth, Networking, And Settings" section of [`SparkyFitnessMobile/AGENTS.md`](../AGENTS.md). Each one has a one-line link there.

## Features (optional features)

- Settings → Features (#3487) is `FeatureSettingsScreen` (root-stack `FeatureSettings`, a Settings row shown while connected). It lists the shared registry's keys (`OPTIONAL_FEATURES` in `@workspace/shared`) by group, one set of rows per key (`FeatureRows` must cover each). Every entry point in the app asks `useMobileFeatures().isEnabled(key)` (`hooks/useMobileFeatures.ts`, the shared `isFeatureEnabled` for `mobile`), never the stored value: the + sheet through `ADD_MENU_ITEM_FEATURES` (`constants/addMenuItems.ts`) and `useAddMenuItemAvailable`, the Dashboard through `DASHBOARD_CARD_FEATURES` (`constants/dashboardCards.ts`), both with the shared `isShownByFeature`, and `CycleCard` itself. Dashboard Settings and Quick Actions keep listing an item of a feature that is off, with its place and switch, and say "Not shown: turned off in Features", so turning the feature back on restores the layout.
- Cycle is the only feature so far and keeps its own account-wide switch, `cycle_settings.enabled`, so it also shows or hides cycle on the website; the app's `feature_choices` are read there once a feature stored in them lands. `useCycleSwitch` is the one cycle switch, shown only on Features (Settings → Cycle & Pregnancy shows its state and links there): it sends only `enabled` (`useSetCycleEnabled`, never `mark_onboarded`), opens `CycleOnboarding` the first time so the setup runs, and works only once the settings have loaded (`state`: `ready` once the query has data, `null` included, else `loadFailed` with Retry, else `loading`). There is no acting-for-someone mode in the app, so the web's `actingOnBehalf` state has no counterpart.
- Settings → Cycle & Pregnancy (`CycleSettingsScreen`) shows its details, Export and Reset only once cycle is on and set up, so none of their per-field writes can create a cycle row (an insert without `enabled` turns cycle on); with no row it says Turned off instead of loading forever, and Reset says it is done only once the server confirms it.
- `CycleHubScreen` runs the setup (`replace('CycleOnboarding')`) only while cycle was never set up or its setup was reset, and the + sheet's cycle row (`handleOpenCycle` in `useAddSheetActions`) opens `CycleOnboarding` instead of the log until `onboarded_at` is set, as `CycleCard`'s Set Up does. Once it was set up, a hub turned off shows "turned off" with **Turn on** and **Open Features**, so the setup never asks again and overwrites the settings; a failed load shows Retry, never the setup.
- Until the cycle settings are known, discreet mode is unknown too (`useDiscreetMode` fails closed), so the Features row names nothing (a spinner, or Retry), and the + sheet's cycle label and the Dashboard Settings row read the fail-closed hook. Both settings writes (`useCycleSettings().updateSettings` and `useSetCycleEnabled`) run one at a time (mutation `scope`), cancel a settings read already on its way (it answers with the values from before the write), refresh the overview, insights and fertility queries, and drop an answer whose cached settings were cleared meanwhile (`useAuth` clears the cache on an account or server change). A queued write takes its snapshot when it is queued, so a failed edit puts back only the fields it changed, never an `enabled` the switch saved meanwhile.
- Data of a feature shown outside its own screens hides only while that feature is turned off on purpose (`useMobileFeatures().isExplicitlyOff`, the shared `isFeatureExplicitlyOff`: for cycle a row with `enabled = false`, never a missing row or a load). The reproductive categories in `hiddenCustomCategories` (the shared `hiddenFeatureCustomCategories`, memoized because forms build lists from it) are left out of what `MeasurementsAddScreen` shows (its form keeps every Daily category, so a value typed before cycle's settings loaded comes back with cycle, but only the shown categories are checked for unsaved edits, validated and saved, so a hidden draft never blocks Save), `MeasurementTimelineCard` (a category picked before falls back to glucose) and the Diary's measurement tiles, with the shared `withoutHiddenCategories` where they use the list, never in the shared `customCategories` query, which Settings → Custom Measurements also reads. `useSymptomEntriesDetailed` and `useOngoingEpisodes` leave out cycle hub symptoms (`source = 'cycle'`, the shared `withoutCycleHubSymptoms`) through `select`. `useSymptomEntries` is not filtered: the hub reads it to save its picks, and a filtered list would log them again.
