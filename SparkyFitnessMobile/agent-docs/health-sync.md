# Health Sync: details

Longer notes for the "Health Sync" section of [`SparkyFitnessMobile/AGENTS.md`](../AGENTS.md). Each one has a one-line link there.

## All-day heart rate

When the Heart Rate toggle is on, `runForegroundSync` (`services/shared/healthSyncEngine.ts`) starts `syncAllDayHeartRate` (`services/shared/heartRateSamplesSync.ts`) to store minute-by-minute heart rate for the Heart Rate report's day and range timelines.

- **When it runs.** After the main `syncHealthData` upload, and `runForegroundSync` returns without waiting for it, so it never delays the upload or holds the sync past the 90 s sync-on-open watchdog. Only one runs at a time: a sync that finds one running queues its own phase, which starts when the running one settles (only the latest queued phase is kept). `allDayHeartRateSettled()` resolves once none is running or queued. Background and observer syncs do not run it yet.
- **What it reads.** Raw `HeartRate` records, a week at a time, at most 30 days back: without the history permission Health Connect shows readings from 30 days before the app's first permission grant, so the last 30 days are always fully visible and no week is silently cut short (a `merge` over a cut-short week would delete stored readings). Readings are averaged to one per minute. Readings outside the week are dropped, and a partial first minute is stamped at the week's start, because the server rejects a write if any sample falls outside its window.
- **What it sends.** Each week goes to `POST /api/generic-health/samples` (`services/api/healthSamplesApi.ts`) as a `merge` write under the source `SparkyFitness Mobile` (the server refuses `HealthKit`, `Health Connect` and `manual`), so resending a week replaces it. A week whose read returns an error is not sent, since a `merge` of partial records would delete stored readings.
- **Coverage.** Once a run has uploaded every week, the span it covered is stored in AsyncStorage. A later run whose range that span already reaches back to starts 2 days before where it ended; otherwise it reads the whole range, so a short earlier run (a `today` sync) never makes a longer range skip its older days (`heartRateSyncPlan`).
- **Accounts.** A run belongs to the account active when `runForegroundSync` started. Its uploads pass that `ServerConfig` to `apiFetch` (`serverConfig`), so they never use whichever account is active later, and it stops before its next read or upload once a different account is active. An account is the config id plus a fingerprint of its URL and credential (`heartRateAccountId`), so another sign-in on the same server is a different account. Coverage is stored under it, one record per config (older accounts' records are dropped on write), so no account ever reads another's coverage and nothing has to be cleaned up on an account change. A renewed session token counts as a new account: the run stops and the next one reads the full range.
- **Timeouts.** Each read and each upload has a 60 s timeout. `apiFetch`'s own timeout stops at the response headers, so a timed-out upload is aborted through the `signal` that `postHealthMetricSamples` passes on; `fetchWithTimeout` keeps that signal wired to the request after the headers, so a stalled body read is cancelled too.
- **Logging.** Uploads pass `logResponseBody: false`, and an upload the server rejects (an `ApiError`) is logged as its HTTP status only (`HTTP 400`), because the response can quote the readings and the app log can be shared in a diagnostic report. Other failures are logged with their own message, which carries no readings: a timeout as `All-day heart rate upload timed out after 60000ms` (or `... read timed out ...`), a network failure as the fetch error's message, and a failed read as the error the reader returned.
- **Failures.** Isolated like writeback: logged, never added to `syncErrors`, and the next run sends the week again.
