# Garmin (Connect IQ): details

Longer notes for the "Garmin" section of [`SparkyFitnessMobile/AGENTS.md`](../AGENTS.md).

The Garmin port of the Apple Watch app is built one feature at a time (the Apple Watch inventory lists every feature). Shipped so far: the bridge and the **Goals** page with its glance. Android only; there is no iOS bridge.

Until the watch app is on the Connect IQ Store, the whole feature is on only in development builds: `isGarminWatchEnabled()` (`src/constants/garmin.ts`) is `Platform.OS === 'android' && (__DEV__ || GARMIN_WATCH_APP_RELEASED) && isGarminAvailable()`, and it gates the Settings row, the sync and every start from JS. A release build therefore starts the Connect IQ SDK only if a flag left by a development build of the same package makes the process start it (see Phone side), and its UI clears that flag the first time it runs; that keeps the SDK's exported broadcast receiver off ordinary installs. Flip `GARMIN_WATCH_APP_RELEASED` when the store listing exists.

## Transport model

Connect IQ has one channel: a mailbox. There is no latest-value slot (Apple's application context, Wear OS's `/sparky/context` DataItem) and no OS queue that delivers later.

- Phone → watch: `ConnectIQ.sendMessage`. When the watch is away the link answers `notConnected` itself (SDK 2.4.0 never reports `FAILURE_DEVICE_NOT_CONNECTED`; a watch that drops mid-transfer comes back as a transfer failure). When the watch is connected but the app is closed, the message waits in the app's mailbox and is handed over, one call per message, when the app registers for phone messages.
- Watch → phone: `Communications.transmit`. In the SDK's default broadcast mode the phone app only receives while its process is alive (the SDK registers its receiver at runtime); with Garmin's binder delivery (see [Binder delivery](#binder-delivery)) Garmin Connect can start the process. Nothing the watch sends is stored by the OS.
- On the watch, a phone message also wakes the app's background service when the app is closed (see Watch app), so the glance can stay current.
- So the phone keeps the latest snapshot itself and resends it when the watch connects or asks, and the watch keeps the last snapshot in `Application.Storage` and asks for a fresh one each time the app opens. Writes from the watch (from the Water step on) will sit in a watch-side outbox until the phone acknowledges them.
- Limits: the watch app's mailbox holds 8 KB from the phone (Connect IQ SDK 2.2.0 changelog), so the link caps a message's estimated size at 8 KB (`GARMIN_MESSAGE_BYTE_CAP`); the estimate errs high (it counts repeated keys per row, the serializer stores them once), so that is about 5 KB serialised, and a Goals topic with every standard nutrient is about 2 KB (the watch parses each into memory; on the fēnix 8 the glance and the background service have about 64 KB). Snapshots are therefore split by topic, and only changed topics are sent.

## Protocol (version 1)

All messages are dictionaries with string keys. Values are strings, numbers, booleans, arrays or dictionaries; null is never sent (an absent key means none). Every message has `type` and `v` (protocol version, `1`). A receiver ignores unknown `type`s and unknown keys. Every phone → watch message also carries `seq` and `origin`, added by the native link as it hands the message to the SDK: `seq` is one more than the last send, or the clock in ms when higher, written to the link's preferences (synchronously, best effort: a failed write is logged and the send still goes) before the message goes, so within one `origin` it only rises, across process starts and whatever the clock does, unless that write failed and the clock reads below the lost number at the next start; `origin` is a random id made once per install and kept with the app's install time, so a reinstall or another phone numbers its own messages even when Android's backup or device transfer copied the preferences over (and cleared data loses it anyway); for the same reason a snapshot cache another install wrote reads as empty. A resend gets a new `seq`. The watch uses the pair to drop a message it already applied, or one sent before that (see Watch app); JS never builds or sees them.

### Watch → phone

| `type`           | Keys | When                                                                                               | Phone action                                                                                                                                                                                                                                                                                                                                         |
| ---------------- | ---- | -------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `requestContext` | none | The full app starts (`getInitialView`; `onStart` also runs for the glance, which never transmits). | That watch gets the latest snapshot in full at once: from JS (its snapshot in memory, else the native cache, else `accountCleared` when signed out), or from native itself when nothing in JS listens for `onGarminResync` (the cache, else `accountCleared`). The request is also routed like a Wear OS one (JS `onContextRequest` → a fresh push). |

### Phone → watch

| `type`           | Keys                                                                                                                                                                                                                                                              | Watch action                                                                                                                                                                                                                                                                                                                                                                                        |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `snapshot`       | `pushedAt` (epoch ms), `today` (`YYYY-MM-DD`, the phone's day), `owner` (active server config id, `""` when none), `topics` (dictionary: topic name → topic dictionary; only the topics that changed since the last snapshot this watch received, or all of them) | If the stored `owner` and the new one are both non-empty and differ, delete every stored topic first. Store each known topic under its own Storage key, replacing the previous one; ignore unknown topic names. Delete the older copy of each topic that cannot be stored (object store full), and then leave `meta` as it was. Store `{pushedAt, today, owner, seq, origin}` under `meta`. Redraw. |
| `accountCleared` | none                                                                                                                                                                                                                                                              | Delete every stored topic. Keep only `seq` and `origin` in `meta` (no owner, day or `pushedAt`). Redraw (the pages show their not-synced state).                                                                                                                                                                                                                                                    |

### Topic `goals`

Built by `buildGarminSnapshot` from the same context the Apple Watch gets (`WatchContextPayload`).

| Key                               | Type               | Meaning                                                                                                                                                                                                                                                            |
| --------------------------------- | ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `energyUnit`                      | `"kcal"` or `"kJ"` | Display unit. Always present. Values are always kcal; the watch converts (kJ = kcal × 4.184, rounded).                                                                                                                                                             |
| `day`                             | `YYYY-MM-DD`       | The day the figures belong to. **Absent when the phone cannot vouch for today** (the context's three calorie figures are not all numbers, which is how the phone blanks a stale day); then the other keys below are absent too.                                    |
| `consumed`, `burned`, `remaining` | integer kcal       | `caloriesConsumed`, `caloriesBurned`, `caloriesRemaining`, rounded. `remaining` is negative when over.                                                                                                                                                             |
| `progress`                        | number 0…1         | `calorieGoalProgress` (already clamped by the phone; 0 when absent).                                                                                                                                                                                               |
| `nutrients`                       | array              | `goalNutrients` in order, each `{key, label, unit, consumed, progress}` plus `goal` only when the nutrient has a goal (a goal that rounds to 0 or less counts as none). `consumed` and `goal` are rounded to whole numbers. Empty array when the phone sends none. |

The watch shows the figures only when `goals.day` equals the watch's own local date; otherwise (absent, or yesterday) it shows the not-synced state. It also reads a malformed or partial topic (a `day` without all three calorie figures) as not synced, treats any `energyUnit` other than `kJ` as kcal, re-clamps progress to 0…1, and skips a nutrient row without a key, label or amount, as the Apple Watch mapper does.

## Watch app

- One device app (manifest type `watch-app`), `minApiLevel` 5.2.0, product `fenix843mm` for now (add products to the manifest as people test them; every product needs its device files to build).
- Pages run in a `WatchUi.ViewLoop` built by a page factory; the Goals page is the only page today. Adding a page means adding it to the factory.
- `getGlanceView` gives the glance: the app name, then today's calories left or over ("1234 kcal left", "254 kcal over": unsigned there, because the words already say which), then a calorie-colour bar with "as of 9:12" on its right (`meta.pushedAt`, local 12/24 h; AM/PM is dropped when the bar would get too short), or "Open on the watch, phone app nearby". The glance shows what the full app or the background service last stored, and the time tells the wearer how old it is. Code the glance uses carries `(:glance)`, and so do the strings it loads (`scope="glance"`); it only reads Storage.
- `Link` wraps Communications. It starts in `getInitialView`, which only the full app reaches, registers for phone messages (waiting messages are handed over at once), sends `requestContext`, and transmits one message at a time from a short queue (a failed send is dropped; the phone answers the next request). `SnapshotStore` owns the Storage keys (`meta`, `goals`) and the owner/day rules.
- Background updates (`BackgroundService.mc`, `Background` permission): `BackgroundRegistration.register()` calls `Background.registerForPhoneAppMessageEvent()` when the device has it, from `onAppInstall` and `onAppUpdate` (run by the system in the background, not guaranteed) and again each time the full app opens, and `onPhoneAppMessage` applies a phone message while the app is closed, then exits. The foreground `Link` and the background service share `Inbound.apply`, so the rules are one, and both drop a snapshot or `accountCleared` already applied or sent before the last one applied: same `origin`, `seq` not above the stored one (`SnapshotStore.isLate`), however late. The background can start seconds late, after the open app took the same message and newer ones (when the watch gives a message to both) or took the next ones itself (a message reaches only the background while the app is closed); and the open app's mailbox can hand it what the background already applied. Applying such a message would bring back replaced figures (a signed-out account's included) or empty the watch of the next account's, and the phone does not resend a topic it thinks the watch has. Ordering by send rather than by `pushedAt` means a resend that kept an old `pushedAt` is still newer than what it follows. Another `origin`, and a message without the pair, is always applied. `onStorageChanged` (which Garmin documents between the background process and the running app, both ways) redraws the page or the glance in the process that did not write, and updates the nutrient list in place, or closes it when its rows no longer match (today's goals gone, or another number of rows; a covered list is checked again whenever it is shown, and a list on screen at local midnight is checked then) (`NutrientList.refresh`, also run after each message the open app applies), so the list never keeps another account's figures. Each background event logs one line (`bg HH:MM:SS snapshot applied`, `null message`, `late message dropped`, ...), readable on a sideloaded build in `GARMIN/APPS/LOGS/<APP>.TXT`. Some watches are reported never to fire the event or to deliver it empty; then the glance waits for the app to open, as before, and until then keeps the last figures it had, a signed-out account's included.
- Goals page (416 × 416 round on the fēnix 8 43 mm; sizes are scaled from the screen width so other round screens work): the calorie ring in `GoalPalette.calories` with calories left inside (signed) and "kcal left" / "kcal over" / "kJ left" / "kJ over" under it, the "eaten · burned" line, then up to three nutrient rows (name, amount, "/ goal unit" or just the unit, a bar when there is a goal). With more than three nutrients, a "+N more" hint shows when it fits, and Select or a tap opens a `Menu2` listing all of them (label, and "62 / 150g" or "62 mg" under it). All nutrient text lines share one left and right edge, the chord of the narrowest line (wider than the bars, which share the chord at the last bar's bottom so they compare), and a row drops "/ goal" for the bare unit when its name would otherwise be cut below a minimum. When the snapshot is older than 15 minutes a footer says "as of 9:12 AM" (in place of the "+N more" hint), also on a page left open, through a timer set for the moment the figures turn old or local midnight, whichever comes first, so a page left open over midnight drops yesterday's figures. Without today's figures: dashes and, for 15 s after the app asked the phone (`SyncRequest`), "Getting today's numbers from your phone…", then "Open SparkyFitness on your phone, nearby, to sync today's numbers." The calories left use Garmin's scalable number face (`BionicMedium`, `Graphics.getVectorFont`) sized to the ring where the watch has it, since the system number fonts are far taller than the ring; other watches keep the largest system font that fits. The nutrient list slides in from the right, as Garmin's menus do, and says under it when its figures are from ("as of 9:12 AM").
- Colours match the Apple Watch `GoalPalette`: calories `0x8992DC`, protein `0xDBB06F`, carbs `0x97C692`, fat `0x8AC2DA`; any other nutrient takes `0xEA96B0`, `0xCDAEF6`, `0xF6D375`, `0x89D7C6`, `0xF4A284` by its row index (index modulo 5, the index counting every row). Text is white or grey on black.
- Strings live in `targets/garmin/resources/strings/strings.xml` (English only; other languages come later through Weblate). Never build a string key or a colour from translated text.
- Unit tests are `(:test)` functions in `targets/garmin/source/test/`; they cover the pure parts (snapshot rules, day gate, energy conversion, formatting, colours, the clock and age rule, the row layout). They compile here but run only in the simulator.

## Phone side

The split is "thin native, logic in TypeScript": the native layer only moves bytes and reports devices, so an iOS transport later is a second thin layer, and everything that decides what to send is shared and covered by Jest in CI.

**Native (`garmin/` in the module: `GarminLink`, `GarminProtocol`, `GarminWire`; mechanics only):**

- The link starts from JS, or at process start once JS has enabled it: JS calls `startGarmin()` when `isGarminWatchEnabled()` allows (and again on every return to the foreground). It is idempotent, re-checks that Garmin Connect is installed, and always re-reads the known watches, which is how a watch paired later is found (the SDK drops messages from watches it was never told about). Starting means `ConnectIQ.getInstance(context, IQConnectType.WIRELESS)`, `initialize(context, autoUI = false, …)` (never show Garmin's install dialogs), then for every known watch `registerForDeviceEvents` and `registerForAppEvents(device, IQApp(GARMIN_APP_ID))`, and `getApplicationInfo` for the Settings display (a watch that sent a message since it connected is never downgraded to not installed by that answer, since a sideloaded app may not be recognised). A 20 s watchdog turns an initialise that never answers into the `bindTimeout` error, and the service going away re-initialises with a backoff (2 s doubling, up to 5 min); a start from JS while the link is in error skips the wait, at most once every 30 s. Until the link has been started (by `startGarmin()`, or at process start when the enabled flag is set) and after `stopGarmin()`, `garminStatus()` reports `unavailable` and starts nothing, and sends and open requests answer `failed`. SDK calls and its state stay on the main thread, as the SDK requires; value conversion for JS's messages and the snapshot cache run on a worker, while the link's own small preferences file (`sparky_garmin_link`: the enabled flag, the binder record, the send `seq` and `origin`, and the install time the origin belongs to, which also drops a binder record restored from another install) is read and written on the main thread.
- Development switch (Settings → Garmin → Development, `canUseGarminSimulator()`): `setGarminSimulator(on)` makes the link use `IQConnectType.TETHERED`, the Connect IQ simulator over ADB (`adb forward tcp:7381 tcp:7381`, then Connection → Start in the simulator), instead of `WIRELESS` through Garmin Connect. Stored in the link's preferences and honoured only by a debuggable build. The mode is chosen at the first start of the process and kept until the app starts again, because the SDK cannot close its ADB connection (its server thread outlives `shutdown` and would call into the old instance): in that mode the link never shuts the SDK down or re-initialises it, a stop only clears the flags, and failing SDK calls (it throws while no simulator is connected) are not taken for a lost service. The simulator's SDK sleeps to mimic Bluetooth and writes to its socket on the calling thread, so sends run on their own thread; it names every incoming message's app `""`, so the link also listens under that id; and the app info is not asked (the simulator runs this app). `isGarminAvailable` reports true while the switch is on (so an emulator without Garmin Connect works), binder delivery is never tried, `delivery` reads `simulator`, and `stopGarmin()` clears it. The SDK's port listens on every network interface, so use a trusted network. Steps in `targets/garmin/README.md`.
- `startGarmin()` also saves an enabled flag (small preferences file `sparky_garmin_link`), and `WatchConnectivityPackage`'s `ApplicationLifecycleListener` starts the link in `Application.onCreate` when that flag is set and Garmin Connect is installed (or the simulator switch is on), so a process Garmin Connect starts through the binder service has the SDK initialised and its listener set before a message is handed over. Until JS has listened to `onGarminResync` in that process, a watch connecting or the SDK becoming ready replays nothing (a cold or background start does not push the whole snapshot to every watch); a `requestContext` still gets the cached snapshot, or `accountCleared` when nothing is cached. `stopGarmin()` (called by JS at start-up when `isGarminWatchEnabled()` is false, so a development build's leftover flag cannot keep a release install's SDK running) unregisters binder delivery when it is on or Garmin Connect may still hold a registration (a confirmed or unconfirmed record; once the SDK is ready), shuts the SDK down, forgets the watches and clears the flag (and the binder record once the unregister went out); it keeps the snapshot cache. Only a process where the link runs can send that unregister. The status carries `delivery` (`binder`, `broadcast`, `simulator`, or `none` while not ready), shown in Settings → Garmin.
- `sendGarminMessage(deviceId, message)` sends one message to one watch as JS built it (values converted by `GarminWire`, `seq` and `origin` added at send time, nothing else) and resolves with `sent`, `notConnected`, `tooLarge` (estimated serialised size over 8 KB less 64 bytes kept for `seq` and `origin`, or the SDK's own "too large"; never retried as is) or `failed`. Sends go one at a time across all watches (30 s timeout). The SDK keeps one send listener per watch and its status carries no message id, so after a send is given up (timeout, disconnect, service lost) that watch is held back (`GarminAbandonedSends`) until the late status arrives and is thrown away or 30 s pass; jobs for it wait meanwhile while other watches keep sending (a bounded wait: the grace period plus the sends queued ahead, 30 s each at most).
- `setGarminSnapshotCache(message | null)` keeps the latest full `snapshot` message (SharedPreferences `sparky.garmin.lastSnapshot`) and `getGarminSnapshotCache()` reads it back (it rejects when the stored copy cannot be read, which JS never takes for signed out; natively, an unreadable copy also stops the `accountCleared` answer); the native side never builds, diffs or edits a snapshot.
- When a watch connects (`reason: 'connected'`), when the SDK becomes ready with a watch connected (`'ready'`), or when a watch sends `requestContext` (`'requested'`), native emits `onGarminResync({deviceId, reason})`, after the matching `onGarminStatusChange`, but only while JS listens to that event (tracked with Expo's per-event `OnStartObserving` / `OnStopObserving`). With no listener it answers a `requestContext` itself with the cached message (or `accountCleared` when nothing is cached), and replays the cache on `connected` and `ready` only once JS has listened in this process (next bullet).
- Inbound messages pass an allowlist (`GARMIN_INBOUND_TYPES`, today only `requestContext`) before the Wear OS router (`WatchConnectivityHub`), so JS also gets `onContextRequest` and pushes fresh data, exactly as for a Wear OS request. The allowlist exists because the SDK registers its receiver exported and never checks the sender: any app on the phone could forge a "watch" message, and Wear OS types such as `runFinished` would reach the account. Each later write type is added to it on purpose, with its owner check. The same exposure lets another app crash the process with a malformed broadcast; the dev-only gate keeps it off release installs (JS never starts it there, and stops a start left by a development build at launch), and the Garmin-approved binder delivery (`registerAppToUseBinderService`, which needs Garmin's sign-off) should replace broadcast mode before release. The SDK's manifest also merges an exported `IQGarminBindingService` and `AutoUIDialogHostActivity` into every build; the service checks that its caller is signed by Garmin, and is idle unless the binder delivery is registered.
- `clearGarminAccount()` (also run by `clearServerCredentials`) deletes the cache, answers queued sends `failed`, and sends `accountCleared` to every watch connected while the SDK is ready. A watch that misses it and asks (`requestContext`) before the next account publishes gets `accountCleared` then; once the next account has published it gets that snapshot in full instead, and an owner change wipes the old topics (with the same owner the topics are overwritten). A watch that only reconnects while nothing in JS listens gets nothing until it asks while nothing is cached, or before JS has listened in this process; once the next account has published and JS has listened, it gets the cached snapshot (see `GarminResyncPolicy`).
- Other JS API (all optional on the module type; Android only): `isGarminAvailable()` (sync: Garmin Connect is installed), `garminStatus()` and the `onGarminStatusChange` event (`state`: `unavailable`, `starting`, `ready` or `error`, with an `error` code that is never shown raw: `garminConnectUpgradeNeeded` and `bindTimeout` get their own hints in Settings; `devices`: `{id, name, connected, app: installed | notInstalled | unknown}`), and `openGarminApp(deviceId)` (shows Garmin's "open app" prompt on the watch).

**TypeScript (shared by any future iOS transport):**

- `buildGarminSnapshot(context)` (`utils/garminSnapshot.ts`) projects the context into topics (`{pushedAt, today, owner, topics}`).
- `services/garminSync.ts` decides what each watch gets. `getGarminSync()` returns the shared instance, or null unless `isGarminWatchEnabled()` and the native methods exist. `publish(snapshot)` stores it, updates the native cache with the full message, and sends each connected watch a `snapshot` with only the topics whose content (key-order independent JSON) differs from what that watch confirmed with `sent`; a watch with nothing new gets nothing, except a bare envelope (no topics) when the snapshot is at least 5 minutes newer than the one it last received, so the watch's "as of" time keeps up with what the phone confirms, and a watch whose record is unknown gets everything (the bare envelope when there are no topics, so the owner still arrives). The app state is for display only: a watch marked not installed still gets sends, and the result decides. A queued send reads the latest snapshot when it runs. An `owner` of `''` means signed out: the cache is cleared and nothing is sent. Each push captures the sync's account epoch when it starts, and a snapshot from before an account clear is dropped, so a push still in flight cannot bring the previous session's figures back. While the link is not ready, `publish` calls `startGarmin()` first.
- Any result other than `sent` or `tooLarge` forgets what that watch has, so its next message is in full; `tooLarge` with several topics is retried one topic per message, and a single topic that is too large goes again without its nutrient rows when it has some (`withoutNutrientRows`, so the calorie figures still arrive; recorded as the whole topic, so it is not tried again until it changes), else it is logged and skipped. A cached copy that is too large is retried the same way, unrecorded; the native side's own replay without JS is not. A resync, a change of `owner`, a watch that disconnects or disappears, and a watch whose app goes from not installed to installed also forget the record (a resync then sends in full at once; with no snapshot in memory yet, it sends the native cache as stored, or `accountCleared` when there is none). Sends to one watch never overlap, and a result that arrives after its record was forgotten is not recorded.
- Account changes: the identity-change handler in `useAuth.ts` (a different active server, a replaced session, the active configuration deleted) calls `clearGarminAccount()`, which resets the sync (no snapshot, no records, cache cleared) and calls the native clear, whatever the connection state, so the watch never keeps the previous account's figures.
- `useWatchCheckInBridge`: `useGarminWatchSync()` subscribes `onGarminResync` and `onGarminStatusChange` (handlers look the sync up when they run) and starts the link whenever the flag allows, independently of the server connection, so a watch is answered from the phone's copy while the server is unreachable; it starts again and re-reads the watches on every return to the foreground. It answers whether the sync has linked; when that turns true after mount (the simulator switch, Garmin Connect installed while the app runs), the bridge sets up the listeners it skipped for want of a watch transport (`hasWatchTransport()`) and pushes the context. After each context push (which needs the server), `sendContextToWatches` starts the Wear OS context send (only when `isSupported()`) and the Garmin publish together but awaits only the first, so a slow Bluetooth delivery never holds up the bridge's own queue (the medication ticks).
- Settings → Garmin (`GarminSettingsScreen`, shown when `isGarminWatchEnabled()`): the link state with hints, each watch with its connection and whether SparkyFitness is installed on it (with a note that the app is not on the Connect IQ Store yet and is installed by hand), "Open on watch" for every connected watch (labelled per watch for screen readers; Garmin Connect's not-installed answer is not trusted for a sideloaded app, so the open result says when the app is missing), and the Goals page nutrients (`WatchGoalNutrientsSection`, the same preference and component as Settings → Wear OS / Apple Watch, so a change shows on every watch).

## Binder delivery

Garmin's SDK 2.4.0 has a second way to receive watch messages: `registerAppToUseBinderService(appId)` asks Garmin Connect to deliver through the exported `IQGarminBindingService` the SDK merges into the app (it accepts only Garmin Connect, checked by package and signing certificate) instead of broadcasts. Garmin Connect can then bind it and start the process, and the exported broadcast receiver is unregistered. The javadoc marks it, and the app-wide `registerForAppEvents(listener)` it needs, "do not use without prior approval from Garmin"; approval is being requested.

What the SDK does (read from its bytecode):

- The registration is a one-way call: no answer comes back, and Garmin Connect's refusal (no approval, or a version without the call) is silent. The SDK has already switched to binder mode and dropped its receiver by then, so a refused registration would leave the app deaf.
- Binder-delivered watch messages reach the app-wide listener on the main thread, for any watch; device status, app info and send status arrive on a binder thread. An empty payload is reported as `FAILURE_UNKNOWN`. A message that reaches a process whose SDK was never initialised is dropped while Garmin Connect is told it succeeded, hence the start in `Application.onCreate`.
- The SDK's binder flag is never reset and a second registration on one instance throws; a fresh instance comes from `getInstance(TETHERED)` followed by `getInstance(WIRELESS)`.

So `GarminLink` probes instead of trusting the call (`GarminBinder.kt`): once the SDK is ready and a watch is connected, it registers, asks each connected watch for its app info, and waits up to 15 s for anything to arrive through the binder. A binder callback confirms it (`delivery: 'binder'`); otherwise it unregisters, starts a fresh SDK instance and reports `broadcast`. A confirmed registration is probed again at every start that has a watch connected (with none, the link stays on broadcasts until the SDK is next ready). A probe that times out after an earlier confirmation is recorded as unconfirmed and retried the next time the link starts, not again in the same start (so a watch busy for a minute cannot run up three timeouts at once), and the registration is kept: the link goes back to broadcasts on a fresh SDK instance without unregistering, so a late answer through the binder still arrives and the watch can still wake the process. Anything that later arrives through the binder records the confirmation again and lets the next time the SDK is ready probe again, even in the same start; until then the link and Settings stay on broadcasts. Three timeouts in a row, a first attempt that is never confirmed, or a registration that throws after Garmin Connect was told record a rejection and unregister; a rejection is not retried for 24 h unless the Garmin Connect version changes. A registration the SDK refuses before telling Garmin Connect records nothing and leaves the link on broadcasts. Without approval this costs about 15 s of "starting" at most once a day, or after a Garmin Connect update. Test on a phone with `adb logcat -s GarminLink IQGarminBindingService ConnectIQ` ("Trying Garmin binder delivery", then "confirmed after N ms" or "not confirmed (…); back to broadcasts").
