# Offline (#1983)

Everything the app keeps for use without a connection lives in `src/offline/`. User guide: `docs/src/features/exercises/offline-workouts.md`. Design notes and decisions: `WIP/offline/` (git-ignored, maintainer's copy).

## Storage

- One SQLite file, `sparky-offline.db` (`expo-sqlite`), opened by `getOfflineDb()` (`db.ts`). Tables in `schema.ts`, versioned with `PRAGMA user_version`: add a step to `MIGRATIONS`, never edit a shipped one. Tables: `cache` (server JSON per collection and key), `outbox` (uploads), `offline_image` (saved pictures), `offline_keep` (exercises the person chose to keep pictures of).
- No table mirrors the server. A new server column needs no change here; a new module adds a `collection` name (`collections.ts`) and an outbox `kind`.
- Every row carries `server_config_id`. An account switch clears `cache` and pictures (`hooks/useAuth.ts`, the cache clear is awaited) and bumps `accountGeneration()` (`accountGeneration.ts`); a refresh, a fetch that stores its answer and a Diary save take the number when they start and write only while it is unchanged, because a switch on the same server keeps the config id. Waiting uploads stay, carry `user_id`, and are sent only while that same account is signed in (`syncEngine.ts`); a row with no recorded account waits for Upload now.
- Tests run the real SQL on Node's built-in SQLite through `__tests__/helpers/offlineTestDb.ts`; `jest.setup.js` makes `expo-sqlite` fail to open everywhere else. Use `__setOfflineDbForTests(db)`.

## Reading without a connection

- `withOfflineFallback({ fetch, store, read })` wraps an API client function: on success it stores the answer, on a connection failure (`serverMayBeDown`, `utils/serverErrors.ts`) it answers from `cache`, and a 4xx is never replaced. While the connection check already says the server is away it answers from the phone at once. It reports a fallback through `offline/connection.ts`, which the query client listens to so the connection is re-checked.
- Wrapped today: workout presets (list, page, search, by id), exercise search, suggested exercises, exercise by id, exercise stats, preferences, plate inventory, profile, active workout plans per day, workout feedback (empty only for a session waiting to upload). `fetchDailySummary` stores the day's own workouts for the offline Diary (`offline/diaryDay.ts`).
- `offlinePack.ts` (`refreshOfflinePack`) downloads what a workout needs, at most every 6 hours, from `useOfflineUploads` while connected; it calls the server directly, never the wrapped fetchers. `isOfflinePackReady` gates an offline start (the weight unit comes from the saved preferences).
- The Library tab offline (`components/OfflineLibrary.tsx`, used by `LibraryScreen` when the connection status is `unreachable`) lists only Workout presets and Exercises; the rest of the Library needs the server.
- `ServerGate offlineCapable` shows a screen's content under `OfflineBanner` while the server is set up but unreachable. The unreachable message offers "Start a saved workout offline".

## Writing without a connection

- The live workout stays in `activeWorkoutStore`. `pendingCreate` marks a session the server does not have yet; the first save (`useActiveWorkoutAutosave`) creates it with its phone-minted id and an update follows at once (the create's answer can be an older stored copy, so it is never adopted). `offlineBaseRevision` guards the first save after an offline stretch; a 409 whose server copy equals what this phone last sent (`sessionsEqual.ts`) is the phone's own lost-answer save, not a conflict.
- The Add workout form (`WorkoutAddScreen`) saves a past workout or an edit with no server through `queueWorkoutCreate` / `queueWorkoutUpdate` (`workoutHandOver.ts`; a second edit merges into the waiting update row); `queueAfterConnectionFailure` queues after a lost connection but never after a timeout, since the server may have processed the request.
- Finishing or discarding with no server hands the workout to the outbox (`workoutHandOver.ts`): a create, an update with the last revision seen, or a delete (also queued by `useDeleteWorkout` for a saved workout, with its `entry_date`, so the diary hides it through `OfflineDiaryDay.deleted`). The live store is cleared only after the outbox row is written.
- `outbox.ts` keeps one unconfirmed row per entity and kind. `syncEngine.ts` (`drainOutbox`) sends due rows oldest first, one run at a time, with a backoff; a row with `depends_on` waits for that row. Triggers: reconnect (`hooks/queryClient.ts`), app open and foreground (`hooks/useOfflineUploads.ts`), the background task, Upload now.
- Water (#1983): one `+` press (`useWaterIntakeMutation`'s `logDrink`, also quick-add presets) is sent with a phone-minted `client_id` and, after a lost connection (never a timeout), queued as `water.add` (`waterHandOver.ts`, `handlers/waterIntake.ts`; one row per press, the press id is the row's `entityId` and the replay key). `−` stays online-only. The server answers a repeat key with the current totals and logs nothing (`water_intake_entries.client_id`, a partial unique index on `(user_id, client_id)`; a container linked to a food puts the same key on its `food_entries` row). Every place on the phone that logs a drink goes through `logDrinkOrQueue` (`offline/logDrink.ts`): the Dashboard `+` and quick-add drinks (`useWaterIntakeMutation`) and the watch's water taps (`useWatchCheckInBridge.handleWaterTap`, which acks the watch once the drink is queued, since the phone owns it durably). Not queued: Siri/widget/Control Center intents (native, they say the server could not be reached), the app-icon quick action (needs a connection to run) and NFC drinks (the server runs those).
- Food entries (#1983): `useAddFoodEntry`'s `createOrQueueFoodEntry` sends an entry that needs nothing created first with a `client_id` and, after a lost connection (never a timeout), queues it as `food_entry.create` (`foodEntryHandOver.ts`, `handlers/foodEntry.ts`; `isQueueableFoodEntry` accepts a food with both its `food_id` and `variant_id`, or a quick-add with a name and calories; a food still to be saved and the save-food chain always need the server).
- New foods (#1983): `useAddFoodEntry` saves a new food and logs it in one go (Log food → New food, a quick-create from the diary). The food goes with a phone-minted `client_id` (and the entry with its own); after a lost connection (never a timeout) a plain food is queued as ONE row, `food.create` (`foodCreateHandOver.ts`, `handlers/foodCreate.ts`), whose `entityId` is the entry's key so the waiting entry (`pending-<key>`) is cancelled or previewed like any other. Sending creates the food (the server answers a repeat key with the food it already made, `foods.client_id`, so no duplicate), then logs the entry against the ids it returns (the default serving's id and unit come from that answer, which is why nothing has to be chosen on the phone). `isQueueableFoodCreate` accepts only a plain food: no picture, no extra or provider servings, no provider/barcode import; anything else still needs the server. The Diary and totals show it as the food's own serving × quantity (`previewFromQueuedFoodCreate`). A food made only for the library (no entry), and a second entry against a food that is still waiting, need the server (the food has no id yet).
- Logged meals (#1983): `useAddFoodEntryMeal`'s `createOrQueueMeal` sends a meal with a `client_id` and, after a lost connection (never a timeout), queues one that names a saved meal as `food_entry_meal.create` (`foodEntryMealHandOver.ts`, `handlers/foodEntryMeal.ts`; `isQueueableFoodEntryMeal`: a `meal_template_id`, and any customised ingredient must name a food and serving the server has; a meal made up on the spot needs the server). The pack keeps the person's saved meals (`meal` collection, by name; `fetchMeals`, `fetchMeal`, `searchMeals` answer from it) and `FoodSearchScreen` searches them offline (landing lists of recent/top meals and favourites stay off). The Diary and totals show a waiting meal as one entry (`previewFromQueuedMeal`: per-serving nutrition from the kept meal × the servings logged); only a plain serving count of a kept meal can be previewed, other units and customised ingredients are left out of the preview but still upload. The caller gets a pending entry (`isPendingEntry`, id `pending-<key>`) so screens carry on. Waiting entries are listed in Settings → Offline and shown in the offline Diary (below). They are counted in the day's totals (below).
- Offline Diary food (#1983): the Diary day's food entries are saved like the workouts (`saveDiaryDayFood` from `fetchDailySummary`, `refreshRecentFoodDays` in each pack refresh through one `GET /api/food-entries/range/…`, 7 days, collection `diary_food_day`). `readOfflineDiaryDay` adds `savedFood` and `waitingFood`: a waiting `food_entry.create` row is shown as the entry it will become (`previewFromQueuedFoodEntry`: a quick-add from its own nutrients, a library food from the serving kept for it, scaled by the Diary's usual value × quantity ÷ serving size; a food no longer kept is left out of the preview but still uploads). `renderOfflineDay` in `DiaryScreen` draws them with `FoodSummary readOnly` (no swipe delete, adjust or detail, since those need the server). Entries are listed as the server last had them (logged meals as their component rows, not collapsed), and a food entry cannot be edited offline.
- Deleting food offline (#1983): `useDeleteFoodEntry` first checks whether the entry is still waiting (`isPendingEntryId`, id `pending-<key>`): then `cancelWaitingEntry` (`foodEntryDeleteHandOver.ts`) takes it out of the outbox (by the key, also for a waiting meal or drink; a row being sent this moment is left alone and the person is told to try again). Otherwise it calls the server and, when the server cannot be reached (a timeout included: a delete is safe to send again), queues `food_entry.delete` (`handlers/foodEntryDelete.ts`; a 404 counts as done). A waiting removal hides the entry in the offline Diary (`deletedFood`) and in the day's totals (`deletedFoodEntryIds` in the overlay: out of the list, calories back in the calorie balance). `SwipeableFoodRow` keeps swipe and long-press delete in its phone-only mode (and for a waiting entry even online), without adjust or detail; the components of a logged meal cannot be deleted from there, because that goes through the meal, which needs the server. Not queued: editing an entry (its quantity or serving), deleting a logged meal, and `−` on a drink.
- Offline day totals (#1983): `fetchDailySummary` (own day only, never a family member's) answers from the phone's copy of the server's whole summary (`daily_summary`, saved on every load and for the last `DIARY_DAYS_KEPT` days by `refreshRecentDailySummaries` in each pack refresh), so goals, adjusted goals, calorie balance and cycling are the server's, as of the last load. `loadDailySummaryRawData` then adds what is waiting to upload (`readWaitingForDay`, `applyWaitingToRawData`): the previews join `foodEntries` (so calories and macros count them), the calorie balance moves (`eaten` and `net` up, `remaining` down), and drinks add their millilitres (container volume ÷ servings from the kept `water_containers`; a container linked to a food adds nothing, since the server works that out). Nothing is counted twice once uploaded: a confirmed row is no longer waiting, and the day is reloaded. Logged meals are not collapsed while the server is away (`resolveCollapsedFoodEntries` fails and the components are listed). `DiaryScreen` reads the summary while offline (`enabled: isConnected || isOffline`) and `renderOfflineDay` shows `DiaryCalorieMacroSummary` and the food from it. While the server is unreachable and the phone holds the day, the Dashboard shows `renderOfflineDashboard`: the offline strip, the calorie ring (if on) and the water card (if on), with the container list from the kept `water_containers`, so `+` and quick-add drinks work and show at once; the water history screen is not offered. The other cards (macros, trends, fasting, sleep…) are not shown offline. With no saved copy of the day it still shows the offline message. Supplements, sleep, measurements and the other cards are not kept.
- Food library (#1983): `offline/foodLibrary.ts` (`refreshFoodLibrary`, run at the end of each pack refresh and best effort) keeps up to `FOOD_LIBRARY_MAX` (2,000) foods in the `food` collection: recent and most-used foods first, then the person's own foods by name (`foods-paginated?foodFilter=mine`), each once (`chooseFoodsToKeep`), searched by "brand name" like the server; the servings of the first `FOOD_VARIANTS_KEPT` (100) in `food_variants` (the rest answer with their default serving); the recents lists and the meal types. `fetchFoodsPage`, `fetchFood`, `fetchFoods`, `fetchFoodVariants` and `fetchMealTypes` answer from it through `withOfflineFallback`. The by-name list is answered only for `sortBy=name:asc` (the phone keeps no other order and no filters), and a food is listed by "brand name", so offline order can differ slightly from the server's name order. Never kept: other people's and public foods beyond what was recently used, favourites, external providers. `FoodSearchScreen` reads the kept foods while the server is unreachable (`canReadSavedFoods`); its favourites, meals and online sections stay off. The + menu's Log food and the Diary's add buttons already lead to it offline (only exercise entries check the connection).
- Barcode offline (#1983): the pack keeps each kept food's barcode (`food_barcode`, barcode → food id, from the foods' `barcode`; an extra barcode added in `EditBarcode` is not on the food list, so it is not kept). `lookupBarcodeV2` answers from it (`readSavedBarcodeResult`: `source: 'local'`, the kept servings) while the server is unreachable, so a scan of a food in the person's library finds it and the add screen logs it like any library food (queued if the upload fails). A barcode the phone does not know stays an error with the message "No connection. This barcode isn't in the foods saved on your phone." (`foodScan.errors.offlineBarcode`): only the server can ask the providers. Label scans and photo estimates need the server.
- Handlers by kind, registered in `handlers/index.ts`: `workout_session.create|update|delete` (`handlers/workoutSession.ts`), `workout_feedback.put` and `workout_preset.update` (`handlers/followUps.ts`; a saved-workout update is skipped with a message if the preset's `updated_at` changed meanwhile).
- A `reconnect` drain ignores the retry delay of waiting rows (the delay grows with attempts made while offline). Android reports a network failure as a plain `Error` ("fetch failed: ...UnknownHostException"), so `serverMayBeDown` also matches the message text. While the server is unreachable `useOfflineUploads` re-checks the connection every 30 s. One workout resumed and finished again has a create and an update row; `uploadsToShow` lists it once.
- Conflicts stop as `conflict`; the person chooses on the Offline screen (`conflicts.ts`: keep phone, keep server, keep both).
- Confirmed rows stay 7 days as a safety copy; unconfirmed rows are never deleted automatically. One reminder notification after 7 days waiting (`waitingReminder.ts`).
- Watch heart rate for a session that is not on the server yet waits (`sessionAwaitingServer.ts`, used by `useWatchWorkoutBridge`).

## Pictures

- `offlineImages.ts`: pictures of exercises the person kept (long-press in `ExercisesLibraryScreen`), this week's plan, then saved workouts, into the cache directory, Wi-Fi only unless `offlinePicturesOnMobileData`, capped at 300 MB. `resolveExerciseImageSource` prefers the saved copy through the synchronous `localImageIndex.ts`.

## Screens

- `OfflineSettingsScreen` (Settings → Offline): waiting uploads with Upload now and conflict choices, Refresh now, storage, the mobile-data switch, Clear offline data, kept exercises.
- Diary: the Exercise section from the phone while unreachable (the last `DIARY_DAYS_KEPT` = 7 days, saved by `refreshRecentDiaryDays` in each pack refresh through `GET /api/v2/exercise-entries/by-date`, since the server has no workout range route and `/history` lists future planned sessions first; a Diary load saves its day too, and a confirmed upload reloads the day, `notifyUploadsConfirmed`), and a "Waiting to upload" pill on waiting workouts (`useOfflineDiaryDay`).
- `ServerSettingsScreen` asks before switching away from or removing a server with uploads waiting (`leaveServerGuard.ts`).
