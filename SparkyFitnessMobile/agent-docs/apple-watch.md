# Apple Watch: details

Longer notes for the "Apple Watch" section of [`SparkyFitnessMobile/AGENTS.md`](../AGENTS.md). Each one has a one-line link there.

## Look and touch targets

- Look and touch targets on the watch: follow Apple's watchOS guidelines. Text uses system text styles (`.headline`, `.body`, `.footnote`; nothing smaller than footnote, no fixed 9–12 pt sizes) so it follows the wearer's text size; large numerals use `WatchStyle.s(_:)` sizes in the rounded design. One main action per screen, names wrap to two lines instead of truncating, and a screen shows only what its job needs. On the workout screens there is one control shape, `SquircleButton` in `WorkoutView.swift` (flat dark squircle from `WatchStyle`, 44 pt tall in a row at the 44 mm reference size, dimmed when disabled, the whole box tappable; `prominent` is the white main action). The set screen is the exercise's name (`ExerciseTitle`, up to two lines, or one line over "Superset · partner" in the superset's colour; tapping it opens the exercise list, so there is no separate list button), `SetProgressRow` ("Set 2 of 3" or "Warm-up 1 of 3" in orange, and one dot per set of the exercise: filled once logged, ringed for the current one; tapping a dot moves to that set through `WorkoutSessionStore.goToStep(setId:)`), the value cards (`ValueBox`, same fill, bold rounded numerals, a white border while selected) and the bottom row: previous set, a wide `DoneButton` (Done in white, Undo in orange once logged) and next set, the arrows crossing into the neighbouring exercise as the dots do not. Elapsed time, heart rate and calories are on the set screen by default, as one line in the clock's row (`SetScreenMetricsLine`); with Settings → Apple Watch → "Metrics on the set screen" off they move to `WorkoutMetricsPage`, the first page after the set screen, or the second when Up Next is on (always before Set options), one large reading per line as in Apple's Workout app, and that page exists only then. With the metrics line off, the heart rate is also inside the rest ring (with it on, the line already shows it). With the "Up Next page" setting on (off by default), the first swipe up is `UpNextPage`: the next exercise's name, one dot per set, its first target, and the exercise after it; a tap opens the exercise list. Under it, Swap (and Swap Exercise on the exercise options page) opens `SwapExerciseSheet`, the exercises still to come; picking one sends the `doExerciseNow` workout edit, which the phone applies with `activeWorkoutStore.doExerciseNow` (the picked exercise moves in front of the current one and becomes active), and the watch jumps to it at once. Both are shown only while the phone's context says `exerciseDoNow`, since an older phone ignores the edit. The rest screen is a countdown ring (time left and heart rate inside it) over back 15 s, skip and forward 15 s, then one "up next" line that opens the exercise list. The exercise list sheet is a `NavigationStack` titled with the workout name over flat squircle rows: name on up to two lines and sets logged over sets planned on the right, green once the exercise is done. Every size on these screens goes through `WatchStyle.s(_:)`, which scales it by the watch's screen height (0.82x to 1.1x of a 44 mm), so a 40 mm watch is not squeezed off its screen. These three settings reach the watch as `setScreenMetrics`, `upNextPage` and `largerText` in the context (absent means today's behaviour: metrics on, no Up Next, original Goals and Water). Goals and Water keep their original layout (`ClassicGoalSummaryView`, `ClassicWaterIntakeView`) unless "Larger text on the watch" is on (`largerText` in the context; `ContentView` picks the view and sets the `watchLargeText` environment value). The same switch picks the Workout page: off is `ClassicWorkoutView`, the pre-#3191 page, on is `WorkoutView` unless "Original workout page" (`classicWorkout`, shown only while larger text is on) keeps the classic page; `usesClassicWorkout` decides (Up Next, Swap and the other new pieces only exist there); the other pages the PR enlarged (Fasting, Steps, Trend, Run, Recording, water log, edit pages, effort picker, check-in entry) use `.watchFont(large, classic:)` from `WatchTextSize.swift` and return to their original text sizes while off. Medications keeps its new layout either way. The larger layouts follow the same rules: Goals is the calorie ring alone on its line with "eaten · burned" under it, then the nutrient rows; Water is the bottle beside the total and "60% of 2.5 L", then one full-width row per container and a Today's Log row; Fasting starts a preset from full-width buttons and puts End fast under the ring. Check a UI change in the simulator on the 40 mm and the largest watch (`ScreenshotSeed`; `SPARKY_SCREENSHOT_SHEET` also takes `dose`, and `SPARKY_SCREENSHOT_SHEET` takes `upnext`, `swap` and `metrics` for the workout pages, and `SPARKY_SCREENSHOT_OPTIONS` takes `nometrics`, `upnext`, `large` and `fast`). Use these, or the same frame, for new controls instead of a bare `Image(systemName:)` in a plain button. The Set options, Exercise options and Workout pages (`WorkoutEditPages.swift`) must fit one screen without scrolling, since each is one stop of the workout's vertical paging: their buttons use `EditPageButtonStyle` (fixed compact height, one line that shrinks), and text growth there is capped at xxLarge.

## Watch pages and their order

- Which watch pages show, and their swipe order, is set on the phone in Settings → Apple Watch (`WatchSettingsScreen`, listed only while `WatchConnectivity.isPaired()`; pages registered in `constants/watchPages.ts`, whose strings are the raw values of the watch's `WatchPage` enum). `useWatchCheckInBridge` sends them in the context as `pageOrder`/`hiddenPages`, the watch carries them forward, and `ContentView` builds its `TabView` from `WatchPage.visible` — unknown names dropped, missing pages appended, a hidden Workout page still shown while a workout runs, and a page that is turned off never selected (jumps to it do nothing). The app opens on the first shown page, or the workout while one runs. A newly armed workout, keyed on `plan.sessionId`, switches to the Workout page, and that page is also where the app lands when it launches or returns to the foreground while one runs. The `TabView` carries `.id(pages)` so a reorder or hide rebuilds it instead of diffing: a page-style `TabView` crashed when the page on screen moved under it. The phone will not let the last shown page be turned off. The same screen picks the rows the watch's Goals page lists under the calorie ring (any `NUTRIENT_META` nutrient except calories and the glycemic index, plus custom nutrients; protein, carbs and fat by default): `buildWatchGoalNutrients` (`utils/watchNutrients.ts`) totals each one with `dayStandardNutrient` / `dayCustomNutrient` from `utils/nutrientUtils.ts`, the same helpers `DailyNutritionDetailsScreen` uses, and sends them as the day-scoped `goalNutrients`. The watch draws `NutritionSnapshot.rows` in that order and keeps its fixed macros when a phone build sends none. Both lists render through `components/ReorderSwitchList.tsx`, which `HealthTrendsSettingsScreen` uses too. Its Set input control (`watchSetInputStyle`, sent as `setInputStyle`) picks how the workout page's weight and reps boxes are edited: a tap opens `NumericKeypadView` (the default), or, in crown mode, selects the box in place (Hevy-style) so the Digital Crown or a vertical drag moves it 0.5 lb/kg or one rep per step, with a second tap opening the keypad. The adjusted value is written to `WorkoutSessionStore` once it settles (0.5s) or when the set is logged or left, not per detent, since every write persists the workout snapshot. Selecting a value the crown cannot represent does not rewrite it. A crown or drag step from that value moves by one detent, not down to the cap, and the crown's range is rebased when it hits zero so the same edit can continue down to zero. A weight-unit change while a box is selected drops that edit instead of saving the old number in the new unit.

## Medications page

- Medications page: `WatchPage.medications` (key `medications` in `constants/watchPages.ts`, after Water) is laid out like Apple's Medications app (`MedicationsView.swift`): a `List` with a large "Medications" title and one section per time ("8:00 AM", "Any Time" for an untimed scheduled slot, "As Needed" for as-needed medications: no schedule, or a PRN schedule; empty `scheduleId`, logged as a once-a-day `prn_taken` entry). Each dose is a row with a pill icon (a leaf for a supplement: `supplement` in the dose payload, from `is_supplement`), the name on up to two lines and the dose, and a tick once taken (orange until the phone has it). A section with more than one scheduled dose still due also has Log All as Taken. Tapping a row opens `MedicationDoseView`: the dose, and big Taken and Skipped buttons, plus Clear once it is logged (a mistaken tap). `useWatchCheckInBridge` builds the day-scoped `medications` context field with `medicationsForWatch` (`utils/watchMedications.ts`) from the same queries and `entryMatchesDose` rule the phone's `MedicationsCard` uses; it is blanked by `NO_FIGURES_FOR_TODAY` across midnight, so the watch reads nil as "not synced" and `[]` as "nothing scheduled". A tap is a `medicationTaken` message (`onMedicationTaken`; `taken: false` is an un-tick that deletes the slot's taken or skipped entry; `skipped: true`, sent with `taken: false`, marks a scheduled slot skipped), acknowledged through `ackedClientIds`/`failedClientIds` like a water tap and kept in `CheckInStore.pendingMedicationTaps` until a later context settles it (`PendingMedicationTap.action`: taken, skipped or undo). Skipped is offered only while the context carries `medicationSkip: true`, which this phone build always sends: an older phone would read the `taken: false` that rides with a skip as an un-tick. The phone handles taps one at a time in arrival order; `watchMedicationWrite` decides the write from the day's entries (none, create, update or delete), reading them first, which is what makes a redelivered tap safe without a persisted dedupe set.

## Workout tracking

- Workout tracking: starting a live preset session (`useStartLiveWorkout.ts`) arms the watch with `WatchConnectivity.startWorkout(plan)` — the full exercise/set/target/rest plan, built from the just-started `activeWorkoutStore` state (`buildWatchWorkoutStartPayload`), and also calls `HKHealthStore.startWatchApp` so watchOS opens the watch app (a no-op unless the watch is worn, unlocked and has the app installed; the watch's `WatchSessionManager` is already up on launch to receive the queued plan). That plan goes out before each exercise's history has loaded, so it carries only the preset's planned values. The history (`previousSessionSets`, `prBaseline`), coaching signals and `weightUnit` that targets resolve from are otherwise captured by `ActiveWorkoutScreen`'s cards, and a workout started from the wrist never opens that screen, so `useLiveWorkoutInputsCapture` (mounted in `WatchWorkoutGate`) captures them headlessly with the same query keys and preset-scope check as the cards; without it no progression reached the watch until the phone app was opened. `useWatchSetTargetsSync` (mounted in `WatchWorkoutGate`) re-resolves every set's weight/reps with `resolveWatchSetTargets` — the same `resolveLiveAssumedSetValues` the phone's rows use, so the progression bump, ramp and adaptive adjustment reach the wrist — and sends the full list via `updateSetTargets` (`setTargets`), together with the phone's completed set ids, whenever either changes. The watch adds those completions (a set logged on the wrist may still be in flight to the phone) and drops one the phone listed earlier and has since stopped listing (`phoneConfirmedIds`: a set just logged on the wrist that the phone has not listed yet is never mistaken for an un-log). The other way, tapping the undo that replaces the tick on a logged set sends `setUncompleted` (queued; `handleSetUncompleted` in `useWatchWorkoutBridge` runs the store's `uncompleteSet`, deduped by `clientId`), and the watch holds that set out of the phone's list (`pendingUnlogs`, kept in the snapshot) until the phone stops listing it or the set is logged on the wrist again. It also moves its cursor past the set on screen when the phone logged it, starting the phone's running rest (`restEndsAt`, an epoch-ms deadline) so both countdowns end together. After that the watch's rest follows the phone's (`restState` `resting`/`paused`/`ready`, so +15s, pause and Skip reach the wrist; a paused rest freezes in `restPausedRemaining`, with the watch's Skip and ±15s disabled, until the phone resumes it), but only from an update that already lists every set logged on the wrist — one that does not predates the rest the wrist just started — and only when the phone's rest changed since the watch last took it (`lastPhoneRest`), so a ±15s pressed on the watch is not undone by an unrelated target update. The other way, Skip and ±15s pressed on the watch go to the phone as `restChanged` (the rest's deadline before and after, epoch ms), and `applyWatchRestChange` in `useWatchWorkoutBridge` applies it only while the phone's rest still ends at that before-deadline, so a duplicate or late delivery changes nothing. Each update also carries `armedAt` (`activeWorkoutStore.watchArmedAt`), and the watch applies it only to the plan armed at that time. The watch keeps the newest revision (a JS ms timestamp, parsed as `Double` because `Int` is 32-bit on arm64_32) in `WorkoutSessionStore.targetOverrides`, which sits between what the wearer typed and the plan's own targets, and holds an update that arrives before its plan until `beginPlan`. Exercises, supersets or sets added, removed or regrouped on the phone after the start reach the watch through `useWatchPlanSync`: when the plan's shape changes (and no set still has a temporary id) it resends the start payload as `updateWorkoutPlan` (`workoutPlanUpdate`, with a `revision`), and `WorkoutSessionStore.updatePlan` swaps it in without restarting, keeping logged sets, typed values, targets, the rest and the cursor (falling back to the first set still to do if its set is gone). The watch's Workout tab (`WorkoutView.swift`) is a Hevy-style set tracker (no exercise picker of its own) that starts a real `HKWorkoutSession` for background HR sampling, buzzes the wrist when its own rest countdown runs out (`WorkoutSessionStore.onRestFinished`, only while the phone's Haptics and rest-complete alert are on — `hapticsEnabled`/`restAlertsEnabled` ride in the watch context from `useWatchCheckInBridge`, carried forward when absent and read via `WatchContext.effectiveRestBuzzEnabled`; `WatchAppDelegate` hides the phone's forwarded `rest-complete` ping while a watch workout runs), reports each completed set (`setCompleted`, queued) straight back into `useActiveWorkoutStore.getState().completeSet(setId)` so rest timers/PR detection/autosave dirtying are untouched, and sends the current reading to the phone every ~3s as a `liveHeartRate` message (`sendMessage` only while reachable, never queued, display-only: `onLiveHeartRate` → `liveHeartRateStore`), buffers heart-rate batches per exercise (`heartRateBatch`, QUEUED not reachability-gated — a phone out of range mid-workout is normal, and dropping batches would lose the data the feature exists for). Samples come from a long-running `HKAnchoredObjectQuery` (`WorkoutHealthKitController.startHeartRateSeriesQuery`) — NOT a bare `HKQuantitySeriesSampleQuery`, which only enumerates samples that already exist and then completes, so started at workout begin it silently collected nothing on real hardware while the live BPM (fed separately by the builder's statistics) still looked fine; a multi-reading sample is expanded with a series query scoped to that one sample. The query has NO `HKSource.default()` filter — samples recorded during the session are attributed to the watch, not the app, so that filter matched nothing on hardware — and each builder-statistics burst (`didCollectDataOf`) is also appended to the buffer as a floor, so heart rate still reaches the diary if the sample query returns nothing (e.g. HR read access withheld); `appendSample` dedupes by instant. That dedupe set does not survive a relaunch, so the jetsam snapshot records `heartRateSentThrough` and `recoverIfNeeded` resumes the query from it (overlapping, so a multi-reading sample that straddles the mark is still read) and drops readings up to it, instead of replaying the workout from its start. A batch goes out every 60s AND at every exercise boundary (`WorkoutSessionStore.onExerciseWillChange`, fired by the store's single `moveCursor`), so each batch is tagged with the exercise its readings were measured during rather than whichever is on screen when the timer fires. Each batch also carries `activeEnergyKcal`, the active energy measured **since the previous batch** — a delta rather than a running total, so the phone sums per exercise and the parts add up to the workout's real total. A workout ends from either side and both flush the same buffer: the watch's Finish Workout (bottom of the exercise-picker sheet) sends `workoutStop`, while finishing/discarding on the phone is caught by `useWatchWorkoutBridge`'s `activeWorkoutStore` subscription, which sends `stopWorkout(sessionId)` the other way so the watch tears its `HKWorkoutSession` down too. On the phone, buffers are kept PER SESSION (`useWatchWorkoutBridge`'s `sessionsRef`, retained ~10 min after a session ends, max 3): the watch's final drain is queued and often lands after the phone has ended the workout, sometimes after the next one has started, and a single-session buffer dropped it. A 4xx from the attach route drops that entry (it will never succeed) except 401/408/429, which like network/5xx errors keep it for retry; dropped batches and rejected entries are logged. A finish on the WATCH saves and clears the phone's live session (if that save fails the session is left live, so the phone's own Finish can retry it) and calls the bridge's `onWatchFinishedWorkout`, which `App.tsx`'s `WatchWorkoutGate` uses to replace `ActiveWorkout` with `WorkoutComplete` (params from the shared `buildWorkoutCelebration`, `utils/workoutCelebration.ts`); `ActiveWorkoutScreen` also leaves itself whenever its session is cleared from outside while focused, so no external clear can strand it on "No active workout". Whichever fires first, `flushHeartRate` attaches the buffered series and summed energy per exercise entry via `POST /api/exercise-entries/:id/watch-telemetry` (`attachExerciseEntryWatchTelemetry` in `exerciseApi.ts`) — a route that only fills in avg/max HR, HR zones and `calories_burned` on an entry that already exists, distinct from the HealthKit/Health Connect/Garmin sync path that creates a new entry as part of importing a whole external session. The measured `activeEnergyKcal` REPLACES the server's duration-and-sets calorie estimate for that entry and is also stored in `active_calories`, which is what makes it survive a later edit of the workout (see the server guide's `resolveEditedCaloriesBurned`); heart rate and energy are each optional on that route (HealthKit permissions are per type) but at least one must be present.

## Workout heart rate on the phone

- Displaying it: `WorkoutCompleteScreen` (the first thing shown when a workout ends) and `WorkoutDetailScreen`'s summary row both show **Avg HR** and **Max HR** when any exercise carries one, via `summarizeWorkoutHeartRate`. `ActiveWorkoutExerciseCard` shows per-exercise heart rate in its chip row next to calories (`142 (168) bpm` — the max in parentheses only when it differs from the average). The saved figures are view-mode only: heart rate has no input anywhere, it only ever arrives from a paired watch or a synced workout. During a live workout the card's chip shows the watch's newest reading instead: `useWatchWorkoutBridge` passes the newest sample of each live-session batch to the in-memory `stores/liveHeartRateStore.ts` (the upload buffer is a ref and renders nothing), and `useLiveHeartRate(entryId)` shows it on the exercise it was measured during until it is `LIVE_HEART_RATE_MAX_AGE_MS` (150s) old. Max HR is the exact maximum of the per-exercise maxima; a missing max is omitted, not shown as a dash. **Avg HR is duration-weighted by each exercise's `duration_minutes`**, so a long block is not pulled down by a short warmup; if any contributing exercise has no positive duration it falls back to a plain mean, because a zero-weight entry would otherwise vanish from it. The phone never holds the raw sample series — the server already duration-weights those into the per-entry average. Zone breakdowns (`exercise_entry_hr_zones`, stored per exercise entry) render on `CardioSessionScreen` for one entry and on `WorkoutDetailScreen` for a whole workout: `useWorkoutHeartRateZones` fetches the zones of each exercise that has an average heart rate (a workout logged without a watch makes no requests), under the cardio screen's `cardioSessionDetailQueryKey('hrZones', id)`, and `combinedHeartRateZoneRows` sums the seconds per zone. `WorkoutCompleteScreen` still shows only avg/max, since the watch's final zones may not have been attached yet when it opens.- The watch also saves the session to Apple Health: `HKLiveWorkoutBuilder.finishWorkout()` writes a real `HKWorkout`, so a Sparky live workout shows up in Fitness and closes rings. That write has to be excluded from the INBOUND sync or the same session is filed twice — the sets are already in the diary. The exclusion is a metadata marker, not the bundle id: `isOwnRecord` compares against the phone's bundle and the watch app's is `<phone-bundle>.watchkitapp`, so a wrist-written workout looks third-party to it. `WorkoutHealthKitController.sessionMetadataKey` stamps `SparkyFitnessSessionId` onto the workout at `beginCollection`; `healthkit/index.ts` forwards that key into the record's `metadata` (the workout reader carries only the keys a transformer consumes, so it is forwarded explicitly like `HKTimeZone`), and `isOwnWatchWorkout` in `healthkit/dataTransformation.ts` drops it. The key is one literal in Swift and one in TypeScript with no way to share them — renaming either alone silently reintroduces duplicate workouts.

## Following a saved route

- Following a saved route on the watch (outdoor walk or run only; the watch's ride is the phone-GPS recording, which has no route support): `startRunOnWatch({ ..., route })` (`services/watchRunControl.ts`) takes a route from the library (`Route` from `@workspace/shared`, at most 2000 points) and sends `toWatchRoutePayload(route)` (`utils/watchRoute.ts`) as the `route` of the `runStart` request, dropped for an indoor start. Transport: it rides the existing `runStart` message (queued `transferUserInfo` plus a live `sendMessage`), not `updateApplicationContext` (the single latest-value slot reserved for the nutrition/water context, which a route would clobber and be clobbered by) and not `transferFile` (new delegate plumbing on both sides for no gain). It fits because the points are one flat integer array in millionths of a degree (`[lat, lon, …]`, ~5 bytes a number, ~20 KB at 2000 points) with no altitude; a route over the cap is re-thinned with `simplifyRoute` and its cues re-pointed. A route with no cues gets derived ones (`deriveRouteCues`: a heading change of 30 degrees or more measured over ~25 m either side, merged within 30 m, sized slight/normal/sharp/U-turn) so the watch always has directions; the library's own `text` wins over the watch's wording. On the watch `ContextPayloadMapper.route(from:)` reads it into `WatchRunStartRequest.route`, `WatchRunStore.start` keeps it as `route` (saved by `WatchRouteStorage` so a relaunch resumes following, cleared when the run ends), and each GPS fix (`WatchRunHealthKitController.onLocation`) goes to `WatchRouteTracker` (`Domain/WatchRoute.swift`, pure Swift: nearest point on the polyline searched near the last position first so a loop is followed on the right lap, progress, metres left, next cue; off-route is more than 40 m from the line for 6 s, cleared at once on return, fixes worse than 50 m ignored; a buzz 50 m before each turn, `Haptics.routeCue`/`offRoute`/`onRoute`, and spoken lines when voice cues are on). `WatchRunView` shows `RouteCueStrip` under the clock and, with a route, a second and third vertical page: `WatchRouteMapPage` (Apple Maps via MapKit's `Map`, close around the wearer and turned heading up, the covered part grey, the rest cyan, the next turn as a marker) and `WatchRouteOverviewPage` (the whole route, north up). The tiles are MapKit's own: the watch asks Apple Maps for tiles for the area on screen and nothing else; there is no tile server URL in the app, and the route and position are never sent anywhere (they are overlays drawn on the watch, so with no signal the tiles stay blank and the route still shows). `WatchRouteCamera` (`Domain/`, pure, tested in `watch-tests/` with the tracker) picks the camera: centred on the wearer, heading from the route 40 m ahead (north up when off the route, arrived or with no fix), pulled back from 450 m to at most 1000 m so the next turn stays in the top half, and `isWorthMoving` drops a new camera unless it moved 8 m, turned 10 degrees or zoomed 50 m, so a 1 Hz fix does not restart a MapKit animation each second. `WatchRunView` gives each page a selection tag and the maps are built only while their page is selected and the screen is not dimmed (a vertical-page `TabView` keeps its neighbours alive); points of interest and the compass badge are off. No extra GPS: the position is the run's own. The tracker's tests are XCTest in `watch-tests/` (a SwiftPM package symlinking `WatchRoute.swift`; run `swift test` there on a Mac) because the watch target has no test target and everything under `targets/watch/` is compiled into the app. The TypeScript half is tested in `__tests__/utils/watchRoute.test.ts` and `__tests__/services/watchRunControl.test.ts`.

## Workout effort

- Workout effort (1-10, `exercise_entries.workout_effort`): when a strength workout or a wrist-only run ends on the watch, the summary offers `WorkoutEffortPicker` ("How hard was that?"): the set screen's `ValueBox` card starting at 5, with Apple Health's band (Easy 1-3, Moderate 4-6, Hard 7-8, All Out 9-10) as the line under the number. As on the set screen the card must be tapped before the crown adjusts it (`.focusable(selected)`; until then the crown scrolls the page), and tapping it again hands the crown back. The rating goes three places. (1) Apple Health, as `workoutEffortScore` related to the saved `HKWorkout` through `WorkoutEffort` (`Infrastructure/WorkoutEffort.swift`, watchOS 11+; older watches skip the Health write and the type is only requested for write access on 11+); `WorkoutHealthKitController` and `WatchRunHealthKitController` keep the `HKWorkout` that `finishWorkout` returned for it. (2) The phone, as a queued message (same four-place rename rule): `runEffort` `{clientId, rating}` for a run and `workoutEffort` `{sessionId, rating}` for a strength workout (`OutboundPayloads`, `WatchSessionManager.sendRunEffort` / `rateWorkoutEffort`; module events `onRunEffort` / `onWorkoutEffort`). (3) The server, by the phone calling `setExerciseEntryEffort` (`POST /api/exercise-entries/:id/effort`, which also rates the other entries of a strength session). A run is handled in `services/watchRunQueue.ts`: it keeps `{rating, entryId, program}` per run under `@SparkyFitness/watchRunEffort` (the entry once the run is filed, the program once it is ticked off), so a rating that arrives before the run is filed waits, and it also rates the program workout (`rateProgramWorkout`, in place of the Diary's `RunEffortPrompt`, which stays as the fallback). A strength rating is handled in `useWatchWorkoutBridge` (`settleEfforts`): it waits in memory until the phone has ended the session and then uses any entry id the session's telemetry or attribution knows; an app that is not running when it arrives loses it (nothing stores it natively, unlike `runFinished`). Apple's own rating is read on sync by `services/healthkit/workoutEffort.ts`: `filter: { workout }` cannot see it (it matches samples saved with the workout, and a rating is related afterwards), so `handleWorkout` reads the `WorkoutEffortScore` samples for the whole window in one query and `matchWorkoutEffort` pairs them to workouts by start and end (5 s tolerance, newest wins), setting `telemetry.workout_effort`; Apple's automatic estimate is never read. The type is in `WORKOUT_TELEMETRY_READ_IDENTIFIERS` (iOS asks for an enabled type it never asked about without the Android permission version; the library skips an identifier the OS does not know, so iOS 17 and older just never see it). Shown by `summarizeWorkoutEffort` on `WorkoutDetailScreen`, and as `workout_effort` / `workoutEffort` on `ActivityDetailScreen` and `CardioSessionScreen`. Phone-only cardio has no `HKWorkout`, so it has no Apple rating and keeps the run summary's program rating row. The watch Swift has not been compiled outside Xcode.
