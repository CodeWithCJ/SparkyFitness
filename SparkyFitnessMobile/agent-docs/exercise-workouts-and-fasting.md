# Exercise, Workouts, And Fasting: details

Longer notes for the "Exercise, Workouts, And Fasting" section of [`SparkyFitnessMobile/AGENTS.md`](../AGENTS.md). Each one has a one-line link there.

## Training load card

- `TrainingLoadCard` (#250) sits above the consistency card (section key `exercise.load`): `useTrainingLoad` reads `GET /api/reports/training-load` (fixed 28 days ending today, refreshed on focus). The server (`reportService.getTrainingLoad`) takes every logged workout, cardio and strength alike, and the shared pure `computeTrainingLoad` (`shared/src/utils/trainingLoad.ts`) turns them into four 7-day loads, acute (last 7 days) against chronic (4-week average), a status (`noData`, `learning` under 21 days of history, `low` under 0.8, `steady` to 1.3, `high` to 1.5, `spike` above) and a rest nudge (`takeRest` after a high/spike week with a session today or yesterday, `ready` after a low week with 2+ rest days). A session's load is minutes times an Edwards zone weight (1 to 5) from average heart rate against the person's heart rate zones (the server resolves them from their own max heart rate, else Nes from their date of birth, else 190; see [Heart rate zones](quick-routing.md#heart-rate-zones)); a session with no heart rate counts at weight 2, so a strength workout with no watch still counts by its time. `RunProgramBanner` reads the same hook: after a `spike` it offers the same one-tap ease as the break offer (`suggestFromLoad` in `shared/src/utils/runProgramLoad.ts`: -15% on the next two workouts, not offered within 72 h of a plan change, and the break offer wins when both apply). The Dashboard has a short version, `TrainingLoadDashboardCard` (card key `trainingLoad`, preference `trainingLoadCardVisible`, shown after Exercise Progress by default and switchable in Dashboard Settings): this week's load against the usual, a one-line verdict, any rest nudge and the four weekly bars, from the same `useTrainingLoad` (its `enabled` argument keeps a hidden card from requesting). It renders nothing until a workout has been logged, and a tap opens Exercise Statistics. When `useFitnessFatigue` has a readiness score the card adds a one-line `Readiness 78 · ready for a hard session` row under the verdict (no separate card key or preference).

## Strength / Cardio switch and cardio sessions

- Its Strength / Cardio switch leaves the range alone. Cardio lists sessions from `GET /api/exercise-stats/query` (`useCardioSessions`, an infinite query; the server leaves strength out when no category is sent), grouped by month and led by `cardioSessionHeadline` from shared, the rule the web list uses. A tap opens `CardioSessionScreen`: the route from `/api/generic-health/workout-gps/:id` (`RouteMap`: renders via `RouteTileMap` on mobile platforms where `canShowRouteMap()` is true, otherwise falling back to the plain SVG `RouteLine` on unsupported platforms), a Pace card (`PaceChart`, fed by `paceSeriesFromTrack` in `utils/cardioSession.ts`: pace over each stretch of at least 30 s between trackpoints against distance in the display unit, using the points' own `dist` when present, dropping standing-still stretches slower than an hour per unit, drawn on negated pace so faster is higher; hidden when fewer than two readings), heart rate from the trackpoints or else the day's stored samples through shared `buildWorkoutHeartRateSeries` (indoor sessions still get a graph), and time in each zone from `/api/generic-health/workout-hr-zones/:id`. The stat tiles come from the `/api/exercise-stats/query` item, which also carries `floorsClimbed` and `elevationGainMeters` (null, never 0, when the source did not measure them) so a stair stepper shows floors and elevation (feet with the miles setting); the HealthKit reader takes floors from the workout's `FlightsClimbed` statistic when the sample's own `totalFlightsClimbed` is empty, as it is for a GymKit workout. Garmin's raw provider blob, which the web still falls back to for old activities, is not read. The Route card has an **Export GPX** button (`shareRouteAsGpx` in `services/gpxExport.ts`: `buildGpx` in `utils/gpx.ts` writes a GPX 1.1 track with elevation, time and Garmin heart-rate/cadence extensions, points in time order, unusable points dropped; the file goes to the cache folder and the system share sheet, so it can reach Files, Strava or Garmin Connect; a cancelled sheet is not an error). From the diary, a synced cardio workout opens it, and so does a run, walk or ride logged in the app (a GPS recording or watch run is an in-app entry) when it has a distance or heart rate; for those it gets a `diaryEntry` param and an Edit button that replaces it with `ActivityDetail`, the in-app editor. `useTrendRangeBounds` keeps both queries' ranges current across midnight.

## GPS activity recording

- GPS activity recording (#125): `RecordActivityScreen` (root-stack `RecordActivity`, opened from `AddSheet`'s Record Activity row) records a walk, run or ride. `services/gpsRecordingService.ts` owns the session: an `expo-location` task registered at module scope (`index.js` imports it, so a location fix can wake a killed app) feeds fixes through `acceptFix` in `utils/gpsRecording.ts` (accuracy, impossible-speed, out-of-order and standing-still filtering) and writes accepted points to AsyncStorage in 100-point chunks as they arrive, so a killed app or a dropped connection loses nothing; `hydrate()` restores them, and the screen reads live state through `useGpsRecording()`. The screen offers Discard (with a confirmation) while recording or paused as well as when finished. Leaving the screen does not hide a recording: while no strength workout is active, `ActiveWorkoutBar` shows it above the dock (`useRecordingBarContent`: clock, distance and pace, discard on the left, pause/resume on the right, a check that opens the screen when finished; the bar is hidden on `RecordActivity` itself and `useActiveWorkoutBarPadding` reserves room through the cheap `useHasGpsRecording`). Indoor sessions (`session.indoor`, chosen with the Outdoor/Indoor control before Start) skip the location permission and the task entirely: `startRecording({ indoor: true })` never touches `expo-location`, pause and resume only flip the status, the Auto-pause switch is hidden and sent off (there are no fixes for it to judge by), and the screen shows the clock (plus watch heart rate) with no map or pace. On Finish the screen asks for an optional distance typed in the user's distance unit, and `saveRecordedActivity(session, points, unit, indoorDistanceKm)` logs it with no track upload under `Indoor Walking`/`Indoor Running`/`Indoor Cycling` (never `Treadmill Walk`: shared `activitySport` reads `treadmill` as running, so a walk would match two sports and fall back to `other`). On iPhone and Android the distance field is prefilled from the step counter: `useIndoorDistanceEstimate` calls `services/stepDistance.estimateIndoorDistance`, which reads the steps over the session window from the system pedometer (`services/stepCounter`; iOS queries the window after Finish and asks for Motion & Fitness the first time; Android stores the hardware counter at Start in `stepCounterAtStart` via `modules/step-counter` and subtracts it at Finish, so the app can be killed in between, and asks for Activity recognition at the start of an indoor walk or run only), scales them by the moving share of the window because pauses are only a total, and multiplies by the learned stride (`services/strideCalibration`, AsyncStorage on this device only, walk and run kept apart, blended with `utils/stride.blendStride`) or a typical default. The screen says whether the stride is learned or typical. A distance the person changes teaches the stride (`learnFromIndoorEntry`; an accepted estimate teaches nothing), and a saved outdoor walk or run teaches it from its GPS distance when Motion & Fitness is already allowed (`learnFromOutdoorRecording`, which never prompts). Both run once, with the entry's first save, and never fail it. The same step count gives running form: `saveRecordedActivity` calls `measureForm` before creating the entry (`measureOutdoorForm` for a GPS recording, which never prompts; the indoor estimate's steps for an indoor session) and sends `avg_cadence` (steps per minute over moving time) and `stride_length_cm` (distance over steps; left off for implausible values) with `createExerciseEntry`; it is best effort and a failure just leaves the fields off, and a recording that paused gets neither, since the step window has no pause boundaries to isolate moving-time steps. Power is not recorded. `/api/exercise-stats/query` returns them as `avgCadence` and `strideLengthCm`, and `CardioSessionScreen` shows them as Avg cadence (spm) and Stride length (metres, or feet with the miles setting). The prompt text is `motionUsagePermission` in `app.config.ts`, so changing it needs a prebuild. Whether the distance was entered or estimated is not stored on the entry (that needs a server field), and indoor sessions are not yet kept out of personal records. The watch still shows distance 0 and pace `—` for an indoor session and starts its HealthKit session as outdoor; nothing in the recording payload says indoor yet. `RecordActivityScreen` shows a spinner until that `hydrate()` resolves (so Start never flashes before a restored recording appears) and, for a live recording the screen did not start itself, a notice with its start time and a Discard button. Pause only flips the session status: the task keeps running and `ingestFixes` drops its fixes, because starting a location task again cannot be done from the background (iOS ignores a while-using start made out of sight, Android 12+ refuses the foreground service), which a resume sent from the watch with the phone locked would need. Resume restarts the task only if the OS dropped it. Auto-pause (`utils/autoPause.ts`, pure `stepAutoPause`) runs inside `ingestFixes` on the raw fixes before `acceptFix`, because standing-still jitter is filtered out of the track: stopped below a per-activity speed for 6 to 10 s pauses the session with `pausedAt` set to when the person stopped and `autoPaused: true`; moving above a higher speed for 2 to 3 s resumes it with a new `seg`, the pause counted up to when movement began. The location task drops the distance filter (`distanceInterval: 0`) only while auto-pause is on, because iOS delivers no fixes to a person standing still when one is set and the detector, which only advances on arriving fixes, would never reach its stop time; with auto-pause off it keeps the 2 m filter. A fix with no Doppler speed (iOS reports -1, common while standing still) falls back to speed from position, measured from the oldest fix in a 5 to 15 s trail and less the larger accuracy radius, so a phone drifting a few metres while its owner stands still reads as stopped; at Finish the app log gets one line counting the fixes auto-pause saw with a speed, without one and too inaccurate. Fixes with accuracy worse than 30 m are ignored, a manual pause is never auto-resumed (only `autoPaused` sessions are watched), and the toggle is `session.autoPause` set from the Record screen's switch (preference in AsyncStorage, on by default). While a recording runs, the screen shows compact Auto-pause and Voice cues switches for that session only (the preferences stay as they are): `setRecordingAutoPause(enabled, notification)` resets the detector, starts the running location task again with the matching distance filter (0 on, 2 m off; a failure is logged and the setting kept) and, when turned off while it holds the session auto-paused, resumes it (an indoor session stays off), and `setRecordingAudioCues(unit | undefined)` counts the splits already completed as said, so none is announced late. Start countdown: `RecordActivityScreen` holds `countdownLeft` (preference `countdownSeconds` from `COUNTDOWN_CHOICES`, off by default, stored beside the other recording preferences); Start with a countdown arms it, each second fires a selection haptic and (voice cues on) speaks the number, and at zero it calls `startRecording`. Nothing is recorded or requested until then, so the first-run location prompt follows the countdown, and Cancel leaves no session. Laps: the Lap button calls `markLap()` (recording only; presses within 3 s of the last are ignored) which stores epoch-ms marks in `session.laps`; `computeLaps(points, marks)` in `utils/gpsRecording.ts` turns them into splits (interpolating distance and active time at each mark, a mark inside a pause taking the fix before it, the stretch after the last mark `partial`), the finished view lists them above the splits, and `saveRecordedActivity` uploads them as the entry's lap windows instead of the automatic splits when any exist. `splitBars` draws the per-split pace bars and picks the fastest (never a partial). Intervals: `utils/intervals.ts` is the pure side (`IntervalPlan` = a style, `runWalk` or `fastEasy`, and timed `warmup`/`work`/`recovery`/`cooldown` steps; `buildIntervalPlan` clamps and builds one from options, `INTERVAL_PRESETS` are the built-in plans, `intervalPosition(plan, activeSeconds)` says where a plan stands). `startRecording({ intervals })` stores it as `session.intervals = { plan, cued }` (`cued` is the last step started, so a restored session never repeats one); `advanceIntervals` runs after each batch of fixes in `ingestFixes` and from `tickIntervals()` (the screen calls it every second while open), against `elapsedSeconds`, so paused time never counts. A new step buzzes (`fireImpactHaptic`), is spoken when voice cues are on (`intervalCue`; the first step replaces the "Recording started" cue) and is marked as a lap at its exact start (`session.laps`, deduped against the 3 s gap), so the saved activity is cut into the work and recovery stretches by the existing lap path; steps passed in one go are all marked but only the latest is spoken. UI: `components/recording/IntervalSetup.tsx` (picker plus custom steppers; the screen owns the choice) and `IntervalCard.tsx` (live step). On a phone recording the watch is told the step (`intervalIndex/Label/Remaining/Next` in `WatchRecordingStatePayload`; `useWatchRecordingBridge` re-sends durably when the step changes, `RecordingStore` buzzes via `Haptics.step()`); watch-only recordings follow no plan. Programs: `utils/runPrograms.ts` is a list of workouts, each an `IntervalPlan` (`RUN_PROGRAMS`: `walkFit` (8 weeks of brisk walking, `activity: 'walk'` so Record starts a walk and "Count it" matches a walk; `programActivity(id)` gives it), `walk10k` (10 weeks of brisk walking to a 10K walk, also `activity: 'walk'`), `returnToRunning` (4), `gentle5k` (12), `beginner5k` (9 weeks of run/walk), `fiveToTenK` (8), `zone2Base` (10 weeks of easy runs held to the person's Zone 2 heart rate: a `runWalk` plan of `zone2`-effort steps, a long run up to 70 minutes, a lighter fourth and eighth week, four strides after the first run in weeks 6, 7 and 9, and a zone check, the middle run of weeks 4, 8 and 10, flagged by `isZoneCheckWorkout` and noted by `ZoneCheckNote` on the program card and the Diary card), `faster5k` (6, speed work in `fastEasy` style), `beginner10k` (12), `faster10k` (8, speed work), `tenKToHalf` (10), `halfMarathon` (12), `fasterHalf` (10, speed work), `beginnerMarathon` (18), `marathon` (16) and `advancedMarathon` (16, five runs a week, speed work). `zone2Base`, `tenKToHalf`, `halfMarathon`, `fasterHalf` and `beginnerMarathon` also have a four-runs-a-week twin (`<id>4`, `variantOf` set); `PICKER_PROGRAMS` is the list the picker shows, and `RunProgramsScreen` puts a `SegmentedControl` on those cards (`programVersions(id)`) to choose 3 or 4 runs, starting the chosen id. A variant needs its own name, description and structure strings; the faster plans use `stridesRun`, `hills`, `tempo` and `marathonPaceLong` in `runPrograms.ts` for strides, hill repeats, tempo runs and marathon-pace blocks, built from run/walk pieces between a warm-up and cool-down; the longer ones are continuous runs timed in minutes, so a plan step may be up to 4 hours (`MAX_PROGRAM_STEP_SECONDS`); `RunProgramCard` shows a picker, and switching a running program to another one asks first and restarts at week 1), with `programStatus`/`advanceProgress` over a `ProgramProgress` (`next` = index of the workout due). `services/runProgramService.ts` is the server-backed side (`services/api/runProgramApi.ts` over `/api/v2/run-program`, a `run_programs` row per user holding the person's own copy of the workouts, the place `next_index`, the `enabled` flag and a change log; the React Query copy under `runProgramQueryKey` is set from each response, and `useRunProgram` re-reads on every mount because the AI assistant may have changed it): `setProgramEnabled`, `restartProgram`, `skipProgramWorkout`, `setProgramPosition`, `completeProgramWorkout`. The status is built with shared `storedProgramStatus`, so adjusted workouts reach the card, the picker and the recording. `RunProgramsScreen` wraps each change in `change`, which toasts a failure (offline); a failed tick-off after a save is logged, not shown, since the activity itself is saved. Programs are opt-in: `ProgramProgress.enabled` is the Record card's switch (absent in older data means on), the card always shows the stored place, but `getProgramStatus()` and the screen's `programStatus` are null while it is off, so nothing is preselected, nothing is ticked off and the Diary shows nothing; turning it off keeps the place. Setup and management live on `RunProgramsScreen` (root-stack `RunPrograms`, from a Library row; with no program it lists the sixteen `PICKER_PROGRAMS` with Start program (which asks Start today / Pick a date, then calls `startProgram(id, startDay)`; null = today), with one it shows `RunProgramCard`: switch, today's workout, Skip, Start over, workout picker, run days and start day); a collapsible `RunProgramGuide` ("How the plans work": what a workout is made of, effort by the talk test and a 1-10 scale rather than pace, and a brisk walking pace of about 5 to 6 km/h; `programStructure` describes each program's weeks and also shows on each program card; `programRest` adds a per-program "Rest days" section, e.g. no back-to-back workouts for the beginner plans) sits on that screen in both states; the Record screen only has the slim `RunProgramSelect` (today's workout, with a Manage link), and the Diary shows `RunProgramBanner` through `ExerciseSummary`'s `programBanner` prop, styled like a scheduled workout plan: `programRunForDate` (shared `utils/runProgramSchedule.ts`) decides what a Diary day shows: with run days chosen it follows the calendar `projectRuns` lays out from the next workout due (one workout per chosen weekday starting today, the first day or tomorrow once today's is done, so a missed run moves everything after it along and nothing is ever skipped), so today shows the workout due ("Scheduled Today") and later days show what is coming ("Scheduled", no Start button); with none chosen it offers the next workout today only ("Up next"); nothing before the first day, after the goal day, once a workout was done today (`doneDay`), or when the program is off or finished. Saving a recording replaces `RecordActivity` with `RunSummary` (`RunSummaryScreen`): `handleSave` builds `RunSummaryParams` with `buildRunSummary` (`utils/runSummary.ts`: figures, a route thinned to 250 points, per-unit splits, the person's laps, average heart rate from `getHeartRateSamples`; plain data, since the recording is cleared right after) and, for a program workout, `nextProgramLine` (`utils/runProgramSummary.ts`: the next workout and the day `projectRuns` puts it on, read from the program the server now holds) with the place in the program. The screen shows the stat cards, the route (`RouteMap`), the program progress with a "How hard was that?" row (1 to 10, shown when `programSummary` returned `rate`, i.e. the workout was ticked off: `rateProgramWorkout` saves it to the server's `effort_log` through `POST /api/v2/run-program/effort`; 8 or more offers "Repeat this workout" = `setProgramPosition(index)`, 3 or less offers "Skip the next workout" = `index + 2` unless that is the last, and shared `suggestFromEffort` adds a note after two hard or two easy in a row; nothing changes unless a button is tapped) and a View program link, and the splits or laps through the shared `SplitRow`/`Stat` (`components/recording/SplitRow.tsx`, also used by the Record screen); Done goes back. A wrist-only run has no summary screen. `RunProgramBanner` also offers "Count it" when `findLoggedRun` (`utils/loggedRun.ts`: a non-preset entry named like a run, at least half the planned length or 10 minutes) is among today's entries, completing the due workout on the person's say-so (a run recorded some other way, such as the watch or an import). Every tick-off passes the diary entry it was done as (`completeProgramWorkout`'s `entryId`: the saved recording, or the counted run), which the server keeps in `completion_log`; `ProgramWorkoutBadge` (`useProgramWorkoutForEntry`, shared lookup `programWorkoutForEntry` in `utils/runProgramSummary.ts`) then shows "Part of your training program" with the workout label on `CardioSessionScreen` and `ActivityDetailScreen`. `RunGoalsCard` tops that screen with the running goals (`useRunGoals`, `services/api/runGoalsApi.ts` over `/api/v2/run-goals`, query key `runGoalsQueryKey`, re-read on focus because a run saved elsewhere changes the week): a weekly distance target with this week's progress and a race with a day countdown, both optional and independent of the program; the card edits in place and converts between the display unit and the km the server stores, and Remove race clears the name, distance and day together (the server refuses a name or distance without a day). `RunProgramCalendar` on the screen lists the dates, the finish day (`projectedFinishDay`) and whether it fits before the goal day. The Record screen never chooses the workout for the person: it is offered on `RunProgramSelect` and in the `IntervalSetup` picker (`programLabel`), and chosen as the interval choice `'program'` only when the screen is opened with the `programWorkout` route param (the Diary card's Start and the program screen's Start today's workout), so a plain walk or run starts with no plan. For a walk or ride, `IntervalSetup` (given `activity`) leaves out the run/walk presets and style, the Record screen drops a run/walk preset when the activity changes, and `intervalPlan` turns a `runWalk` plan into `fastEasy`, so the card, spoken cues and watch steps say Fast and Easy rather than Run. While a recording exists the screen's header names it (`recordingTitle`: "Outdoor run", "Indoor walk", "Outdoor ride"), and outdoors `GpsSignalBadge` shows bars from the newest fix's accuracy (`useLatestGpsFix`, its own listener set in `gpsRecordingService` so the bars do not re-render the screen; `gpsSignalLevel` in `utils/gpsRecording.ts`, the watch's thresholds). The watch-run live screen is titled "Run on your watch" or "Walk on your watch". `startRecording({ program })` stores `session.program = { id, index }`, and `handleSave` calls `completeProgramWorkout` only when `planCompleted(session)`, so a run cut short is offered again. `setProgramPosition(index)` lets the person jump to any workout (the card's "Choose a different workout" picker lists the weeks, finished runs ticked), clamped to the program. Schedule: the weekdays the workout shows in the Diary (`run_days`, 0 = Sunday, empty = every day), the first day it shows (`start_date`, null = from today), the goal day (`end_date`, null = none; nothing is scheduled after it and the screen says whether the program fits before it) and the last local day a workout was completed (`last_done_date`, sent as `day` by `completeProgramWorkout`) are columns on the same `run_programs` row, like a workout plan's schedule, so they follow the person between devices; `useRunProgram` returns them as `schedule` and `doneDay`, `setProgramSchedule` writes them, and `RunProgramCard` edits them (day chips; a start date picked from a calendar, today unless one is set). Switching programs keeps the schedule. There are no run notifications; `cancelLegacyRunReminders` (`services/legacyRunReminders.ts`, run at startup) cancels weekly reminders an earlier build scheduled and deletes their stored key. An indoor session has no location task, so the plan moves on while the record screen is open and catches up when it is opened again. Voice cues (`session.audioCues` = `'km'`/`'miles'`, off by default, set from the Record screen's switch via `getRecordingPreferences`/`setRecordingPreference`): `ingestFixes` calls `cueSplit` after new points, which runs `computeSplits` and speaks only the latest newly completed full split (`session.cuedSplits` is persisted so a restore never repeats one); start, manual pause/resume, auto-pause/resume and finish speak through `services/recordingCues.ts` (`Speech.speak` with `useApplicationAudioSession`, each cue replacing the one before; it reuses `beginCueDucking`/`endCueDucking`, so ducking follows `duckMusicDuringCues`). The voice is `resolveSpeechVoice` (`services/speechVoice.ts`), shared with guided workouts: the installed voices are read ahead (`loadSpeechVoices`, called by `beginRecordingCues` and `speakGuided`), then it returns the person's pick (`guidedVoiceId`, one device-local setting for both) while still installed, otherwise the best Premium/Enhanced voice for the app language (`bestVoiceId` in `utils/speechVoices.ts`), otherwise undefined (system default, and also until the voices have loaded, so a stale id never reaches `expo-speech`, which throws on an unknown iOS identifier). `expo-speech` reports an iOS Premium voice as "Default" (it only maps `.enhanced`), so `voiceTier` also reads `.premium.` / `.enhanced.` from Apple's identifier and drops `com.apple.speech.synthesis.voice.*` novelty voices; Siri voices are not exposed to apps. The picker is `useSpeechVoiceChoices`, rendered by `RecordingVoiceCard` (Record screen, while voice cues are on) and `GuidedWorkoutSettingsSection`. The words come from `utils/recordingCues.ts` with an injected `t` (durations are spelled out, since a speech engine reads "5:24" as a time of day). The audio session is `startRecordingCueSession()` in `sounds.ts` (silent-switch override plus iOS `shouldPlayInBackground`): the location task already keeps the app running on iOS, so no keep-alive track is used. Each resume starts a new `seg`, so the jump across a pause is never distance or time. The first fix of a stretch (the start, or after a resume) must be within `STRETCH_START_MAX_ACCURACY_M` (25 m), tighter than the 50 m cutoff for the rest, so a cold-start fix does not put a spike at the head of the route. Coaching audio (#250): on top of splits and plan steps, `advanceCoaching` (next to `advanceIntervals`, from each fix batch and `tickIntervals`) speaks the cues `nextCoachingCues` (`utils/coachingCues.ts`, pure) says are due, only with voice cues on and at most one a tick (the rest are marked said): "three, two, one" in the last three seconds of such a step (one utterance, `stepCountdownCue`; it makes the ten-second warning of that step stale, so both are marked said together) after a ten-second warning before a step of 30 s or more that names the next step, a halfway call and a last-minute call for plan workouts of 5 and 3 minutes or more, a milestone word when the recorded distance passes 5K, 10K, a half marathon or a marathon (`RACE_MILESTONES_METERS`, outdoors only, whatever the unit; the furthest one after a gap), and a spoken check-in (time, distance and average pace; time only indoors) every `session.checkInMinutes` (the `CHECK_IN_CHOICES` 0, 5, 10 or 15, set in `CheckInCard` before Start, changed mid-run with `setRecordingCheckIn`, remembered as a preference). `session.coaching` holds what was said so a restore never repeats it (a state saved before the countdown and milestones existed is read with their defaults). A split announced at the same fix is spoken first, in the same breath as the coaching cue (`advanceCoaching(now, splitText)`), because a second utterance replaces the first; the countdown alone skips that, as it is for this second only. A program workout adds two sentences (`programSpokenCues` in `utils/programCues.ts`, already in the app language): `start` ("Week 2, run 3. 25 minutes.", plus "Eased for today." when its running time is 10% or more under the original) spoken in the same breath as the first step, and `done` ("Workout 4 of 27 done. Next up, Week 2, run 4.", or "Program complete. Well done.") added to the finish cue once every step of the plan has run for its full unpaused duration (a run stopped early gets none). The phone service reads them from `session.program`/`session.intervals`; the watch gets them as `startText`/`doneText` on the plan (`buildWatchRunPlans`, `buildWatchStartPlan`) and speaks them as they are. Splits also say how much faster or slower they were than the split before when it differs by 5 s or more (`splitTrendNote`). A watch run speaks the same cues: `Domain/WatchCoaching.swift` is the Swift port of `nextCoachingCues` (constants and cue order must stay in step), `WatchRunStore.cueCoachingIfDue` runs on its 1 s timer (which now also runs for a run with a check-in interval but no plan, and for any outdoor run, for the milestones) and speaks through `WatchRunCues` (`stepCountdownText` (spoken with `interrupt`), `milestoneText`, `stepWarningText`, `halfwayText`, `lastMinuteText`, `checkInText`, localized like the other watch cues; check-ins give only the time indoors). The interval comes from `runStart` (`checkInMinutes`, sent with voice cues on) or, for a run begun on the wrist, the context's `runCheckInMinutes`; it lives in `WatchRunSettings.checkInMinutes` (optional, so older snapshots decode), and after a relaunch `WatchCoachingState.resumed` counts what has passed as said. Only while-using permission is requested: iOS keeps recording through `UIBackgroundModes: location` set in `app.config.ts`, Android through the plugin's foreground service, so `ACCESS_BACKGROUND_LOCATION` stays off (Google Play reviews it closely). `utils/gpsRecording.ts` is the pure maths (distance, pace, smoothed elevation gain/loss, per-km/mile splits); `services/gpsRecordingSave.ts` finds or creates the Walking/Running/Cycling cardio exercise, creates a normal entry with `createExerciseEntry` (no `calories_burned`, so the server estimates it), then posts the route and split windows to `POST /api/exercise-entries/:id/gps-track` (`attachExerciseEntryGpsTrack`). It does NOT go through `/api/health-data`, whose per-source delete-then-insert would wipe other recorded activities on the same day. The entry id is kept on the session, so a failed track upload retries without logging the activity twice, and the server replaces an existing track on re-post. The live map reuses `RouteMap`, rendering a real map surface on iOS and Android (via MapLibre on keyless Android). Changing the recorder's permissions, background modes or foreground-service options needs `npx expo prebuild --clean` and an outdoor check on a real iPhone and Android phone. Apple Watch tie-in (phone GPS + watch): the phone still records; `hooks/useWatchRecordingBridge.ts` (mounted in `WatchWorkoutGate`, gated on `WatchConnectivity.isSupported()`) sends the session to the watch as `recordingState` through `updateRecordingState` (`sendMessage` when reachable, plus `transferUserInfo` for status changes only, never application context, which belongs to the check-in data; `sentAt` lets the watch drop an out-of-order queued copy; a `status: 'ended'` message tells the watch the recording was saved or discarded, with `discarded` true when the session left the store without a `savedEntryId`), refreshes distance and pace every 3s while recording, and applies the watch's `recordingControl` (`pause`/`resume`/`finish`/`lap`) to `gpsRecordingService` for the live session id only. A `lap` carries `at`, when the wearer pressed it (controls ride the queued transport and can arrive late); `markLap(at)` stores that time (a future or pre-recording time counts as now, a press within 3 s of an existing mark is dropped as a re-delivery, marks are kept sorted), and the state sent to the watch carries `lapCount` for the page's "Lap N" line. Heart-rate batches arrive as `recordingHeartRate` (`onRecordingHeartRate`, deduped by `clientId`), go to `addHeartRateSamples` (persisted beside the session, still accepted after Finish because the last batch is queued and lands late, cleared by `discardRecording`), and `gpsRecordingSave` posts them to the existing `watch-telemetry` route after the route upload (best effort: a failure is logged and never blocks the save; fewer than two readings are skipped). The current reading is also shown live: the watch puts the newest one beside the status on `RecordingView` (`RecordingStore.liveHeartRate`, cleared after 15 s without a new reading or when the recording stops being live) and sends it to the phone as the same live-only `liveHeartRate` message the strength workout uses, with the recording's id as `sessionId` and an empty `exerciseEntryId` (`WatchSessionManager.sendRecordingLiveHeartRate`, at most every 3 s and only while the phone is reachable; never queued). `useWatchRecordingBridge` takes it for the live session into `liveHeartRateStore`, and `RecordActivityScreen` shows a Heart rate tile through `useRecordingHeartRate` (hidden once the reading is 15 s old, so a watch that goes quiet does not leave a stale number). No new message type, so nothing to rename in four places. On the watch, `RecordingStore` mirrors the state and `RecordingView` shows it on the Workout page (`WorkoutView`, after a strength workout and before the idle picker; `ContentView` keeps the Workout page showing and lands on it while `RecordingStore.isActive`, as for a strength workout; the old `WatchPage.recording` page is no longer put in the list); `RecordingHealthKitController` runs an `HKWorkoutSession` for heart-rate sampling only (skipped while a strength workout owns the session) and stamps `SparkyFitnessSessionId` so the saved HKWorkout is not imported back. It writes nothing to Apple Health until the phone decides: on Finish the collection stops but the workout is held (`Outcome.hold`, `heldFor`), and the phone's `ended` message then finishes it (`resolveHeld(save: true)`) or discards it, so a discarded recording never reaches Health (a workout already written cannot be reliably removed: deleting the `HKWorkout` leaves attached samples). An older phone build that sends no `discarded` is treated as saved, and a watch app that is relaunched before the phone decides loses the held workout (the diary entry is unaffected). Message type and key strings (`recordingState`, `recordingControl`, `recordingHeartRate`) are duplicated in `index.ts`, `WatchConnectivityModule.swift`, `ContextPayloadMapper`/`OutboundPayloads` and `WatchSessionManager.route`; rename all or none. The watch Swift has not been compiled outside Xcode; verify on a real watch after `npx expo prebuild --clean`.

- Watch-only walk/run: started from the Workout page's picker (`WaitingForWorkoutView`), which shows a **Cardio** row above the saved presets whenever `WatchRunStore.canStart`; it opens `CardioChoicesView` (a sheet titled Cardio: Run and Walk tiles side by side under Outdoor and Indoor, then any plans, each opening `PlanPlaceView` to pick outdoor or indoor). Outdoors the controller also runs a `CLLocationManager` (the watch target's Info.plist carries `NSLocationWhenInUseUsageDescription`, written by `expo-target.config.js`) and feeds accurate-enough fixes (horizontal accuracy 0 to 50 m, and only while not paused) to an `HKWorkoutRouteBuilder`, whose route is attached to the workout with `finishRoute(with:)` once `finishWorkout` returns it (and discarded with a discarded workout); a denied location permission leaves a workout with no route. Finish writes the workout to Apple Health AND sends the run to the phone as a queued `runFinished` message (`OutboundPayloads.runFinished`, `WatchSessionManager.sendRunFinished`; a `WatchRunResult` with the builder's distance, energy and active seconds, the accepted route as `[t, lat, lon, alt, hacc, seg]` rows (`seg` goes up on every resume; no altitude is `-9999`) and heart-rate `[t, bpm]` rows, thinned to 1500 and 600 rows). The Health workout is stamped with `SparkyFitnessSessionId` (the run's `clientId`), so the HealthKit import skips it: the message is the only route into the diary, so the phone writes it to a stored queue before anything else. Phone side: `onRunFinished` (module event, same four-place rename rule as the other messages) → `useWatchRunBridge` (mounted in `WatchWorkoutGate`) validates with `parseWatchRunPayload` (`utils/watchRun.ts`) → `enqueueWatchRun` (`services/watchRunQueue.ts`, AsyncStorage, deduped by `clientId` against the queue and the last 50 filed) → `processWatchRunQueue` calls `saveWatchRun` (`services/watchRunSave.ts`: a normal Walking/Running entry from the watch's distance and active time, then the gps-track with splits for an outdoor run, then `watch-telemetry` with heart rate and the measured energy, best effort). When it creates the entry it also gets the steps over the run window (`measureWatchRunForm` in `services/stepDistance.ts`: Apple Health's steps first through `getHealthStepsBetween`, which the watch writes so the phone can be left behind, else the phone's pedometer with `askForPermission: false`, steps scaled by the moving share, ignored when there are under 150 of them or when they imply an impossible stride for the distance, i.e. the phone was not carried) and sends `avg_cadence` and `stride_length_cm` from `computeFormMetrics` against the stored distance (for a treadmill run the figure the wearer entered on the wrist), best effort. `saveWatchRun` resolves to `{ entryId, form }`; the queue stores the form beside the entry id so a retry does not measure again, and hands it to `onFiled` / `announceWatchRun` / `watchRunSummary` as `RunSummaryParams.form` (with `steps`). It retries whenever the server is connected, keeps the entry id so a retry never logs twice, and drops a run only for a non-retryable 4xx. The risk to know: a run whose message never reaches the phone is in Apple Health but not the diary (the stamp hides it from the import). Only one workout session can exist on the watch, so `WatchRunStore.canStart` refuses while a strength workout or the phone-GPS recording's session is live, and `RecordingStore` does not start its heart-rate session while a wrist run is active. A run left going when the watch app is killed is picked back up: while it runs the controller writes a `WatchRunSnapshot` (`Domain/WatchRunSnapshot.swift`: identity, kind, place, route and heart-rate rows, last figures; a file in Application Support, rewritten at most every 15 s and on pause/resume, removed when the run ends or fails) and `WatchSessionManager.recoverLiveWorkoutIfNeeded` asks `WatchRunStore.recoverIfNeeded` first, before the strength-workout path (which would otherwise end the session as a leftover). Only a run with a snapshot is claimed, and only when the recovered Health session is the same activity type; the route builder cannot be re-attached, so the route in Health restarts at the relaunch (the phone still gets every fix, with a new `seg` across the gap). If the Health session was lost but the snapshot survived and holds at least a minute and some distance, the run is sent to the phone as it stood and the summary is shown; a snapshot older than 12 h is dropped. A saved run's snapshot is kept until `WatchRunStore` has queued the message for the phone (so a kill in between still sends it on relaunch, and the phone dedupes by `clientId`); a failed Health session (`didFailWithError`) sends the run on the same way instead of discarding it; a phone-armed strength workout (`handle(workoutStart:)`) is ignored while a wrist run is active, and `canStart` waits for the launch recovery when a snapshot exists. Split cues and laps: `WatchRunStore.cueSplitIfDue` (on each metrics update) buzzes via `Haptics.step()` at every whole km/mile in the phone's distance unit and, when the run's voice cues are on (`WatchRunStore.settings`, a `WatchRunSettings` of `autoPause` and `voiceCues`: taken from the phone's `runStart` request, or for a run begun on the wrist from the context's `runVoiceCues`/`runAutoPause`, the phone's preferences read by `useWatchCheckInBridge` from `getRecordingPreferences` and re-pushed by `onRecordingPreferenceChange` when a switch flips; kept in `WatchRunSnapshot.settings`; changed mid-run from the gear button's sheet on `WatchRunView` or from the phone's `WatchRunLive` switches, sent as `runControl` actions `autoPauseOn`/`autoPauseOff`/`voiceCuesOn`/`voiceCuesOff`, and reported back in `runLive` as `autoPause`/`voiceCues`; turning auto-pause off while it holds the run paused resumes it, and the controller's `updateSettings` resets both detectors), speaks it through `WatchRunCues` (`AVSpeechSynthesizer` on a `.playback`/`.voicePrompt` session that ducks other audio, a session error printed to the device console; only the latest of several splits passed at once). With voice cues on the run also says when it starts (unless a plan's first step does), pauses, resumes, auto-pauses and is saved (`WatchRunCues.finishText`: distance and time), switching them on mid-run says "Voice cues on.", and the gear sheet has a Test voice button that speaks whatever the switch says; a recovered run does not replay splits already passed. The flag button calls `WatchRunStore.lap()` → the controller's `markLap()` (epoch-ms `lapMarks`, 3 s dedupe, kept in `WatchRunSnapshot.lapMarks` and `WatchRunResult.laps`, sent in `runFinished` as `laps`); `saveWatchRun` cuts an outdoor route with `computeLaps` when laps exist, otherwise per-km/mile splits. The windows are wall-clock, so a paused stretch counts in a lap's duration. Pace chart: an indoor run also records `distanceSeries` (`[active seconds, metres]` about every 10 s from the builder's elapsed time and distance, thinned to 300 and scaled with the distance by `scalingDistance`; kept in the recovery snapshot), sent in `runFinished`, parsed by `parseWatchRunPayload` and passed by `watchRunSummary` as `RunSummaryParams.distanceSeries`; `RunSummaryScreen` draws it with `PaceChart` through `paceSeriesFromDistance` (`utils/cardioSession.ts`, the same 30 s windows as a track) and moves it with the Treadmill distance correction. `saveWatchRun` also posts the series (best effort) to `POST /api/exercise-entries/:id/distance-series` (`exercise_entry_distance_series`, one row per entry; the treadmill distance correction rescales it server-side like the laps), and `useCardioSessionDetail` reads `GET` of the same path when an entry has no route, so `CardioSessionScreen` draws the same Pace card for an indoor run from the diary. Plans: the phone puts `runPlans` in the context (`buildWatchRunPlans` in `utils/watchRunPlans.ts`: the program workout due, tagged `programId`/`programIndex`, then `INTERVAL_PRESETS`, step names already translated; `useWatchCheckInBridge` reads `useRunProgram`), the watch decodes them as `WatchRunPlan` (`ContextPayloadMapper.runPlans`) and `CardioChoicesView` lists them under **Follow a plan** (then Outdoor/Indoor). `WatchRunHealthKitController.start(_:place:plan:)` keeps the plan (and in `WatchRunSnapshot.plan`, so a relaunch carries on), `WatchRunStore` runs a 1 s timer (`cueStepIfDue`) against the builder's active `elapsed`, so pauses never count: a new step taps (`Haptics.step`), is spoken with Voice cues on, and forces a lap mark (`markLap(force: true)`, not the first step), and `WatchRunView.planStep` shows the step, the time left and the next one. `runFinished` carries `planId`, `programId`/`programIndex` (a program workout only) and `planCompleted` (`WatchRunPlan.completed(at:)`, the same rule as `planCompleted` on the phone: every step has run its full length); the module forwards them as `onRunFinished` fields (`programIndex` -1 = none), `parseWatchRunPayload` reads them and `watchRunQueue.tickOffProgram` calls `completeProgramWorkout(programId, index, day of the run)` after the entry is filed (best effort, safe to repeat since the server only moves on for the due index). Summary: when `processWatchRunQueue` files a run it calls its `onFiled` listener, which `useWatchRunBridge` points at `announceWatchRun` (`services/watchRunToast.ts`): a toast (8 s) saying the run is saved with its distance and time, whose tap opens `RunSummary` with `watchRunSummary` (`utils/watchRunSummary.ts`: the watch's own distance and time, the splits, elevation and marked laps from the route outdoors, the laps from `indoorLapWindows` indoors, average heart rate from the readings, and for a completed program workout the program part from the cache the queue just updated via `programSummary`). A listener failing never undoes a filed run. Queue behaviour: a program tick-off that fails for a reason that may pass (offline, 5xx, 401/408/429) keeps the run queued and unannounced, since the stored entry id makes the retry repeat only the later steps; `markDone` is written before the run leaves the queue, so a stop between the two refiles onto the stored entry instead of filing a second one; a caller that joins a running pass makes it look again before it ends (`again`); `useWatchRunBridge` does not drain until the preferences are loaded (the distance unit decides the lap windows) and retries every 60 s while `hasQueuedWatchRuns()`. The plan list reaches the watch with the next context push, so a program change shows after the phone app is opened. The watch Swift has not been compiled outside Xcode.

## Distance interval steps

- Distance interval steps (#244): a plan step can carry `meters` (a distance step that ends once that many metres were recorded in it; `seconds` is only its expected time at `EXPECTED_SECONDS_PER_METER`); `workMeters` in `buildIntervalPlan` makes the work steps distance steps and `sixBy400m`/`fiveBy1k` are presets. `advanceIntervalCursor(plan, cursor, activeSeconds, activeMeters)` in `shared/src/utils/runIntervals.ts` moves an `IntervalCursor` past every step that has ended and `intervalPosition` takes `{ cursor, meters }` and reports `remainingMeters` on a distance step; the phone stores the cursor as `session.intervals.cursor` (a session from an earlier build is placed again from the clock). Distance plans are outdoor only (`IntervalSetup`'s `distanceAllowed`). A distance step is shown and spoken in the unit it was set in (`IntervalStep.unit`, `'mi'` or absent for metres; `stepDistanceText`, `spokenStepDistance`): presets are metres, as on a track, and Custom offers a Meters / Miles switch only when the account distance unit is miles (`IntervalSetup`'s `milesAvailable`; `workUnit` in `IntervalOptions`, quarter-mile steps from 0.25 to 6 mi, stored as whole metres). The "to go" cue is 100 m, or 0.1 mi on a mile step (`stepToGoMeters`). The watch gets the unit as the step's `unit` and mirrors these rules in `WatchRunPlan.distance` and `WatchRunCues`. On the watch `WatchRunPlan.Step.meters` marks a distance step and the controller keeps a `WatchRunPlan.Cursor` (a Swift copy of `advanceIntervalCursor`, saved as `WatchRunSnapshot.planCursor`; keep the two cursor rules in step); `runLive` puts the metres left in `stepLabel` with no `stepRemaining`. A plan with a distance step is complete once every step has ended, by time or by the distance recorded in it (`planCompleted` on the phone passes the cursor and metres; the watch uses `WatchRunPlan.completed(cursor:)`), and the voice coach gives such a step no ten-second warning or countdown and the plan no halfway or last-minute call, since its length is only a guess (`nextCoachingCues` and `WatchCoaching.next` take the cursor and metres).

## Routes

- Routes: `RoutesScreen` (root-stack `Routes`, a Library row) lists the saved routes from `/api/v2/routes` (`services/api/routeApi.ts`, `services/routeService.ts`: `useRoutes`, `useRoute`, `saveDrawnRoute`, `saveActivityAsRoute`, `renameRoute`, `removeRoute`, `pickAndImportGpx` through `expo-document-picker` (a file over 10 MB is refused before upload with `GpxFileTooLargeError`; the picker's cache copy is deleted afterwards) and `shareRouteGpx`, which writes through the same `shareGpxFile` (`services/gpxExport.ts`) as the cardio session's Export GPX; query keys `routesQueryKey`/`routeQueryKey`, so create, rename and import invalidate the whole `['routes']` family, while delete trims the list and refetches only it, because the detail screen is still mounted and would fetch a 404). `RouteDetailScreen` shows the route on `RouteMap` (a real map where `canShowRouteMap()` allows, otherwise the plain SVG `RouteLine`) with distance and climb, rename, Edit route on map (only where `canShowRouteMap()` is true), Share as GPX and Delete. `RouteDrawScreen` is the route editor on `MapSurface` (offered where `canShowRouteMap()` is true; the screen itself also shows a fallback notice on unsupported platforms, and importing a GPX file works everywhere). `RouteDraw` takes an optional `routeId` to open a saved route and save over it with `PATCH /api/v2/routes/:id` (`saveRouteEdits`, which accepts `points` + `cues`; the server recomputes distance and climb); edits are ignored until the route has loaded. Tap to add a point (up to `ROUTE_EDITOR_MAX_POINTS`, 100), tap the line to insert one on it (`utils/routeEditor.ts` `hitTestLine`, within 4% of the visible height; a stretch that still has its saved line is cut there, so the curve is kept), drag a marker to move it, select a marker to delete it or make the stretch before/after it straight; Undo, Redo and Clear walk `EditorHistory` (100 steps); where `canShowSatelliteMap()` is true, a Map/Satellite button switches `mapType` between `standard` and `hybrid` (the platform map's own imagery, no API key; hidden on keyless Android where OpenStreetMap has no satellite layer). The editor state is `EditorState` (waypoints plus one `EditorLeg` per stretch: a `straight` flag and, for a saved route, the `fixed` line and cues it had until that stretch is edited, so untouched parts come back exactly; a saved route opens thinned to at most 60 points). When the person has a routing provider a Follow roads switch snaps every non-straight, non-fixed stretch (otherwise a disabled row says a routing provider is needed, set up in Settings > External Providers on the web app): `planSegments` groups consecutive such stretches into pieces of at most `ROUTE_FOLLOW_ROADS_MAX_POINTS` points, `hooks/useFollowRoadsRoute.ts` sends each piece to `POST /api/v2/routes/generate` (800 ms debounce, answers cached by the piece's waypoints so undo/redo and unchanged pieces cost no request), and `assembleLine` joins routed, straight and kept pieces into one line with recomputed cue distances. Moving a point re-routes only the pieces beside it. The endpoint allows 10 requests per person per 10 minutes, so the hook counts its requests in `utils/routeRequestBudget.ts` (a sliding window of 8, shared by every editor session; the rest is left for the Generate screen): once spent, or after a 429, automatic requests pause, the unrouted pieces stay on the map as straight lines with a message and Retry (a spent budget resumes by itself when the window frees up), and no point is ever lost. Saving waits for every snapped piece to be routed; turning Follow roads off saves the stretches straight. A line with more than `ROUTE_MAX_CUES` cues is saved without cues. `RouteGenerateScreen` (root-stack `RouteGenerate`, offered in the Routes Add menu only when generation is available and `canShowRouteMap()` is true, since its preview is drawn on a map) makes a loop or out-and-back of a chosen distance (in `default_distance_unit`) for run/walk/ride/hike from the person's location or a tapped map point, previews distance, climb and turns, regenerates toward another heading (`nextBearingDeg`) and saves with source `generated` through `saveGeneratedRoute`. `useRouteGenerationCapabilities` (`GET /api/v2/routes/generate/capabilities`: per person, cached 10 min, read through shared `resolveRouteGenerateCapabilities` so a failed check or an older server reads as nothing supported; `useRouteGenerationAvailable` is its `available` flag) gates both and decides what else shows: when the engine offers alternatives `RouteGenerateScreen` asks for `maxAlternatives` loops and shows them as `RouteOptionCards` (Option N with distance, climb and a Flatter / More trail / Shorter label only where the server sent one), and `RouteStyleControls` (surface, hills, avoid steps, avoid busy roads, only the ones the engine supports; steps hidden for a ride) appears on both the generate screen and the Follow roads drawer, with the style part of the follow-roads request key. Generate errors map to short messages in `utils/routeGenerateError.ts` (422 no route, 429 rate limit, 502/504 engine, 503 no routing provider). The pure helpers (waypoint building, limits, error kinds, bearing, loop request, turn counting) live in `shared/src/utils/routeGenerate.ts` so the web can reuse them. `RouteDetailScreen` lists a route's turn cues (`components/RouteCueList.tsx`, straight-on cues hidden). `CardioSessionScreen` has a Save as route button for a workout with a GPS track. Distances use `utils/routeDisplay.ts` and the person's `default_distance_unit`. Adding `expo-document-picker` needs a new native build (`npx expo prebuild --clean`).

## Pace alert

- Pace alert (#250): `RecordActivityScreen` shows `PaceBandCard` (a switch and fastest/slowest steppers in the display unit; for a walk or run on the phone outdoors or on the watch, not a ride or a phone-indoor session). An alert is per run, as in other apps: the switches are off every time the screen opens. Only the last range is remembered (`setPaceBandPreference`, seconds per km, read back through `getRecordingPreferences` as `paceBand`) as the starting point, and `useWatchCheckInBridge` sends it to the watch as `runPaceMinSecondsPerKm`/`runPaceMaxSecondsPerKm` so the watch's start screen can offer it. `normalizePaceBand` and the pure `stepPaceAlert` rule are in `@workspace/shared` (`utils/paceTargets.ts`); `Domain/WatchPaceAlert.swift` is the Swift port (`WatchPaceBand`, `WatchPaceAlertState`, plus `WatchRecentPace`, the pace over the last 30 s from the builder's distance and active time) and the constants must stay in step: the pace must stay 3% past an edge for 8 s before an alert, repeating at most every 30 s, and crossing to the other side starts the wait again. Phone recording: `startRecording({ paceBand })`, `gpsRecordingService.checkPaceBand` after each batch of fixes (pace over the last 100 m via `currentPaceSecondsPerUnit`) buzzes and, with voice cues on, speaks `paceAlertCue`; `session.paceBand` is persisted, the alert state is not, and `setRecordingPaceBand` changes it mid-run (nothing calls it yet). Watch run: `WatchRunSettings.paceBand` (nil = off; kept in the snapshot) comes from the phone's `runStart` (`paceMin`/`paceMax`, sent by `startRunOnWatch`) or, for a run begun on the wrist, from the **Alerts** row at the top of the Cardio sheet (`RunAlertsView` in `WorkoutView.swift`: a Pace alert and a Heart rate alert, each a toggle with a Fastest/Slowest or Lowest/Highest stepper that the Digital Crown also turns, starting from the phone's last range or 5:00–5:30/km and 130–150 bpm; the choice lives in the sheet's state, so it resets for the next run, and `WatchRunStore.start(..., alerts:)` applies it); `WatchRunStore.checkPaceBand` runs on each metrics update (indoors too, on the scaled estimate) and gives a `directionDown` tap for too fast or `directionUp` for too slow (`Haptics.pace`) and, with voice cues on, the same words through `WatchRunCues`; the gear sheet's Pace alert switch (`setPaceAlert`) turns it on or off mid-run, using the phone's last range (or the default) when it has none. Per-step targets: a plan step can carry `pace` (a `PaceBand`; `applyPaceTargets` in shared puts the Record screen's fast-stretch range on every `work` step, its easy-stretch range on every `recovery` step and its warm-up and cool-down range on the `warmup` and `cooldown` steps, and a step left without a range keeps the run's; `isValidIntervalPlan` rejects an unusable range). While a step has one, it beats the run's range, a step without one keeps the run's range, and a new step starts the wait again (`checkPaceBand` on the phone, `WatchRunStore.checkPaceBand` on the watch, whose `WatchRunPlan.Step.pace` comes from `paceMin`/`paceMax` on each step of the plan payload). The range can also be changed mid-run on the phone recording's screen (`setRecordingPaceBand`). Heart-rate targets work the same way (`heartRateTargets.ts` in shared: 2 bpm margin, 15 s before the first alert, 45 s between repeats, since heart rate lags effort; `Domain/WatchHeartRateAlert.swift` is the port): `HeartRateBandCard` (needs a paired watch) on the Record screen for the run, for a plan's fast and easy stretches (`applyHeartRateTargets`, `IntervalStep.heartRate`, `hrMin`/`hrMax` on plan steps, which is how the watch gets the warm-up and cool-down range too) and mid-run (`setRecordingHeartRateBand`); the last range is remembered with `setHeartRateBandPreference` and sent in the context as `runHeartRateMinBpm`/`runHeartRateMaxBpm` (a starting point only), and in `runStart` as `hrMin`/`hrMax`. On the phone recording the reading is the watch's live heart rate: `useWatchRecordingBridge` hands each `liveHeartRate` to `noteLiveHeartRate`, which gives a buzz and, with voice cues on, `heartRateAlertCue` ("Heart rate high. Ease off." / "Heart rate low. Pick it up."); with no watch there is no reading and no alert. On the watch `WatchRunStore.checkHeartRate` judges `metrics.heartRate` on each update, with `Haptics.heartRate` and a gear-sheet switch. The phone's `WatchRunLive` screen has Pace alert and Heart rate alert switches too (`runControl` actions `paceAlertOn`/`Off` and `heartRateAlertOn`/`Off` call the watch's `setPaceAlert`/`setHeartRateAlert`, which use the run's range or the phone's last one, and `runLive` reports `paceAlert`/`heartRateAlert` as whether a range is set; hidden for a watch build that does not report them). Suggested ranges: while a plan is chosen (and the pace cards show: outdoors, or on the watch), `SuggestedRangesCard` offers starting ranges for the fast and easy stretches and a **Use these** button that switches the matching cards on with them; nothing is applied until it is tapped. `useSuggestedRanges(activity, enabled)` builds them (a fast, an easy and a warm-up and cool-down range each): pace from `referencePace` (`utils/suggestedRanges.ts`: the distance-weighted average pace of the latest 8 outdoor sessions of the same sport in the last 60 days of the cardio list, `useCardioSessions('90d')`, at least 2 sessions of 1 km or more) with `suggestedPaceRanges` putting fast stretches at 84-94% of it, easy ones at 105-122% and the warm-up and cool-down at 110-240% (a walk 90-98%, 102-115% and 100-160%), rounded to 5 s and kept inside what the alert accepts; heart rate, only with a watch, from the person's heart rate zones (`useHeartRateZones`, shared `resolveHeartRateZones`): warm-up and cool-down are zone 1, easy is zone 2 and fast is zone 4, rounded to 5 bpm, and offered only when the zones are custom or the max heart rate is the person's own or from their date of birth. They are estimates, said so on the card, and a ride gets none. Zone 2 steps (`StepEffort` `zone2`) are not one of those suggestions: `useZone2HeartRateBand` (the second zone of the person's own heart rate zones, from `useHeartRateZones` through shared `zone2HeartRateBand`; null until zones are known, and for percent-of-maximum zones on the fixed fallback maximum; custom and heart-rate-reserve zones always give a band) puts the range on every Zone 2 step through `applyHeartRateTargets({ zone2 })` on the Record screen's plan and in `buildWatchRunPlans`, with no tap and with or without a watch. `IntervalCard` shows the target and, for a Zone 2 step, a cue from `stepHeartRateGuidance` (`utils/stepHeartRateGuidance.ts`: in range, above or below the range loosened by shared `zone2LiveBand`, waiting for a reading when a watch is paired, or the talk test with no watch or no range); `noteLiveHeartRate` judges a Zone 2 step against the same `zone2LiveBand` (the lower edge relaxed for the first three minutes, up to 5 bpm of drift on the upper edge between 20 and 60 minutes), so the buzz and the card agree. The only live heart rate source is the paired Apple Watch (no chest-strap or phone-strap source exists), and the watch's own Swift alert judges the plain range without the drift allowance. Not yet done: per-stretch ranges for a plan started on the wrist. Switching an alert off mid-run silences a plan step's own range as well as the run's (`paceStepsOff`/`heartRateStepsOff` on `WatchRunSettings` and the phone session; a range set again turns it back on), and `runLive` reports `paceAlert`/`heartRateAlert` as whether any range is active, step ranges included. The run's live screen is sized so the plan strip, readings and button row fit a 41 mm watch without scrolling (`CardioLiveLayout`, `SquircleButton`'s `height`).

## Phone starts the watch

- Phone starts the watch (walk and run): when a watch is paired (`useWatchConnectivity`) and the activity is a walk or run, `RecordActivityScreen` asks Outdoor/Indoor first (`indoor`) and then shows **Record with** (`recordWith`: `phone` (default) or `watch`, labelled Phone GPS / Watch GPS outdoors and Phone / Watch indoors, each with its own hint); a ride is phone-only. Indoor + Phone is the step-counted phone session above, Indoor + Watch the watch's treadmill run. The Auto-pause and Voice cues switches (`components/recording/RecordingSwitchRow.tsx`) show for both devices and save the same preferences; auto-pause is hidden (and sent off) only for a phone indoor session, which gets no location fixes to judge by (the watch judges indoors by its step counter), and the voice picker is phone-only. With a watch choice Start calls `startRunOnWatch` (`services/watchRunControl.ts`, which sends the two switches as `autoPause`/`voiceCues` in `runStart`) instead of `startRecording`, then opens `WatchRunLive`. Messages (same four-place rename rule): `runStart` {requestId, kind, place, requestedAt (ms), optional plan from `buildWatchStartPlan`} is sent by the module's `startRun` with `transferUserInfo` (queued) plus `sendMessage` when reachable, then `launchWatchApp(activity:indoor:)` opens the watch app so the `HKWorkoutConfiguration` location type matches; `runControl` {runId, action pause|resume|lap|finish|discard, controlId} via `sendRunControl`, same transports. On the watch `WatchSessionManager.route` hands them to `WatchRunStore.startRequested` (dedupes by requestId, ignores a request older than 120 s or while `!canStart`) and `applyRemote` (dedupes by controlId, needs `runId == healthKit.runId`). The watch's `runLive` carries the `requestId` (nil for a run begun on the wrist), which settles the phone's pending request in `watchRunLiveStore` (`pending`, shown as "Starting on your watch…" for up to `WATCH_RUN_PENDING_MAX_AGE_MS`; the stale-run sweep leaves it alone). The run still files through `runFinished`, so a phone that goes away mid-run loses nothing; the wrist-only start (Cardio row) is unchanged. The watch Swift has not been compiled outside Xcode.

## Treadmill distance

- Treadmill distance: a watch run recorded indoors has no route, so its distance is the watch's motion estimate. `watchRunSummary` sets `RunSummaryParams.editableDistance` (indoor and filed), and `RunSummaryScreen` then shows a "Treadmill distance" card: the person types what the machine showed (in their distance unit), `setExerciseEntryDistance` posts it to `POST /api/exercise-entries/:id/distance` (km), and the screen swaps the figure, the pace and the lap distances (scaled by the same factor, as the server does). When the run has a measured form with `steps`, the stride is worked out again from the corrected distance and written with `setExerciseEntryStrideLength` (`PUT /api/exercise-entries/:id` with only `stride_length_cm`, which the server merges without touching the rest; `null` clears a stride the new distance cannot support). No server change was needed for that; the `/distance` route still does not touch stride. Indoor distance learning: the watch's indoor figure is Apple's motion estimate, which the app cannot retrain, so it learns a correction factor instead, one per walk and run (`utils/indoorDistanceScale.ts` `learnScale`: the first correction is taken as is, later ones averaged geometrically over at most three, clamped to 0.5–2, an entry within 1% of what was shown teaches nothing). `services/watchIndoorScale.ts` stores it and `useWatchCheckInBridge` sends it as `indoorDistanceScale` (`{walk, run}`). The watch (`WatchRunStore.distanceScale`, set at start and on recovery from `IndoorDistanceScale.factor`) multiplies its live indoor distance and the finished run by it, and sends the factor as `distanceScale` in `runFinished` (the phone module's `normalizedRunEvent` passes it and `estimatedDistanceMeters` through; it forwards only listed keys). An indoor finish first asks "Treadmill distance?" on the wrist (`Phase.confirmingDistance`, `TreadmillDistanceView` with the strength keypad, or Keep watch distance); the run is held, its snapshot kept, until the answer, and an entered figure goes out as `distanceMeters` with the shown one as `estimatedDistanceMeters`. The phone learns from that pair in `watchRunQueue` once the run is filed, and from a correction on the Treadmill distance card (`RunSummaryParams.watchIndoor`, the factor applied and the distance shown before any correction). It is only reachable from the filed-run toast; there is no later edit screen.
