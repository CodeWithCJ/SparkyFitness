# AGENTS.md

_Last updated: 2026-10-31_

`@workspace/shared` is a source-first TypeScript workspace library package for schemas, constants, and timezone/day helpers consumed by SparkyFitnessServer, SparkyFitnessFrontend, and SparkyFitnessMobile.

## Scope

- This package defines contracts and shared logic, not an app.
- Validate changes from consuming packages (server, frontend, mobile), not in isolation.
- Every schema change here potentially touches three packages.

## Food Assistant State

`schemas/api/FoodAssistant.api.zod.ts` and `schemas/database/FoodAssistant.zod.ts` define lasting preferences, versioned tasks, unresolved ingredients and idempotent operation records. All state is owner-only; these additive contracts do not change existing chat clients.

## Structure

- Family diary copies: `schemas/api/FoodEntryCopy.api.zod.ts` defines reviewed/selected requests in both directions and recipient meal types. `foodEntryCopyFingerprint` remains byte-compatible with older copy-from clients; `copyFingerprintFor(version)` selects the contract for both clients and the server. New copy-to requests use `foodEntryCopyToUserFingerprint`, which also checks notes, meal identity, caffeine, water, and alcohol.

- Barcode search: `schemas/api/FoodLookup.api.zod.ts` and `BarcodeLookup.api.zod.ts` define normalized foods and source comparison results. `utils/barcodeNutrition.ts` supplies one comparison basis for web and mobile.

- `src/schemas/database/` - one Zod file per table (`Foods.zod.ts`, `Exercises.zod.ts`, ~115 files). Agent shortcut: to learn a table shape, read the matching file here instead of the SQL dump. Remote MCP OAuth storage is described by `Oauth*.zod.ts`; `GlobalSettings.zod.ts` includes the feature switch and administrator-managed redirect URI allowlist.
- `src/schemas/api/` - API request/response contracts (`*api.zod.ts`). `VoiceTranscription.api.zod.ts` defines multipart limits/MIME types, transcription responses, voice preference patches, and compatible public service options shared by web/mobile/server.
- `src/constants/` - shared constants and enums (exercises, nutrients, meal types, fasting protocols, medication schedules, cycle phases, etc.).
- `src/utils/plateCalculator.ts` - the plate calculator: `calculatePlateLoad` finds, with a bounded knapsack over the plate sizes (greedy is wrong with limited counts and odd plates), which plates go on each side of a bar for a target weight, using the fewest plates and the heaviest first. It never rounds: when the target is not loadable it returns the nearest loadable totals below and above (`below`/`above`, `shortBy`/`overBy`), and a search too large to run gives `too_large`. Weights are kg or lbs (`PlateUnit`, plate weights up to 3 decimals); the target converts exactly into the inventory's unit. Also `PLATE_PRESETS`/`presetInventory` (kg: 25 to 0.5, lb: 45 to 1.25, with bars), `usesBarbell`, `suggestBar`, `inventoryConfigFrom`. API contract: `PlateInventory.api.zod.ts`, table schema `PlateInventories.zod.ts`. Tested in `SparkyFitnessServer/tests/plateCalculator.test.ts`.
- `src/utils/` - timezone helpers (`todayInZone`, `instantToDay`, `instantForDay`, `dayToUtcRange`, `compareDays`, `addDays`, `isDayString`), cycle/menstruation helpers, unit/calculation utilities, the race plan generator (`racePlan.ts`, `buildRacePlan`), the run program schedule helpers (`runProgramSchedule.ts`, `runProgramCatchUp.ts`, `runProgramTimeline.ts`: `buildProgramTimeline` / `itemsByDay`, and `runProgramActions.ts`: the `PUT /api/v2/run-program` body builders; web and mobile both use them), and the training pace zones (`racePaceZones.ts`: `racePaceZones` turns a recent race result into easy, interval, tempo, marathon-pace and stride ranges with Riegel's formula; `equivalent5kPace` is the shared 5K conversion; `paceZones.ts` holds the effort-based `paceZones`, `thresholdPaceFromEffort` and `PACE_ZONE_IDS`), the running fitness tests (`fitnessTest.ts`: `evaluateFitnessTest` turns a 5K time trial, a 30-minute all-out run (threshold = average pace of the last 20 minutes) or a 12-minute Cooper test (`cooperToFiveKSeconds`) into a threshold pace, an equivalent 5K time, the five `paceZones` and the `racePaceZones` ranges; `inclineSpeedFactor` / `applyIncline` for a treadmill test (ACSM running cost per metre relative to 1% incline, 0 to 15%), `comparePaces` for a retest, `retestStatus` for the six-to-eight-week window, and `levelFromFiveK`, `racePaceFromFiveK` and `programIdForFiveK` for starting a race plan or program from a test; `buildRacePlan` takes an optional `racePaceSecondsPerKm`), and the plan realigner (`runProgramRealign.ts` (`realignProgram` rebuilds the rest of a plan to end on the goal day: drops repeats and the shortest easy runs first, folds lighter weeks, never touches the taper or final workout, keeps two runs a week for three-plus run days, stretches with repeated base weeks when there is room, eases after a long gap, and reports an unrealistic goal with the options; `applyRealign` is the confirmed change, `toRealignResult` the API shape); its contract is in `RunProgram.api.zod.ts`: `realignRunProgramBodySchema`, `runProgramRealignResultSchema`). Zone 2: the helpers (`zone2Guidance.ts`: `zone2HeartRateBand` turns the person's own resolved zones into the Zone 2 target band, `zone2LiveBand` loosens it for the slow start and drift of a long run, `heartRateStanding` says whether a reading is above, below or inside a range). Run programs (`runPrograms.ts`) include the Zone 2 base (`zone2Base`, `zone2Base4`): steps tagged with the `zone2` `StepEffort`, which `applyHeartRateTargets` gives only the `zone2` range and `applyPaceTargets` never gives a pace; `isZoneCheckWorkout` marks the zone-check runs.
- `src/utils/heartRateZones.ts` - the single source of truth for heart rate zones: `resolveMaxHr` (own value, else Nes from date of birth, else observed max, else 190), `resolveHeartRateZones` (three methods: `percent_max`, `heart_rate_reserve` (Karvonen, needs resting HR) and `custom` floors; falls back to percent of max when the chosen method lacks input and says so in `effectiveMethod`), `defaultHeartRateZones()` (the zones before anything is set or loaded), `heartRateZoneBands(zones)` (the five zones with the one shared `HEART_RATE_ZONE_COLORS` palette) and `heartRateDisplayBands(zones, 4 | 5)` (five zones, or four tiers with zones 1 and 2 merged as Light and `HEART_RATE_TIER_COLORS`; used by the web and mobile Heart Rate reports and settings; display only, storage stays five zones), `heartRateZoneRange(resolved, zone)` (bpm range of zone 1-5; the top zone ends at max HR - the function for training programs that need "zone N in bpm"), `computeTimeInZones` (buckets a heart rate series), `percentMaxFloors` / `heartRateReserveFloors`, `floorsFromAppleHeartRateZones` (five custom floors from Apple's preferred zones; null unless there are exactly five, and a missing zone-1 minimum becomes 30 bpm), `bucketsFromAppleWorkoutZones` (a finished workout's five zone durations, keeping time below the first boundary as zone 1; empty when Apple reported no time, null when the group is not five ascending zones). `trainingLoad.ts` weights sessions by these zones. `readiness.ts` (`computeReadiness`) leaves the resting heart rate and HRV factors out when their baseline has fewer than `MIN_BASELINE_NIGHTS` (5) nights and returns the raw `vitals` (current, baseline, nights) next to the factor scores; both the vitals and the night counts are optional so older servers and clients keep working. `runningEstimates.ts` (`computeRunningEstimates`) returns the VO2 max estimate with an optional `series` (median per run day, oldest first) that the mobile Dashboard trend falls back to. The API contract is `src/schemas/api/HeartRateZones.api.zod.ts`.
- `src/utils/sleepSameNight.ts` - one night recorded by two sources (`sleep_entries` can hold several rows per day, including several from one source, such as a night and a nap): `keepMostDetailedSleepEntries` treats a day's records that overlap for at least half of the shorter one as one sleep (also through a chain) and keeps its most detailed record by `sleepEntryDetail` (distinct stages, then other measures such as score, HRV and resting heart rate, then stage segments, then duration; ties go to the earlier bedtime), choosing only among records at least 80% as long as the longest, so a fragment never replaces the night; a nap that does not overlap, or only clips the night, stays in, from the same source or another. `keepMostDetailedSleep(items, place)` is the same rule for any record shape. The server's sleep analytics and sleep history (sleep debt, chronotype) and the web Sleep Report and cycle day log apply it before adding a day's sleep up; tested in `SparkyFitnessServer/tests/sleepSameNight.test.ts`. `mainSleepEntry` picks a day's main sleep among its records (the longest, the earlier bedtime on a tie, as the server's `MAIN_SLEEP_ORDER_SQL`); server sleep science and the web Sleep Report day row take bed and wake times from it, so a nap never stands in for the night.
- `src/utils/exerciseCalorieLink.ts` - linking a logged workout to the same session synced from a watch (#2353): `resolveLinkedCalories` (what each side counts for `sparkyfitness` / `synced` / `higher` / `lower` / `average` / `custom`), `distributeCountedCalories` (spreads a session total over its entries) and `matchCalorieLink` (set `completed_at` times inside the synced workout's window plus 10 minutes, else window overlap). The entry-level counterpart is `entryCaloriesCounted` in `calorieCalculations.ts`. Contract: `setCalorieLinkRequestSchema` and friends in `ExerciseEntries.api.zod.ts`.
- `src/nutrients/` - nutrient catalogs and the goal calculator used by web onboarding, the web Goals editor and mobile Goals (`nutrientCalculation.ts`: per-nutrient recommended values from age, sex, weight, calories and the saved algorithm choices; `nutrientAlgorithms.ts`: the algorithm enums and labels).
- `src/ai/`, `src/cycle/`, `src/medications/`, `src/mood/` - domain-specific helpers. `src/medications/adherence.ts` is the one implementation of medication adherence for web and mobile (`computeAdherence`, `computeChecklistProgress`, `entryMatchesDue`, and the month-calendar helpers `tallyEntriesByDay`, `dayLogStatus`, `tallySymptomsByDay`); `subtype.ts` holds the All | Meds | Supplements filter rules. Both are pure, take timezone and data as arguments, and are tested in `SparkyFitnessServer/tests/medicationAdherence.test.ts` and `medicationSubtype.test.ts`.
- `src/types/` - shared plain TypeScript types that are not Zod-derived.
- Routes: `src/schemas/api/Route.api.zod.ts` (points, turn cues, bodies), `src/utils/routeGeometry.ts` (distance, climb, simplify, bounds, and the `localProjector` / `distanceToSegment` nearest-point helpers the route editor uses), `src/utils/routeGpx.ts` (dependency-free GPX read/write), `src/utils/routeGenerate.ts` (generate and follow-roads request builders, error kinds, turn counts, route style helpers, capability reading and option labels) and `src/constants/routingProviderTypes.ts` (the `valhalla` external provider type; there is no default server URL). `src/constants/weatherProviderTypes.ts` holds the `open_meteo` weather provider type and the public Open-Meteo address used only as a form placeholder. `routeOverlapFraction` / `routesAreDistinct` in `routeGeometry.ts` compare routes in bounded time.
- `src/compare/` - compare any two tracked things: `stats.ts` (statistics), `metrics.ts` (metric catalog: kind, missing-day rule, weekly form, `rolling` for a value read over the 7 days ending on the day, and `since: false` for a metric since mode cannot answer honestly (weight trend); `offeredInMode(key, mode)` is the check for whether a metric is offered by day, week or since), `analyze.ts` (day and week-by-week analysis), `since.ts` (before vs. since a habit started: suggested start, stretches, regularity, pre-trend; its limits are exported as `SINCE_*` constants), `question.ts` (the question model web and mobile share: timing choices, spans and `compareWindow`, custom-range limits, since-start bounds, `SUGGESTED_QUESTIONS`, and the recents helpers `knownCompareQuestions` / `withRecentQuestion`, and `questionForMode`, which drops a chosen metric the mode doesn't offer), `chartData.ts` (chart data both apps draw: `pairedDots` and `displayDots`, `trendLine`, `overTimeData`, `sinceChartData`), `sinceLine.ts` (`sinceLineOptions`: the lines offered for a since answer, with the label formatter passed in so the wording stays in each app), `sinceVerdict.ts` (`sinceVerdictCase`: which since answer to give, as a text-free case with the facts its wording needs (no start, not enough with the short side and why, changed, no clear change, and whether it covers the last year); `sinceAlreadyChanging` and `sinceCoversLastYear`; the phone's and the website's `compareSinceCopy.ts` word each case). The API contract is `src/schemas/api/Compare.api.zod.ts`.
- `src/symptoms/` - generic symptom tracking: constants and enums (scales, templates, sections, option kinds), template section resolution (`resolveSections`), built-in symptoms and pick-lists, head/body region ids for the location maps, custom-field validation, and `symptomEntryDays` (`entryDays.ts`: the days of a window an entry covers, its `entry_date` plus, for an episode, every day from its start to its end or to today in the profile timezone; the web and mobile symptom calendars use it with the list endpoint's `overlapping` flag, so an episode shows on each of its days). The API contract is `src/schemas/api/Symptoms.api.zod.ts`.

## Naming Convention

- `X.api.zod.ts` = API request/response schema
- `X.zod.ts` = database table schema
- Export everything from `src/index.ts`; consuming packages import both types and values via `@workspace/shared`

## Cross-Package Contract Rules

- Changes to `src/schemas/api/` usually affect server routes and both frontend/mobile API clients.
- Changes to `src/schemas/database/` require matching server migrations and RLS policies when changing the stored schema. CI regenerates the schema backup after merge; never hand-edit or regenerate it locally. Mirroring existing columns missing from a Zod schema does not require another migration.
- Timezone/day-string helpers prevent bugs; prefer them over `toISOString().split('T')[0]`.
- Verified commands (run from `shared/`): `pnpm run typecheck`, `pnpm run format:check`, `pnpm run format`, `pnpm run i18n:audit`, `pnpm run validate` (typecheck + i18n audit + format check). The package has no lint or tests of its own; behavior is covered by the consumers' test suites.
- Shared exports ids and data; apps own translation. `pnpm run i18n:audit` (`scripts/audit-user-facing-strings.mjs`) fails when a file gains more prose in `label`/`title`/`description`/`message`/`hint`/`summary`/`body`/`text` properties than `scripts/user-facing-strings.baseline.json` allows (the cycle, GLP-1, and body-region English catalogs are grandfathered). After moving text out, run it with `--update-baseline` to lower the allowance; use `// i18n-ignore` for literals that must stay.
- Formatting uses the same `.prettierrc` as the other packages, and lint-staged formats staged `shared/` files on commit.
- CI (`.github/workflows/ci-tests.yml`) runs `Shared Validate` and re-runs the frontend, mobile, and server jobs on any `shared/**` change.
- Test any shared change from the consumer packages (`pnpm run validate` in SparkyFitnessServer, SparkyFitnessFrontend, and SparkyFitnessMobile after modifying shared).

## Working Rules

- Keep this package export-focused and schema-focused; logic that scales should live in consuming packages.
- Never export stale or unfinished types; if a consumer is drafting code and needs a type not yet here, add it.
